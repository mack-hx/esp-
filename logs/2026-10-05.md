# 2026-10-05 开发日志

## 腿弯曲导致 MPU 读数偏移：加腿角几何补偿 + 标定工具

**用户反馈**：MPU9250 的 Y 轴指向俯仰角，但小车平衡时 MPU 的摆放不是水平的，
具体角度会根据腿的弯曲程度改变。

### 一、先把问题定位清楚（这一步最花时间，但决定了方案）

用户补充的机械信息（问过 4 个问题确认）：

| 事实 | 值 |
|---|---|
| MPU 安装位置 | 车身上，和两个舵机在一个水平面 |
| 能否挪位置 | **不能**（结构限死） |
| 腿的角色 | **主动参与平衡**（但当前版本先做静态） |
| 平衡时腿动不动 | 现在不动，以后会做动态 |

**关键认知修正**：一开始我以为问题出在"测量"上，错了。

两轮车站在地上，**轮轴被地面强制水平**。所以：

- 轮轴相对铅垂线 ≈ 恒定 0°
- 变的是**车身相对轮轴**的角度，而这个角度**完全由腿弯曲程度决定**

MPU 装在车身上，报的是「车身相对铅垂线」——**这个测量本身没错**。
真正的问题是：

> 控制器把「车身 pitch = 0」当成站立目标，但真实的站立目标是
> 「车身相对轮轴 = 某个随腿弯曲而变的角度」。

现有 `PARAM_ANGLE_ZERO` 是个**常量**，只能配准**一个**腿的角度。
腿一弯目标就偏，`ang_zero` 配平就失效。

于是 pitch 读数分解成三项：

```
pitch_MPU = 车身相对轮轴角(要的) + 腿弯曲带来的 + MPU焊歪的固定角
             └─ 被 leg_k 补偿 ─┘        └─ 被 ang_zero 补偿 ─┘
```

### 二、方案：加一个参数 `leg_k`

**只加 1 个新参数**（`leg_k`，单位 °/°），`φ_home` 复用现有的 `PARAM_SERVO_CENTER`
（舵机中心角），不新增。修正放在**信号侧**：

```c
pitch_修正 = pitch_原始 + ang_zero - leg_k * (φ - φ_home)
```

`leg_k = 0`（默认）时整个项退化为 0，**行为和加补偿之前完全一致**，所以不标定也能安全跑。

**为什么放信号侧而不是加在目标倾角上**（这是个设计决策，记一下理由）：

1. 摔倒判定 `balance_check_fallen()` 判的是 `|pitch|`。放信号侧则判定**跟着一起被修正**，
   否则腿弯多了会误判摔倒。放目标值上判定不会跟着变。
2. 目标倾角就干干净净只剩"想让它倾斜多少"（速度环输出），语义清晰，不和配平值混在一起。

**局限性（必须知道）**：舵机是**开环**的（`servo_set_angle()` 只写 PWM，没有位置回读），
拿到的 φ 是"指令角"不是"实际角"，腿受力变形会造成误差。
但这只是个**前馈平移量**，常值误差由平衡环的 Ki 自己吃掉，不需要精确模型。

### 三、顺手修的 2 个真实 bug

这两个不管最后用哪种方案都得修，用户也确认了"一起改"。

#### Bug 1：一个控制周期读了两次 I2C

`balance_read_sensors()` 原来分别调 `mpu9250_get_euler_angle()` 和
`mpu9250_read_gyro()`，这是**两次独立的 I2C 事务**，数据不同时刻。

**危害**：平衡环的 D 项（角速度阻尼）依赖姿态角与角速度的**严格对应关系**。
错位会让阻尼失准，10ms 周期下误差不小。

**修法**：新增 `mpu9250_get_pose(euler, gyro)` 一次读同时出两个，
`balance_read_sensors()` 改用它。旧的 `get_euler_angle()` 保留为兼容包装（内部也只读一次）。

#### Bug 2：互补滤波的 dt 硬编码 `0.01f`

```c
float dt = 0.01f;              // 假设 100Hz
current_angle.pitch += data.gyro.y * dt;
```

**危害**：控制周期一改，陀螺仪积分就错，而且**没有任何提示**，静默算错。

**修法**：改用 `esp_timer_get_time()` 实测两次调用的真实间隔，并夹住上限 100ms
（防止跨设备复位 / 长时间空档时 dt 异常大导致积分发散）。

**踩坑**：加 `esp_timer.h` 报 `No such file or directory`。
按 10-04 日志记的老办法处理——`idf_component_register(REQUIRES esp_timer)`，
然后**删 `.pio/build/<env>/CMakeCache.txt` 重编**才生效。

#### 附带修：I2C 并发保护

`mpu9250_read_data()` 是对外独立接口，控制任务和 UI 页可能同时调用，
两条 `i2c_master_*` 并发操作同一总线会拿到互相穿插的数据。
在底层加 `portMUX` 临界区。代价约 0.4ms（400kHz 下读 14 字节），可接受。

### 四、标定工具（网页，方案 C）

用户选了"网页手动拨腿 + 自动算斜率"。

**为什么这么测才安全且准**：关键在**车身固定不动，只让腿动**。
- 电机全程刹车 + 强制停平衡控制（接口里有安全闸门，每次调用都执行）
- 车放桌上 / 夹具固定 / 手扶
- 这样 Pitch 的变化纯粹来自"腿在动"，混不进地面不平、轮子打滑的干扰
- **全程车一动不动，不存在摔倒风险**

**采样策略**：每个腿角停留 300ms 等姿态稳，连采 30 次求平均，压掉互补滤波残余抖动。
默认建议 5 个点（35/50/65/80/95°）。

**拟合用最小二乘**而不是两点差值：单点差值带噪声，残差还能反映"读数稳不稳"。

**实现细节**：
- `POST /api/legcal`，body `{"act":"reset|move|sample|fit","deg":80}`
- 新增 `json_str()` 工具函数（原来只有 `json_num()`）
- `max_uri_handlers` 16 → 18（原值 16 已接近上限，加路由容易静默失败）

#### 踩坑：退化检查写错了（已修）

第一版用 `fabsf(den) < 1e-6` 判断"腿角拉不开"，**这个检查根本不起作用**。

`den = n·Σx² − (Σx)²` 是**平方和量级**，实测 5 个点全挤在 80~81°
（跨度只有 1°）时 `den = 38884`，永远不接近 0，
结果会算出 `k = 噪声/1°` 这种巨大的假斜率。

**改成判断腿角跨度**：`xmax - xmin < 20°` 直接拒绝。这个检查才真正拦得住。

（这个 bug 是用合成数据离线跑拟合公式验证时发现的，不是靠肉眼看出来。）

## 第二阶段：改走「实测查表」路线（Route B）

### 十一、为什么推翻线性方案，改成查表

上一阶段做的是线性补偿 `leg_k`。但看了 WL1
([lk888l/wheeled-legged_Robot-WL1](https://github.com/lk888l/wheeled-legged_Robot-WL1))
的实现后，发现两个问题：

1. **WL1 用的是二次曲线，不是直线**：
   `pitchBias(h) = bias_min + (h - h_min) * (0.01026*(h + h_min) - 1.258)`
2. **WL1 调度 Kp**：`Kp_eff = Kp_ref + 0.3 * (h - 61.5)`（高腿位加 Kp）

   拿 U 型曲线做算术：直线拟合的**残差可达变化幅度的 53%**。
   也就是说线性方案会丢掉一半以上的补偿量。

用户也说明了：自己的模型和 WL1 尺寸不同，**数据测量的也不精准**。
解析四连杆运动学要 4 根杆长 + 铰接点坐标，5% 的测量误差在死点附近
会被放大到腿高 20% 的误差 —— 底子就不牢。

**结论：改用实测查表。** 它量的是真实世界，把杆长误差、销孔间隙、
装配偏差、打印形变全包含进去了，对「配平」这个用途实测远优于推算。

### 十二、新增 `user/legmap` 组件

| 文件 | 作用 |
|---|---|
| `legmap.h` | 数据结构 + 接口 |
| `legmap.c` | 查表 / 插值 / 可用性判定 / NVS 持久化 |
| `CMakeLists.txt` | 组件注册 |

每条记录 = `{ 舵机角(°), 腿高(mm), 该姿态 Pitch(°) }`，最多 24 个点。
按舵机角**升序插入**（不是 append），支持同角度覆盖。

**为什么不存「四连杆参数」而是存「实测点」**：见上一节，测量不准是根本问题。
存实测点把「模型精度」这个变量彻底消掉了。

### 十三、关键设计决策

**1. 越界不外推，夹到端点**

超出标定范围时机构可能已到死点，曲线形状完全变了，外推出来的值是编的。
夹到端点至少是有据可依的，且补偿幅值始终有界。

`legmap_pitch_comp()` 也统一成夹端点（不是返回 0）——
返回 0 会在范围边界造成补偿**突变**：腿刚过边界，补偿突然归零，车会猛地一歪。

**2. 优先级：查表 > 线性 leg_k > 不补偿**

`balance_leg_compensation()` 里三级降级，任一级拿不到数据就退下一级，
任何一级都拿不到就返回 0（行为退回到最初版本），**保证不标定也能安全跑**。

**3. Kp 按腿高调度**

新增两个参数 `kp_hslope` (%/mm) 和 `kp_href` (mm)：

    Kp_eff = base_kp + kp_hslope * (腿高 - kp_href)

物理依据：腿长 → 重心高 → 绕轮的转动惯量大。同样的 Kp 在高腿位下阻尼不足，
车会发软振荡。**斜率没有通用值，必须自己试车标定**（站不起来那个腿高的 Kp 记下来，
换腿高再记一次，差值除以高度差）。

限幅到 `[0, 200]`，避免腿高跳变时直接把车搞飞。

**4. 补偿仍放在信号侧**（沿用上一阶段的结论）

`pitch_修正 = pitch_原始 + ang_zero - 补偿`

放信号侧而不是加在目标倾角上，是为了让**摔倒判定也跟着对** ——
否则腿弯多了会误判摔倒。

### 十四、实测发现并修掉一个 Bug：单调性检查误杀 U 型数据

离线验证时发现：**真实的四连杆腿高曲线是 U 型**（腿伸直时轮心高，
弯到中间最低，再弯又开始抬），而我最初写的可用性检查要求
「高度随角度单调递增」—— 结果把**所有合法标定数据都判为不可用**。

修法：改成检查**单峰**性（先降后升，最多 1 个拐点）。
拐点 > 1 才是真问题（尺子读错、腿没到位又采了一次）。
1mm 容差吸收量尺误差和机构回差。

这个 bug 光靠读代码发现不了 —— 判据本身写错了，
只有拿真实形状的数据跑一遍才会暴露。

### 十六、网页标定流程（半自动）

新接口（替换掉旧的 `/api/legcal`）：

| 接口 | 作用 |
|---|---|
| `GET /api/legmap` | 取整张表 |
| `POST /api/legmap` | `{"act":"clear\|move\|read\|add","deg":80,"h":61.5}` |
| `POST /api/legmap_fit_legk` | 用标定点反推线性 leg_k（兜底） |

**为什么是半自动**：ESP32 能读 Pitch，但**量不了自己的腿高**。
所以每录一个点都要：点「动腿并读取」（ESP32 读 Pitch）→ 你拿尺子量腿高填进去
→ 点「录入这个点」。

安全闸门保留：每次调用都强制刹车 + 停平衡控制，且放在解析 act 之后、
任何动作之前，保证每个子动作都受保护。

### 十八、待用户操作

1. `pio run -t upload`
2. 手机连 `BalanceRobot_XXXX`，开 `http://192.168.4.1`
3. 展开「**腿高标定（实测查表，推荐）**」：
   - **把车固定住**（桌上/夹具/手扶），全程不落地
   - 点「清空重来」
   - 腿角设 30° → 「动腿并读取」→ **量腿高填进去** → 「录入这个点」
   - 重复 40 / 50 / 60 / 70 / 80 / 90 / 100°（录 6~8 个点铺满行程）
4. 网页会实时提示：点数、腿角跨度够不够、高度是不是在乱抖
5. 录完点顶部「**保存到 NVS**」才落盘
