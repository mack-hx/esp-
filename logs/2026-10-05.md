# 2026-10-05 开发日志

## 腿弯曲导致 MPU 读数偏移：加腿角几何补偿 + 标定工具

**用户反馈**：MPU9250 的 Y 轴指向俯仰角，但小车平衡时 MPU 的摆放不是水平的，
具体角度会根据腿的弯曲程度改变。

### 一、先把问题定位清楚（这一步最花时间，但决定了方案）

用户补充的机械信息（问过 4 个问题确认）：

| 事实 | 值 |
|---|---|
| MPU 安装位置 | 车身上，和两个舵机在一个水平面 |
| 能否挪位置 | **不能**（结构限死） |
| 腿的角色 | **主动参与平衡**（但当前版本先做静态） |
| 平衡时腿动不动 | 现在不动，以后会做动态 |

**关键认知修正**：一开始我以为问题出在"测量"上，错了。

两轮车站在地上，**轮轴被地面强制水平**。所以：

- 轮轴相对铅垂线 ≈ 恒定 0°
- 变的是**车身相对轮轴**的角度，而这个角度**完全由腿弯曲程度决定**

MPU 装在车身上，报的是「车身相对铅垂线」——**这个测量本身没错**。
真正的问题是：

> 控制器把「车身 pitch = 0」当成站立目标，但真实的站立目标是
> 「车身相对轮轴 = 某个随腿弯曲而变的角度」。

现有 `PARAM_ANGLE_ZERO` 是个**常量**，只能配准**一个**腿的角度。
腿一弯目标就偏，`ang_zero` 配平就失效。

于是 pitch 读数分解成三项：

```
pitch_MPU = 车身相对轮轴角(要的) + 腿弯曲带来的 + MPU焊歪的固定角
             └─ 被 leg_k 补偿 ─┘        └─ 被 ang_zero 补偿 ─┘
```

### 二、方案：加一个参数 `leg_k`

**只加 1 个新参数**（`leg_k`，单位 °/°），`φ_home` 复用现有的 `PARAM_SERVO_CENTER`
（舵机中心角），不新增。修正放在**信号侧**：

```c
pitch_修正 = pitch_原始 + ang_zero - leg_k * (φ - φ_home)
```

`leg_k = 0`（默认）时整个项退化为 0，**行为和加补偿之前完全一致**，所以不标定也能安全跑。

**为什么放信号侧而不是加在目标倾角上**（这是个设计决策，记一下理由）：

1. 摔倒判定 `balance_check_fallen()` 判的是 `|pitch|`。放信号侧则判定**跟着一起被修正**，
   否则腿弯多了会误判摔倒。放目标值上判定不会跟着变。
2. 目标倾角就干干净净只剩"想让它倾斜多少"（速度环输出），语义清晰，不和配平值混在一起。

**局限性（必须知道）**：舵机是**开环**的（`servo_set_angle()` 只写 PWM，没有位置回读），
拿到的 φ 是"指令角"不是"实际角"，腿受力变形会造成误差。
但这只是个**前馈平移量**，常值误差由平衡环的 Ki 自己吃掉，不需要精确模型。

### 三、顺手修的 2 个真实 bug

这两个不管最后用哪种方案都得修，用户也确认了"一起改"。

#### Bug 1：一个控制周期读了两次 I2C

`balance_read_sensors()` 原来分别调 `mpu9250_get_euler_angle()` 和
`mpu9250_read_gyro()`，这是**两次独立的 I2C 事务**，数据不同时刻。

**危害**：平衡环的 D 项（角速度阻尼）依赖姿态角与角速度的**严格对应关系**。
错位会让阻尼失准，10ms 周期下误差不小。

**修法**：新增 `mpu9250_get_pose(euler, gyro)` 一次读同时出两个，
`balance_read_sensors()` 改用它。旧的 `get_euler_angle()` 保留为兼容包装（内部也只读一次）。

#### Bug 2：互补滤波的 dt 硬编码 `0.01f`

```c
float dt = 0.01f;              // 假设 100Hz
current_angle.pitch += data.gyro.y * dt;
```

**危害**：控制周期一改，陀螺仪积分就错，而且**没有任何提示**，静默算错。

**修法**：改用 `esp_timer_get_time()` 实测两次调用的真实间隔，并夹住上限 100ms
（防止跨设备复位 / 长时间空档时 dt 异常大导致积分发散）。

**踩坑**：加 `esp_timer.h` 报 `No such file or directory`。
按 10-04 日志记的老办法处理——`idf_component_register(REQUIRES esp_timer)`，
然后**删 `.pio/build/<env>/CMakeCache.txt` 重编**才生效。

#### 附带修：I2C 并发保护

`mpu9250_read_data()` 是对外独立接口，控制任务和 UI 页可能同时调用，
两条 `i2c_master_*` 并发操作同一总线会拿到互相穿插的数据。
在底层加 `portMUX` 临界区。代价约 0.4ms（400kHz 下读 14 字节），可接受。

### 四、标定工具（网页，方案 C）

用户选了"网页手动拨腿 + 自动算斜率"。

**为什么这么测才安全且准**：关键在**车身固定不动，只让腿动**。
- 电机全程刹车 + 强制停平衡控制（接口里有安全闸门，每次调用都执行）
- 车放桌上 / 夹具固定 / 手扶
- 这样 Pitch 的变化纯粹来自"腿在动"，混不进地面不平、轮子打滑的干扰
- **全程车一动不动，不存在摔倒风险**

**采样策略**：每个腿角停留 300ms 等姿态稳，连采 30 次求平均，压掉互补滤波残余抖动。
默认建议 5 个点（35/50/65/80/95°）。

**拟合用最小二乘**而不是两点差值：单点差值带噪声，残差还能反映"读数稳不稳"。

**实现细节**：
- `POST /api/legcal`，body `{"act":"reset|move|sample|fit","deg":80}`
- 新增 `json_str()` 工具函数（原来只有 `json_num()`）
- `max_uri_handlers` 16 → 18（原值 16 已接近上限，加路由容易静默失败）

#### 踩坑：退化检查写错了（已修）

第一版用 `fabsf(den) < 1e-6` 判断"腿角拉不开"，**这个检查根本不起作用**。

`den = n·Σx² − (Σx)²` 是**平方和量级**，实测 5 个点全挤在 80~81°
（跨度只有 1°）时 `den = 38884`，永远不接近 0，
结果会算出 `k = 噪声/1°` 这种巨大的假斜率。

**改成判断腿角跨度**：`xmax - xmin < 20°` 直接拒绝。这个检查才真正拦得住。

（这个 bug 是用合成数据离线跑拟合公式验证时发现的，不是靠肉眼看出来。）

## 第二阶段：改走「实测查表」路线（Route B）

### 十一、为什么推翻线性方案，改成查表

上一阶段做的是线性补偿 `leg_k`。但看了 WL1
([lk888l/wheeled-legged_Robot-WL1](https://github.com/lk888l/wheeled-legged_Robot-WL1))
的实现后，发现两个问题：

1. **WL1 用的是二次曲线，不是直线**：
   `pitchBias(h) = bias_min + (h - h_min) * (0.01026*(h + h_min) - 1.258)`
2. **WL1 调度 Kp**：`Kp_eff = Kp_ref + 0.3 * (h - 61.5)`（高腿位加 Kp）

   拿 U 型曲线做算术：直线拟合的**残差可达变化幅度的 53%**。
   也就是说线性方案会丢掉一半以上的补偿量。

用户也说明了：自己的模型和 WL1 尺寸不同，**数据测量的也不精准**。
解析四连杆运动学要 4 根杆长 + 铰接点坐标，5% 的测量误差在死点附近
会被放大到腿高 20% 的误差 —— 底子就不牢。

**结论：改用实测查表。** 它量的是真实世界，把杆长误差、销孔间隙、
装配偏差、打印形变全包含进去了，对「配平」这个用途实测远优于推算。

### 十二、新增 `user/legmap` 组件

| 文件 | 作用 |
|---|---|
| `legmap.h` | 数据结构 + 接口 |
| `legmap.c` | 查表 / 插值 / 可用性判定 / NVS 持久化 |
| `CMakeLists.txt` | 组件注册 |

每条记录 = `{ 舵机角(°), 腿高(mm), 该姿态 Pitch(°) }`，最多 24 个点。
按舵机角**升序插入**（不是 append），支持同角度覆盖。

**为什么不存「四连杆参数」而是存「实测点」**：见上一节，测量不准是根本问题。
存实测点把「模型精度」这个变量彻底消掉了。

### 十三、关键设计决策

**1. 越界不外推，夹到端点**

超出标定范围时机构可能已到死点，曲线形状完全变了，外推出来的值是编的。
夹到端点至少是有据可依的，且补偿幅值始终有界。

`legmap_pitch_comp()` 也统一成夹端点（不是返回 0）——
返回 0 会在范围边界造成补偿**突变**：腿刚过边界，补偿突然归零，车会猛地一歪。

**2. 优先级：查表 > 线性 leg_k > 不补偿**

`balance_leg_compensation()` 里三级降级，任一级拿不到数据就退下一级，
任何一级都拿不到就返回 0（行为退回到最初版本），**保证不标定也能安全跑**。

**3. Kp 按腿高调度**

新增两个参数 `kp_hslope` (%/mm) 和 `kp_href` (mm)：

    Kp_eff = base_kp + kp_hslope * (腿高 - kp_href)

物理依据：腿长 → 重心高 → 绕轮的转动惯量大。同样的 Kp 在高腿位下阻尼不足，
车会发软振荡。**斜率没有通用值，必须自己试车标定**（站不起来那个腿高的 Kp 记下来，
换腿高再记一次，差值除以高度差）。

限幅到 `[0, 200]`，避免腿高跳变时直接把车搞飞。

**4. 补偿仍放在信号侧**（沿用上一阶段的结论）

`pitch_修正 = pitch_原始 + ang_zero - 补偿`

放信号侧而不是加在目标倾角上，是为了让**摔倒判定也跟着对** ——
否则腿弯多了会误判摔倒。

### 十四、实测发现并修掉一个 Bug：单调性检查误杀 U 型数据

离线验证时发现：**真实的四连杆腿高曲线是 U 型**（腿伸直时轮心高，
弯到中间最低，再弯又开始抬），而我最初写的可用性检查要求
「高度随角度单调递增」—— 结果把**所有合法标定数据都判为不可用**。

修法：改成检查**单峰**性（先降后升，最多 1 个拐点）。
拐点 > 1 才是真问题（尺子读错、腿没到位又采了一次）。
1mm 容差吸收量尺误差和机构回差。

这个 bug 光靠读代码发现不了 —— 判据本身写错了，
只有拿真实形状的数据跑一遍才会暴露。

### 十六、网页标定流程（半自动）

新接口（替换掉旧的 `/api/legcal`）：

| 接口 | 作用 |
|---|---|
| `GET /api/legmap` | 取整张表 |
| `POST /api/legmap` | `{"act":"clear\|move\|read\|add","deg":80,"h":61.5}` |
| `POST /api/legmap_fit_legk` | 用标定点反推线性 leg_k（兜底） |

**为什么是半自动**：ESP32 能读 Pitch，但**量不了自己的腿高**。
所以每录一个点都要：点「动腿并读取」（ESP32 读 Pitch）→ 你拿尺子量腿高填进去
→ 点「录入这个点」。

安全闸门保留：每次调用都强制刹车 + 停平衡控制，且放在解析 act 之后、
任何动作之前，保证每个子动作都受保护。

## 第四阶段：腿高标定拆成左右两腿 + 改测「电机中心↔舵机轴心直距」

### 二十四、用户提的两个标定难题

实测腿高标定时碰到的两个问题：

1. **左右两腿不太齐**：同一根舵机角下，左右两边轮心高度有可见偏差，
   共用一张表补偿永远有一边欠补一边过补，表现是车往一边偏。
2. **拿到空中不太稳**：车稍微摆一下，腿高读数就跳。
   实际上"测轮心离地面距离"这件事本身就脆——轮子是悬空的，
   高度完全取决于车身当前姿态，一点小摆动就是几 mm 的跳变。

### 二十五、解决方案 + 设计决策

#### 1. 改测「电机中心 ↔ 舵机输出轴中心」直线距离（用户提的方案）

两个点都是打印件/金属件上的**硬位置**，尺子一量就是定值，
**不受车身姿态/MPU 漂移/弹簧回弹影响**。录一次能用很久。

字段名 `height_mm` 保留不动（避免插值/判定代码大改），但**含义已变**为直距。
注释里、网页文案里、README 里都明确写清楚。

#### 2. 左右两腿各一张表（`legmap_all_t.legs[LEG_LEFT/RIGHT]`）

数据结构加 `LEG_ID` 枚举（`LEG_LEFT`/`LEG_RIGHT`），所有 API 加 leg 参数。
NVS 里存的 blob 升级到 v2：原来是单表，现在是 `legmap_all_t`（含两张表）。
版本号不匹配自动丢弃旧数据。

#### 3. 两张表怎么采（用户确认"分两次标定"）

现在两路舵机镜像同动，**一次只能采一条**：

- **第一次采左腿**：把右腿（连杆/舵机）物理上固定到中立位不参与，
  只动左腿，读到的 Pitch 变化 = 左腿单独贡献。标完左表。
- **拆下来换右腿**：固定左腿，只动右腿，标右表。

网页标定面板前加了 L / R 两个 Tab 切换"现在录的是哪张表"。
后端接口的 `leg` 字段（"L"/"R"）决定往哪张表写。

#### 4. 补偿逻辑：左右各查各的，叠加

```c
pitch_修正 = pitch_原始 + ang_zero − (左表.pitch(φ_L) − 左表.pitch(φ_home)
                                       + 右表.pitch(φ_R) − 右表.pitch(φ_home))
```

现在两路舵机是镜像的，`φ_L == φ_R`，但查表仍分两路走——
这样未来舵机如果改成独立驱动，**整套补偿代码不用动**。

降级条件：双路都查表可用 > 任一路不可用 → leg_k 线性 > 不补偿。
任一路不可用就退回 leg_k，**不要"半查表半线性"**（那样补偿项会跳）。

#### 6. 加了离线测试 (PC 直接 gcc 跑)

新加 `test/test_legmap_pc.c` + `test/legmap_offline.h` + 桩头 `esp_err.h` / `esp_log.h`。
`legmap.c` 的 NVS 段用 `#ifndef LEGMAP_OFFLINE_TEST` 包起来，离线时不参与编译。

## 第五阶段：接通电机输出（车第一次有可能站起来）

### 三十一、先分析标定数据：回差其实不是问题

用户反馈"舵机角度固定后手还能摆动，导致上下来回测的距离不一样，
标定距离只有大概"。我先从 NVS 把 34 个标定点全 dump 出来做定量分析。

**NVS 里的实际数据**（`legmap/m` blob，两张表）：

| | 点数 | servo 范围 | 直距范围 | pitch 范围 |
|---|---|---|---|---|
| L 腿 | 18 | 30°~100° | 175→65 mm | -0.72°→+3.74° |
| R 腿 | 16 | 30°~100° | 185→71 mm | -0.38°→+3.66° |

两条曲线的斜率（**量纲要说清楚，这是关键**）：

| | dh/dservo | dpitch/dservo | 1mm 直距误差 = 多少 pitch 误差 |
|---|---|---|---|
| L 腿 | -1.512 mm/° | +0.0557 °/° | **0.037°** |
| R 腿 | -1.673 mm/° | +0.0714 °/° | **0.043°** |

**结论：回差不构成问题。** 换算链条是
`回差 Δh → Δservo = Δh/|dh/dservo| → Δpitch = Δservo × |dpitch/dservo|`：

| 直距读数差 | pitch 补偿误差 |
|---|---|
| 1mm | 0.04° |
| 3mm | 0.11° |
| 10mm | 0.40° |

根因：**几何补偿对舵机角是低增益的**（0.064 °/°）。
舵机角那点回差根本传不到 pitch 上。所以"标定距离只有大概"这个担心，
对 pitch 补偿这条链路不构成影响。

**真正把数据搞脏的是 pitch 那列的噪声**：
L 腿信号/噪声只有 2.9（变化 4.46°，残差 RMS 0.77°），
且残差自相关显示是**低频漂移**（相邻残差同号 11/17 次）——采样时车没真正固定住。
最扎眼的：L 腿 30°/33°/35° 三点 pitch 是 -0.72 → +1.83 → -0.59，
同期直距只动 8mm，机构上不可能让 pitch 摆 2.5°，**这是纯测量噪声**。

**试过"加多点平滑"，无效**：跑留一法交叉验证（拿掉一点用剩下的预测它），
邻域最小二乘只降 4% 噪声（0.639° → 0.614°）。
原因是低频漂移方向一致，邻域平均压不掉同向漂移。

**用户决定**：不再折腾标定，按现有参数往下走，先看能不能站起来。

### 三十二、接通电机输出 + 加 bal_sign 参数

原来的 `balance_control_step()` 里是 `s_data.motor_a = 0; motor_b = 0;` 写死，
**PID 输出根本没接到电机**，这是车不可能站起来的直接原因。

**改动**：

1. **驱动方式改为双轮同向**（不是差速）
2. **新增 `bal_sign` 参数**（+1/-1），方向搞反了网页改一下即可，不用重烧
3. 修 `balance.h` 里过期的错误注释
4. `PARAM_DATA_VERSION` 3→4

**为什么必须改"差速→双轮同向"**：
早先 `balance.h` 注释写的是"坦克转向/差速驱动"，**那是错的**。
差速只能让车原地转，产生不了把重心托回来所需的**平移**加速度，扶不住倒下的车身。
要托住重心必须让两轮**一起**朝倒的方向跑，靠轮子的牵引力把重心甩到轮轴上方 ——
这是标准 inverted-pendulum-on-wheels 平衡车的做法。

**踩坑：`param` 的 step 填错会让滑块跳变**

最初给 `bal_sign` 填 `step=2.0, min=-1.0`。
`snap_to_step()` = `min + round((val-min)/step)*step`，
网格点是 {...,-1,1,3...}，网页上拖滑块值会"跳着变"，反馈很差。
最后改 `step=1.0` —— **必须保证 min/max 都落在格点上**。

**`bal_sign=0` 的处理**：代码里显式把 0 归为 +1 并打警告。
不能让它静默通过——那样 `out` 恒为 0，看起来像"没输出"，
实际是"符号参数没设好"，很难查。

**验证**：编译 SUCCESS（RAM 11.9% / Flash 24.9%），legmap 离线测试 36/36 通过。

### 三十三、发现并修掉一个真 bug：MPU6500 被误判为"未接"

烧录后串口日志：

```
I MPU9250: I2C 初始化成功 (SCL=1, SDA=2)
E MPU9250: WHO_AM_I 错误: 0x70 (期望 0x71 或 0x73)
E MAIN: MPU9250 初始化失败 (模块未接或 I2C 故障)
W BALANCE: MPU9250 不可用, 平衡控制无法工作
```

用户说"接了啊，mpu9250 页都有读数"——**这个矛盾是关键线索**。

**为什么 UI 页有读数但 init 失败**：两条完全不同的检测路径

| 路径 | 实现 | 行为 |
|---|---|---|
| `mpu9250_init()` | 查 `WHO_AM_I` | 不通过就 `return`，`s_ready` 保持 false |
| `ui_mpu9250.c` 的 `check_mpu9250_ready()` | **只试着读 14 字节数据** | 不查 ID，所以能显示 |

所以 UI 能显示，但 `mpu9250_is_ready()` 返回 false，平衡控制直接判定 IMU 不可用。

**`0x70` 是什么**：查 TDK 官方资料确认 ——
**MPU6500 的 `WHO_AM_I = 0x70`，MPU9250 是 `0x71`**。
MPU9250 本质就是 MPU6500 + 一颗 AK8963 磁力计，
**加速度计/陀螺仪寄存器完全相同，I2C 地址也相同**，而我们代码根本没用磁力计。
所以硬件完全可用，只是 ID 白名单漏了 `0x70`。

**顺带发现一个更隐蔽的隐患**：`mpu9250_init()` 在 WHO_AM_I 失败时**提前 return**，
后面的时钟源选择（`PWR_MGMT_1`）、DLPF 配置、量程设置**全都没执行**。
所以就算 UI 页能出数，用的也一直是芯片上电默认值。修好 ID 后这个隐患自然消失。

**修复**：把 `0x70` 加进白名单，并打印器件型号提示。

```
W MPU9250: 检测到 MPU6500 (WHO_AM_I=0x70), 加速度+陀螺与 MPU9250 兼容, 不支持磁力计
```

## 第六阶段：参照 WL1 修平衡控制的 3 个真 bug + 2 个安全机制

**参考项目**：[lk888l/wheeled-legged_Robot-WL1](https://github.com/lk888l/wheeled-legged_Robot-WL1)
（STM32F411 + TB6612 的轮腿机器人，外形结构与我们相似）。
重点读了 `MotionControlTask.cpp`、`PID.hpp`、`BalanceCompensation.hpp`、
`BalanceStartupGate.hpp`、`MotionParameters.hpp`。

用户提示："**我这里 mpu9250 的 Y 轴是俯仰角**" —— 这句话直接定位到了核心 bug。

### 三十六、先说结论：不是参数没调好，是代码逻辑错了 3 处

之前一直把"车站不起来"归因为 `bal_kp/ki/kd` 是占位值、没试过车。
读 WL1 时发现**代码本身就有 3 个实打实的错误**，参数再好也站不起来。

### 三十七、Bug 1（最严重）：平衡环的阻尼取错了陀螺仪轴

用户那句"Y 轴是俯仰角"是关键线索。核对代码：

| 位置 | 用的是哪个轴 | 对不对 |
|---|---|---|
| `mpu9250.c` 融合 pitch | `gyro.y` | ✅ 姿态角是对的 |
| `balance.c` 取阻尼 | `gyro.x` | ❌ **轴不一致** |

```249:257:1.0/user/control/balance.c   (改前)
            if (!s_lpf_primed) {
                s_gyro_lpf = gyro.x;      // ← 这里
```

**危害**：阻尼项在"车前后摆"这个自由度上取的是 roll 方向的角速度。
对两轮前后走的平衡车来说那基本是**纯噪声**。
所以 `bal_kd` 怎么调都不对 —— 它不是在给车加阻尼，是在往控制回路里灌噪声。
表现就是车发软、抖、参数毫无规律。这也解释了为什么"Kd 怎么调都不行"。

**修法**：取 `gyro.y`，并新增 `gyro_sign` 参数（+1/-1）调符号。
这个符号取决于 MPU 装配朝向，**我无法从代码判断**，必须真机抬轮子测。

> 教训：这类"轴/单位/符号搞错"的 bug，编译和静态检查都发现不了。
> 只有把"谁产生这个量、谁消费这个量"对起来看才会暴露。

### 三十八、Bug 2：控制周期漂移，且 dt 写死

`vTaskDelay(10ms)` 的语义是"**至少**等 10ms"，实际周期 = 10ms + 本次执行耗时。
执行耗时里有 I2C 读（14 字节 @400kHz ≈ 0.4ms）、legmap 插值、快照拷贝等。

但 PID 的 `dt` 参数传的是写死的 `CONTROL_DT = 0.01`：

**危害**：积分和微分都按 0.01 算，实际却是 0.012。
相当于 Kd/积分被**系统性低估**，而且误差随负载浮动
—— 表现为"同一组参数有时行有时不行"。

**修法**（两处一起）：
1. `vTaskDelay` → `vTaskDelayUntil(&last_wake, period)`，从上次唤醒时刻起算，
   执行耗时自动扣掉，周期严格稳定
2. 实测 `dt` 喂给 PID，上限夹 100ms（防长时间抢占后积分发散）
3. `bal_data_t` 新增 `dt` 字段，网页 `/api/status` 透出 `dt_ms`，**可观测**

### 三十九、Bug 3：电机死区（低速爬行 + 突跳）

直流电机 + TB6612 有起动死区：占空比低于某值电机根本不转。
对平衡车的后果是 PID 在接近平衡点时输出长时间停在这个"转不动"区间：
表现为**慢慢往一边倒，然后突然越过死区猛冲一下**。

**修法**（照 WL1 `TB6612::setAVel_raw` 的做法）：
非零输出低于死区时**抬到**死区值。
关键分支：`duty == 0` 直接返回 0 —— **停车必须真的停**，
不能被抬成"最低转速"。`motor_brake()` 走 `ledc_set_duty(0)` 直写，
完全不经过死区函数。

新参数 `deadzone`（默认 8%）。

### 四十、附加 1：启动门控（参照 WL1 `BalanceStartupGate`）

**旧逻辑的问题**：`enable` → 看一眼 pitch 没超限 → 立刻输出。
"没超限"和"稳得住"完全是两回事：
- 车被扶着还在小幅晃 → 旧逻辑立刻放行 → 晃得更厉害
- 推着车启动 → 旧逻辑照样放行 → 立刻冲出去

两种情况都会直接摔，而且**摔的瞬间电机还在全力输出**。

**新逻辑**：连续满足 3 个条件才放行，期间电机保持刹车：
1. `|pitch| < arm_pitch`（默认 8°）
2. `|角速度| < arm_rate`（默认 20°/s）← 这条能抓住"正在被晃动"
3. 持续 `arm_time`（默认 500ms）

**放在 STANDBY 而不是新加状态**：状态枚举被 UI/网页引用，
加新状态要改 4 个文件；STANDBY 的语义本来就是"已上电等解锁"，
门控正是"解锁条件变严了"，语义吻合且改动面小。

用 `!(fabsf(x) <= lim)` 而不是 `fabsf(x) > lim` 判断条件 ——
NaN 的比较永远返回 false，不能让"数据坏了"被当成"条件通过"。

### 四十一、附加 2：电机死区 + 收紧危险默认值

- `motor_max` 默认 **100 → 30**。默认值不该是全功率：
  每次烧录/恢复默认参数就该是安全的
- `deadzone` 新增，默认 8%

### 四十二、D 项改用角速度反馈（参照 WL1）

新增 `pid_update_rate()`，D 项直接取角速度而非误差微分：

| | 误差微分 (`pid_update`) | 角速度反馈 (`pid_update_rate`) |
|---|---|---|
| D 项 | `(err - prev_err)/dt` = 姿态的**二阶导** | `rate` = 姿态的一阶导 |
| 目标阶跃 | 产生**尖峰**（微分冲击） | 无尖峰 |
| 量化噪声 | 二次放大 | 放一次 |
| dt 敏感 | 敏感 | **免疫** |

D 项取负号：车往前摆时电机要往回收一把力。同号会变成正反馈把车推倒。

`pid_update()` 保留（速度环用），并在头文件注明平衡环**不要**用它。

### 四十八、用户提出问题：1.0 加的东西太多，看不懂

**第 4 点是关键**：用户要的是**直接测最终要的量**，
而不是测一个中间变量再靠模型换算。

### 四十九、为什么 1.0 的腿高这条路是错的（想清楚才敢推翻）

1.0 的表是 `{舵机角, 腿高(mm), Pitch(°)}`，补偿靠 `pitch(φ)` 查表。
理论上腿高只是"描述机构的中间坐标"，补偿只用到了 pitch 那一列。

**那腿高这一列到底有没有用？** 逐一检查：

| 用途 | 需要腿高吗 | 结论 |
|---|---|---|
| 算俯仰角补偿 | ❌ 补偿只用 `pitch(φ)` | **不需要** |
| Kp 按腿高调度 | ✅ 但那是个**猜测**（见下） | 唯一的用处，而它是猜的 |

所以**腿高从头到尾就没被真正使用过**。它是纯粹的负担：
要拿尺子量、要拆腿分两次采、量不准还污染数据
（1.0 日志第三十一节实测：1mm 直距误差 → 0.04° pitch 误差，
 信号/噪声比只有 2.9~4.0）。

**而它唯一支撑的 `kp_hslope`（Kp 按腿高调度）本身就没有任何实测依据** ——
WL1 的公式是照他们自己的尺寸和手感定的，我们照抄过来。
用它当"所以需要腿高"的理由，是**循环论证**：
先假设需要腿高，再找一个需要腿高的理由。

**根本问题（一句话）**：

> 控制器只需要知道「这个腿角对应的平衡姿态是多少度」。
> 腿高只是这个答案的中间变量，**不是必要输入**。

去掉它，方案从「二维表 + 分腿 + 降级」退化成「一维表」。

### 五十、1.1 的方案

### 五十二、决策：为什么"点数不足 2 个"直接不补偿，而不是降级

1.0 有三级降级（查表 → 线性 leg_k → 不补偿），逻辑分支很多。
1.1 只有一级：**表可用就用，不可用就返回 0**。

**理由**：降级方案的价值是"数据不全时还能凑合用"。但 1.0 的实测已经证明
`leg_k` 线性近似在 U 型数据上会丢掉 **53%** 的补偿量
（本次 trim 测试里重跑了一遍，30° 处查表补偿 1.500° vs 线性 0.229°，
**丢掉 85%**）。一个丢掉一半的补偿比不补偿更糟 ——
它会让车往一个**错误的方向**偏，比偏 0 更难排查。

**降级只有在"降级方案也足够准"时才值得存在。线性不够准，所以砍掉。**

### 五十三、新增：可用性判据只看一件事

```c
bool trim_is_usable(uint8_t min_points)
{
    if (s_trim.count < min_points) return false;
    if (trim_pitch_span() < 0.05f) return false;   /* 完全没有变化 */
    return true;
}
```

**1.0 踩过的坑**：我最初给"直距曲线形状"写了判据
（要求单峰、拐点 ≤ 1），结果**真实的四连杆直距是 U 型**，
判据把**所有合法标定数据都判成了不可用**。判据本身写错了。

1.1 干脆不判形状 —— 一维表只要"角度升序 + Pitch 有过变化"就够了，
没有任何物理形状假设。**判据越简单，越不容易自己把自己坑了。**

跨度门槛定 0.05°（而不是 1.0 那种"变化太小就报警"）：
实测换角度时 Pitch 变化确实可能只有 0.3°，门槛卡太死会把合法数据判死。
只拦"完全没变化"（说明车根本没扶到不同姿态，或 MPU 没工作）。

### 五十四、踩坑：`lookup()` 少了精确命中分支 —— 查中间的点全查错

**这是本次唯一一个真 bug，而且是离线测试当场抓出来的。**

我写 `lookup()` 时把 1.0 `map_lookup()` 的结构简化了，
把里面的"精确命中"提前 return 删掉了，只留了区间插值：

```c
/* 改前 —— 有 bug */
if (deg > d0 && deg < d1) {          /* ← 严格不等号 */
    ...插值...
}
return m->pts[m->count - 1].pitch_deg;   /* 兜底 */
```

**后果**：查询角度**恰好等于某个中间点**时
（比如表里有 60°，你查 60°），`deg > d0 && deg < d1` 在
`[45,60]` 和 `[60,80]` 两个区间都不满足 → 掉到兜底 →
**返回最后一个点（100°）的值**。

测试输出：
```
[FAIL] 30° 修正后应为 2.40, 实得 4.5000     ← 4.5 是 100° 的值
[FAIL] 60° 相对 40° 应为 1.0, 实得 4.0000
```

**为什么难发现**：
- 编译不报错
- 代码看着完全合理
- 越界查询、插值查询都正常，**只有精确命中中间点是错的**
- 真机表现：车在某几个腿角上会突然歪一下，别的腿角都正常
  —— 这种"大部分时候对、偶尔错"最难查

**修法**：条件改成闭区间
```c
if (deg >= d0 && deg <= d1) {
    float t = (d1 > d0) ? (deg - d0) / (d1 - d0) : 0.0f;
    ...
}
```
`deg == d0` 时 `t=0`、`deg == d1` 时 `t=1`，精确命中自然正确，
而且**不需要额外的精确命中分支**（1.0 那个分支本来就是多余的）。

> 教训：简化别人的代码时，"看起来多余"的那个分支可能正是关键。
> 而且这种 bug 只能靠**跑边界值**发现 —— 我第一版测试里
> `test_interp` 只测了 50°/60° 这种**非表内**角度，恰好绕开了。
> 补上"精确命中中间点"的断言后立刻暴露。

### 五十六、踩坑：离线测试桩头的依赖方向

第一次把 `trim.h` 里的 `esp_err.h` 用 `#ifndef TRIM_OFFLINE_TEST` 屏蔽掉，
结果 `trim.c` 编译报 `unknown type name 'esp_err_t'` ——
因为 `trim.c` 是 `#include "trim.h"` 打头的，桩头没人带进来。

**错误做法**：在 `test/` 下造 `esp_err.h` 假头文件，靠 `-I test` 让 GCC 找到
（1.0 就是这么干的，遗留了 `test/esp_err.h` / `test/esp_log.h` 两个文件）。

**这个做法的问题**：它让"能找到假头文件"变成一个**隐式依赖** ——
换个编译顺序、换个工具、忘了 `-I test`，就直接崩，错误信息还很难懂。

**正确做法**：桩头由 `trim.h` **自己**带进来
```c
#ifdef TRIM_OFFLINE_TEST
#include "trim_offline.h"
#else
#include "esp_err.h"
#endif
```
这样 include 顺序完全不影响结果。1.1 顺手删掉了 `test/esp_err.h`、
`test/esp_log.h` 两个遗留文件。
