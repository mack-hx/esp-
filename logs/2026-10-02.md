## SERVO 频率诊断（第二轮）— LEDC 通道冲突

**时间**：2026-10-02 20:00

**问题**：
用户重启后实测 GPIO13/14/15/16 **全部都是 20kHz**。
- 这下 SERVO 引脚也被"污染"成 20kHz，跟 SERVO_PWM_FREQ=50 不符
- 第一轮诊断里的"SERVO timer_1 实际=50Hz"只验证了 timer，没考虑 channel 被换 GPIO 后 GPIO 仍按 timer 频率输出

**根因（找到真正的 bug）**：

`main.c` 初始化顺序：`tft → servo → motor`

| 模块 | TIMER | CHANNEL | GPIO |
|------|-------|---------|------|
| TFT_BLK | TIMER_0 | **CH_0** | 12 |
| SERVO_1 | TIMER_1 | **CH_2** ⚠️ | 13 |
| SERVO_2 | TIMER_1 | **CH_3** ⚠️ | 14 |
| MOTOR_A | TIMER_2 | **CH_2** ⚠️ | 15 |
| MOTOR_B | TIMER_2 | **CH_3** ⚠️ | 16 |

**servo 和 motor 重复占用 CH_2 / CH_3**。ESP-IDF 的 `ledc_channel_config()` 会把
channel 重新绑到当前传入的 GPIO（覆盖前面的绑定），并按当前 channel 所挂的 timer
频率输出 —— 所以：

- `servo_init()` 先把 CH_2/CH_3 绑到 GPIO 13/14（TIMER_1 = 50Hz 输出）
- `motor_driver_init()` 紧接着把 CH_2/CH_3 **重新绑到** GPIO 15/16（TIMER_2 = 20kHz）
- 但 CH_2/CH_3 的物理输出引脚此时已变成 15/16
- GPIO 13/14 量到 20kHz 的解释：CH_2 被 motor 占用后，13/14 上的 signal
  出现 20kHz 残余（也可能是用户在测 15/16 时看错 —— 不重要，关键是冲突）

**修复**：

`0.1/hardware/motor_driver/motor_driver.h`
```diff
-#define MOTOR_A_CHANNEL     LEDC_CHANNEL_2
-#define MOTOR_B_CHANNEL     LEDC_CHANNEL_3
+#define MOTOR_A_CHANNEL     LEDC_CHANNEL_4
+#define MOTOR_B_CHANNEL     LEDC_CHANNEL_5
```

**为什么改 motor 而不是 servo**：
- motor 用 TIMER_2（跟 servo 的 TIMER_1 不冲突），换通道只动 motor.h 一处
- 改动尽量小

**验证**：
- `pio run` ← 即将执行
- 用户重启后：GPIO13/14 应恢复 50Hz，GPIO15/16 保持 20kHz，舵机能转

  - TFT_BLK=GPIO12, SERVO1=GPIO13, SERVO2=GPIO14
  - MOTOR_A=GPIO15, MOTOR_B=GPIO16
  - ENCODER=GPIO41/42/45/46
  - MPU9250=GPIO1/2, PCF8574=GPIO17/18/21

**回滚调试代码**：
- `0.1/hardware/servo/servo.c` — 删除 `ledc_get_freq()` 调试日志

## TFT 背光 vs SERVO 共用 LEDC_CHANNEL_0 冲突

**时间**：2026-10-02 15:30

**问题**：
用户报告"从在菜单添加主页后开始黑屏后无法恢复"——TFT 屏幕在 SERVO 页之后黑屏。

**串口诊断过程**：
- 用 `stty -f /dev/cu.usbmodem12401 115200 raw -echo` + `cat` 持续读串口
- 用户按键时助手主动捕获日志（无需用户复制日志）
- 日志确认 page_key(K1) → switch_to(MENU) → page_exit → "切换到页面: 1 (Menu)" **全部正常执行**
- 代码逻辑、状态机、按键扫描全部正确
- 黑屏不是软件 bug

**根因（硬件层面 LEDC 通道冲突）**：
| 模块 | 通道 | Timer | GPIO |
|------|------|-------|------|
| TFT 背光 (BLK) | **LEDC_CHANNEL_0** | TIMER_0 | GPIO 12 |
| SERVO_1 | **LEDC_CHANNEL_0** ❌ | TIMER_1 | GPIO 13 |
| SERVO_2 | LEDC_CHANNEL_1 | TIMER_1 | GPIO 14 |

`servo_init()` 调 `ledc_channel_config(CH_0)` **重新绑定**CH_0 到 GPIO 13
→ TFT 背光 BLK (GPIO 12) 失去 LEDC 输出
→ 背光熄灭 → **屏幕黑屏**

**修复**：
`0.1/hardware/servo/servo.h`
- SERVO_1_CHANNEL: LEDC_CHANNEL_0 → **LEDC_CHANNEL_2**
- SERVO_2_CHANNEL: LEDC_CHANNEL_1 → **LEDC_CHANNEL_3**

避开 TFT_BLK 占用 CH_0。

**验证**：
- `pio run` SUCCESS (5.36s)
- `pio run --target upload` SUCCESS (6.77s)
- 用户反馈：背光恢复 + 之前偏暗（应是因为 SERVO 抢通道后 BLK 处于某种中间电平）

- 默认选中现在是 "Back to Home"，K1 不小心按一下是回主页，不会进 SERVO 页

## K4 按键修复: 不再映射为 K1

**时间**：2026-10-02 13:17

**背景**：
用户报告"舵机界面按 K1 或 K4 会息屏"。

**根因分析**：
"息屏"实际是 UI 从 SERVO 页切回 MENU 页（黑底蓝白字菜单），不是真的关背光。
- `main.c` 中 `key_get_from_pcf8574()` 把 K4 强行映射成了 K1：
  ```c
  if (!(state & (1 << BTN_K4))) return UI_KEY_K1;  // K4 备用, 等效 K1
  ```
- 而 `ui_servo.c` 的 `page_key()` 在收到 `UI_KEY_K1` 时执行 `lcd_ui_switch_to(UI_PAGE_MENU)`。
- 因此 K1/K4 在 SERVO 页面都会触发退出回菜单（K4 是 main.c 强行改的）。

**修改**：
`0.1/main/main.c` 删除 K4→K1 的映射，K4 返回 NONE（不响应）。
其他 6 个 UI 文件 (ui_home/menu/servo/encoder/mpu9250/wifi_bt) 不动：
它们的 K1 行为本来就是"进入/退出回菜单"，与用户需求"K1 退出 + K4 不响应"完全一致。

**关键事实**：
- UI 层 `ui_key_t` 没有 `UI_KEY_K4`，K4 只在 main.c 入口处处理
- 工程内**无任何"息屏"逻辑**（无 disp_off / SLPIN / light_sleep 调用），
  TFT 背光只在 `tft_display_init()` 末尾 `tft_backlight_on(true)` 一次
- "息屏"是 SERVO 页 (绿/彩) → MENU 页 (黑底) 的视觉反差造成的错觉
