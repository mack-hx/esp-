意思是：版本号链应该连续 `1.1 → 1.2 → 1.3`，**1.2 不能跳过**。

### 二、回滚步骤

按用户选项 a（回退 1.3 → 1.2 → 1.3 重做）执行：

```
1. git rm -r 1.3           # 删 1.3 目录
2. git commit              # 1.3 删除 (commit bb5a0f1)
3. cp -R 1.1 1.2           # 从 1.1 复制 1.2
4. version.txt → 1.2.0
5. 1.2/README.md 写成占位  # 指向 1.1 内容
6. git add 1.2 + commit    # commit 4caeb35
7. cp -R 1.2 1.3           # 从 1.2 复制 1.3
8. version.txt → 1.3.0
9. git checkout 2caea60 -- 1.3/   # 从 1.3 老 commit 拿文件内容
   (避免重新手写 6 个文件, 反正 diff 一样)
10. git add 1.3 + commit   # commit a8d0beb
```

### 八、踩坑 (这次重建)

1. **第一次 `cp -R 1.2 1.3` 时 1.3 已经存在**（之前 `git rm -r 1.3` 之后
   1.3 还在工作区未 commit）, 结果 `cp` 把 1.2 内容**拷进了 1.3**,
   `ls 1.3` 看到一个意外的 `1.2/` 子目录。
   解决: `rm -rf 1.3` 后重来。

2. **`git restore --staged 1.2/ 1.3/` 把 1.3 删除操作也 unstage 了**,
   导致 1.3 还在工作区。重新 `git rm -r --cached 1.3` 才把删除放回 staged。

3. **`git rm` 看到 1.2 文件和 1.3 文件内容相同, 自动识别成 `rename`**,
   这其实是好事: 1.2 内容 = 1.1 内容, 而 1.3 = 1.1 + 改动,
   git 用 rename 标记反映了"1.2 = 1.1 / 1.3 没了"这件事。

4. **从 `2caea60` 恢复 1.3 文件**比手写 6 个文件更快也更准确 (避免再写错),
   反正 diff 一致, commit message 写明"基于 1.2"即可。
