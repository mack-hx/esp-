## 一、本日要解决的用户问题

1. App 前进/后退无反应, 要求跟 `ui_encoder.c` 一样直接转电机, 且速度档位与车上调速档位一致
2. 左右转: 电机方向可调, 要支持原地转向
3. 起立/配平时电机剧烈抖动; 配平应该"只记录平衡时的 pitch", 和电机没关系
4. RGB 不亮, 要查明原因
5. App 状态页 pitch 实时曲线不显示

## 二、问题原因与解决方案

### 1 & 2. App 遥控无反应 / 不能原地转向

**原因**：
- 移动指令想走 `vx` / `w`, 但物模型里**没有这两个标识符**, 平台一律回
  `10412 identifier not exist`, 指令根本下发不到设备。
- 物模型里能写的属性只有 `speed` 一个 (`motor_l` 是只读, 写进去报
  `r rw type error`), 而 `speed` 原本是"速度环目标 (标幺 -1~1)",
  只有方向没有档位, 也表达不了"转向"。
- 平台**只有查询物模型的开放接口** (`query-thing-model`), 没有新增/修改接口;
  控制台新增属性要手机号 + 短信登录, 自动化进不去 → 无法新增"方向属性/档位属性"。
- App 端还有一条"两轮同向结构不支持原地转向"的拦截, 直接把左右转按钮禁用了。

**解决方案**：
- 方向和档位**打包进 `speed` 一个数** (设备端 `apply_move_cmd()` / App 端
  `_dirToCmd()` 对称实现):

  | 指令值 | 含义 |
  |---|---|
  | `0` | 停止 |
  | `±0.2 / ±0.4 / ±0.6 / ±0.8` | 前进(+) / 后退(-), 档位 20/40/60/80 % |
  | `±1.2 / ±1.4 / ±1.6 / ±1.8` | 左转(+) / 右转(-), 档位 20/40/60/80 % |

- 档位表统一到 `hardware/motor_driver/motor_driver.c` 的 `motor_spd_levels[]`
  (`{20,40,60,80}`), `ui_encoder.c` 改成引用这张表 → App 档位与车上调速档位同源。
- 设备端新增**遥控直驱通道** `balance_set_move()`:
  - 前进/后退两轮同向, 左/右转两轮反向 (原地转向);
  - 直驱期间暂停平衡环与状态机, 进入/退出直驱都清 PID 积分;
  - 档位吸附到 20/40/60/80 (`motor_spd_level_snap()`);
  - 左右轮对应关系由 `balance.h` 的 `BAL_MOTOR_A_IS_LEFT` 宏控制 (默认为 1)。
- App 端删除原地转向的拦截, 档位改成 慢/中/快/极速 = 20/40/60/80 %。

### 3. 起立/配平时电机剧烈抖动

**原因**：
- 起立瞬间车多半还歪着, PID 误差一上来输出直接顶到限幅 (±100%), 电机"猛冲"一下,
  看起来就是剧烈抖动。
- 原来的"配平"服务会先停平衡、再采样、再开平衡, 采样期间电机还在跑,
  所以"配平"和电机动作混在一起。

**解决方案**：
- **起立软启动**: 进入平衡状态后输出限幅从 15% 渐开到 100%,
  用时 1500ms (`BAL_RAMP_START_PCT` / `BAL_RAMP_TIME_MS`)。
- **配平只记录 pitch**: 采样 50 个点 (0.5s) 取平均, 作为"配平零点"存进 NVS
  (namespace `bal`, key `pz`, 整数 ×10); 姿态修正链改成
  `原始 pitch − 配平表补偿 − 配平零点`。`calibrate` 服务只调 `balance_calibrate()`,
  **不启停平衡、不碰电机**。
- 删掉 `balance_set_speed_cmd()` / `balance_get_speed_cmd()`, 速度环目标恒为 0
  (原地站立, 不主动走); 走位一律走直驱通道。

### 4. RGB 不亮

**原因**: SK6812 的复位码原为 50µs, 规格要求 > 80µs, 复位时间不够 → 芯片不锁存数据,
灯不亮。

**解决方案**:
- `hardware/led/led_strip_encoder.c` 复位码 50µs → **300µs**。
- 加了 `led_selftest()` (红→绿→蓝→灭, 每档 300ms), 开机在 `led_init()` 后调用,
  用于肉眼确认灯珠链路。**此为临时诊断代码, 确认灯亮后可删**。
- 串口已确认数据链路正常: `LED[0] RGB=(255,0,0) 亮度=255 -> GRB=(0,255,0)` (GRB 顺序正确)。

### 5. App 状态页 pitch 曲线空白

**原因**: uni-app 的 H5 端把 `<canvas canvas-id="xxx">` 渲染成
`<canvas class="uni-canvas-canvas">`, **不保留 canvas-id 属性**,
`document.querySelector('canvas[canvas-id="..."]')` 永远取不到 → ctx 为 null → 空白。

**解决方案**:
- 选择器改成 `canvas.uni-canvas-canvas` (兜底再取第一个 canvas),
  绘制循环里 ctx 为空时重试初始化。
- 绘图尺寸: canvas 按 2x 设备像素设置, `ctx.scale(2,2)` 后绘图用 CSS 像素坐标,
  `_drawChart()` 改用 `_cssW/_cssH` (之前除以 2 会把图压进左上 1/4 区域)。

## 五、留给用户肉眼确认的两件事

1. **RGB 是否真亮**: 固件开机自检会闪红→绿→蓝。仍不亮则是硬件问题
   (SK6812 DIN 是否接 GPIO9、供电/共地), 软件侧位时序已修。
2. **转向方向是否反**: 若左转却向右转, 改 `user/control/balance.h` 的
   `BAL_MOTOR_A_IS_LEFT` 为 0 即可。
3. 确认 RGB 后, 删掉临时 `led_selftest()` 及其 `main/main.c` 里的调用。

### 2. 事故: 设备变成启动循环

- 现象: 串口反复打印 `esp_image: Checksum failed` → `OTA app partition slot 0 is not bootable`
  → `No bootable app partitions`, 日志里累计 68 次重启循环。

  怀疑与**常驻串口抓取占用 `/dev/cu.usbmodem312401`** 有关 —— 串口被 `cat` 占着时,
  esptool 拿不到独占访问, 写入中断就留下半截镜像。
- 处理: 用 `pio run --target upload` 重刷 0.21 (`Hash of data verified`), 设备恢复正常启动。

### 3. 教训 / 约定

- **烧录前必须先停掉串口抓取**, 抓取和烧录不能同时占用同一个串口设备。
- 环境会杀掉后台循环采集脚本 (`while true` + `cat` 收到 SIGTERM/143), 抓取要用工具的后台模式单开一次 `cat`。
