## SK6812 时序问题结论与 Q0 开关版实现

**时间**：2026-10-01 13:30

**背景**：
SK6812 DIN 接 74HC595 Q0，按文档要求本应使用 RMT 外设生成精确时序。
但项目当前无多余 GPIO 可飞线到 SK6812，需评估能否"仅用 Q0 模拟"。

**问题分析**（已查阅 Nexperia / TI / Onsemi 数据手册）：

74HC595 内部有两套独立寄存器：
- **移位寄存器 (Shift Register)**：每个 SCLK 上升沿移入 1 bit
- **存储寄存器 (Storage Register)**：只有 RCLK 上升沿时，移位寄存器内容才**拷贝**到存储寄存器，并更新到 Q0~Q7 输出

**关键事实**：
- RCLK 触发后，Q0 被锁存为某个固定值，并**保持稳定**
- 不触发 RCLK 时，Q0 维持上一次锁存状态，**完全不动**
- SK6812 要求 1 bit 周期 1.25µs 内产生 T0H/T0L 或 T1H/T1L 的高低翻转
- 74HC595 在 1.25µs 内无论怎样操作 SCLK/RCLK，都只能让 Q0 跳变 1 次（不锁存不变 / 锁存后只跳一次）

**结论**：**单纯依靠 74HC595 Q0 物理上无法产生 SK6812 归零码时序**。

**尝试过的方案与可行性**：
| 方案 | 结论 |
|------|------|
| 软模拟 (esp_rom_delay_us(1)) | 1.25µs 内翻转不了 ❌ |
| SPI 硬件外设驱动 HC595 (5MHz) | Rclk 不触发则 Q0 不动 ❌ |
| LEDC PWM 直驱 | Q0 是 HC595 输出稳态，LEDC 无法控制 ❌ |
| Q0~Q7 编码预设色 | SK6812 收到稳态电平，行为是"保持上次颜色" ❌ |

**最终方案**（用户认可）：Q0 开关版 + 颜色亮度缓存

**修改文件**：
- `0.1/hardware/led/led.h` — 重新设计接口
  - 增加 `led_preset_t` 预设颜色枚举（8 种）
  - 增加 `led_set_preset()` / `led_set_brightness()` / `led_get_on()` / `led_get_color()` 函数
  - `led_color_t` 颜色结构保留，但明确标注"仅逻辑记录"
  - 文件头注释说明硬件限制和未来改线方向

- `0.1/hardware/led/led.c` — 实现开关逻辑
  - `current_color[]` / `current_on[]` 数组记录每颗 LED 的逻辑状态
  - 颜色变化时仅做亮度阈值判断（>0 则点亮 Q0）
  - **仅在状态变化时才触发 RCLK**，避免无谓锁存影响 Q1~Q7 其他引脚
  - 7 种预设颜色映射为开/关状态
  - 启动日志明确告知用户 SK6812 实际只支持开关

**后续建议**（不在本次范围内）：
- 改线：将 SK6812 DIN 改接到 ESP32 任意空闲 GPIO（如 PCF8574 INT 引脚 GPIO21、MPU9250 INT 引脚 GPIO3）
- 软件：用 RMT 外设 + 10 MHz 时钟驱动 SK6812，调色调光即可正常工作
- 或者改用普通 LED（仅开关），放弃 RGB 灯珠

**备注**：
- 本次未触碰 `hc595.c` / `hc595.h`，Q1~Q7 输出行为完全保留
- Q0 现在被 LED 模块独占，但 hc595_set_led() 仍然能正常工作
- 调用方在 `main.c` 中按需使用 `led_set_preset(id, LED_PRESET_GREEN)` 等 API

## 修复 Cursor 中的 PlatformIO 集成

**时间**：2026-10-01 13:35

**问题**：
用户反馈截图显示 Cursor 报 `command 'platformio-ide.build' not found`，
并且终端一直停在 `Resolving esp32-s3-devkitc-1 dependencies...`。

**根因分析**：
1. **PlatformIO 扩展没装到 Cursor 扩展目录**
   - Cursor 用 `/Users/m/Library/Application Support/Cursor/extensions/`
   - 扩展实际装在 `/Users/m/.vscode/extensions/`（VS Code 路径）
   - Cursor 启动时找不到 PlatformIO 命令提供者 → 报 `not found`

2. **`.vscode/launch.json` 和 `c_cpp_properties.json` 是 Windows 路径**
   - 旧配置含 `D:/code/code/ESP32/ESP32began/...` 和
     `C:/Users/asus/.platformio/packages/...`
   - macOS 上完全无效，导致 PlatformIO 在解析依赖时卡死

**修复**：

1. **复制 PlatformIO 扩展到 Cursor 目录**
   ```
   cp -R /Users/m/.vscode/extensions/platformio.platformio-ide-3.3.4-darwin-arm64 \
         "/Users/m/Library/Application Support/Cursor/extensions/"
   ```

2. **重写 `.vscode/launch.json`** — 把 Windows 路径改为 macOS `${userHome}`、
   把 `freenove_esp32_s3_wroom` 改为当前环境名 `esp32-s3-devkitc-1`。

3. **重写 `.vscode/c_cpp_properties.json`** — 通用 ESP32-S3 IntelliSense
   配置（删除旧 522 行的 Windows 路径配置）。

**关键点**：
- `${workspaceFolder}` = `0.1/` （项目根）
- `${userHome}` = `/Users/m`
- ESP32-S3 工具链：`/Users/m/.platformio/packages/toolchain-xtensa-esp32s3/bin/`
- `configurationProvider` 设为 `platformio.platformio-ide`，让
  PlatformIO 扩展接管 IntelliSense（避免手动维护 includePath）

**接下来需要做的**（用户手动）：
1. 在 Cursor 中按 `Cmd+Shift+P` → "Developer: Reload Window"
2. 等待 PlatformIO 扩展重新初始化（约 10-30 秒）
3. 状态栏出现 PlatformIO 徽标后，命令面板里 `PlatformIO: Build` 可用

**注意事项**：
- 旧的 `~/.platformio/penv` (PlatformIO 6.1.19) 仍存在。
  Cursor 扩展默认会用 penv 的旧版本——这是 PlatformIO 扩展内部
  行为，与 PATH 无关。
- 如果仍报 `pio` 命令找不到，可能需要点击状态栏的 PlatformIO 徽标
  让扩展重新选择 Python 环境。
