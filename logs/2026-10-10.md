## 修复：1.3/app 安卓端 (app-plus) 白屏问题

### 一、问题
- 用户在安卓真机运行 app 时出现白屏, 控制台报错:
  `Uncaught TypeError: Cannot destructure property 'AbortController' of ... as it is undefined`
  堆栈位于 `app-service.js` (uni-app 编译后的运行时)
- 错误结尾的 `[AI修复]` 是系统提示, 不是代码

### 二、原因
- `1.3/app/package.json` 依赖 `mqtt: ^5.10.1`, 实际安装为 `mqtt@5.16.0`
- mqtt@5.x 内部在 `mqtt/dist/mqtt.js` 第 2667 行附近有这段代码:
  ```js
  var { AbortController, AbortSignal } = typeof self !== "undefined" ? self :
    typeof window !== "undefined" ? window : void 0;
  ```
- 老版本 Android WebView 或 app-plus 容器中 `self` / `window` 上没有 `AbortController`,
  三元表达式最终结果是 `void 0`, 解构 undefined 立刻抛错, 整个 app 启动失败
- 工程内整个项目 grep `AbortController` 0 命中, 说明问题不在用户代码, 是 mqtt 库 + 运行环境缺 API
- `utils/mqtt.js` 顶部有 `import mqtt from 'mqtt'`, 该 import 一旦执行就会触发上面的解构

### 三、解决方案
采用"AbortController polyfill"路线 (用户已确认):
1. 新建 `1.3/app/utils/polyfill.js`, 提供一个最小可用的 `AbortController` / `AbortSignal` 实现,
   并同时挂到 `globalThis` / `window` / `self` 上, 覆盖 mqtt 那段三元判断的所有分支
2. `1.3/app/main.js` 顶部第一行 `import './utils/polyfill.js'`,
   确保在 `import App` (进而 `import 'mqtt'`) 之前 polyfill 已经执行
3. polyfill 自带"已有原生支持则直接跳过"的判断, 不影响 H5 / 新版 WebView

### 四、改动文件
- 新增 `1.3/app/utils/polyfill.js`
- 修改 `1.3/app/main.js` (在 import App 之前增加一行 polyfill import)

### 五、待验证
- 需用户在安卓真机上重新运行自定义基座 / wgt 包, 确认白屏消失
- 重点验证: app 启动 → 进入设备连接页 → 点击连接 → MQTT 实际连通 ESP32

### 六、注意事项
- polyfill 只覆盖 mqtt 实际用到的 `signal.aborted` / `addEventListener('abort')` / `abort()`,
  不是完整的 Web 标准实现. 如果后续引入其他依赖也用到 `AbortSignal` 高级特性 (timeout / reason / throwIfAborted),
  需要再扩展 SimpleAbortSignal 类
- `mqtt@5.x` 还有其他浏览器端坑 (比如 `process` polyfill、`stream` 依赖), 本次只在 AbortController 这条链路上止血,
  之后真机联调如果出现新报错再继续 polyfill

## 修复：vite.config.js 注入式 polyfill (方案升级)

### 一、问题复发

- 这样无论模块体何时被求值, AbortController / AbortSignal 都已挂到 globalThis / window / self 上
- 恢复 `main.js`, 不再依赖 import 顺序

### 三、改动文件

- `1.3/app/main.js` 恢复成只 import App 和 createSSRApp

2. 运行到 Android 真机 / 模拟器

### 五、关键设计

#### 1. token 计算 (App + ESP32 必须 1:1 一致)
- res  = `products/{pid}/devices/{dev}`
- et   = (now + 86400) 的 Unix 秒
- sign = base64( hmac_sha1( base64decode(accessKey), "{et}\nsha1\n{res}\n2018-10-31" ) )
- token = `version=2018-10-31&res=products%2F{pid}%2Fdevices%2F{dev}&et=...&method=sha1&sign=...`
- App 端: `common/onenet.js` 纯 JS 实现, 不依赖 node Buffer (uni-app 全端可用)
- ESP32 端: `onenet_client.c` 用 mbedtls (md + base64)

#### 2. 命令下发: 双轨
- 持续移动 (vx/vy/w):  走 `SetDeviceDesiredProperty` 写期望值, 设备订阅
  `$sys/.../thing/property/desired/get/reply` 拉最新值
- 单次动作 (急停/起立/配平): 走 `invokeService('stop' / 'stand' / 'calibrate')`,
  设备订阅 `$sys/.../thing/service/{name}/invoke`
- 参数读写: 走 `invokeService('param_get' / 'param_set' / 'param_save')`

#### 3. 数据上报 (ESP32 → OneNet)
- 周期 100ms publish 到 `$sys/.../thing/property/post`
- 字段: pitch / roll / motor_l / motor_r / speed
- 状态机变化时 publish 到 `$sys/.../thing/event/post` (fallen / armed / error)

#### 4. App 状态显示 (已知问题)
**OneNet Studio 公开 HTTP API 不直接提供"读设备最新属性"接口**.
App 想看实时姿态/电机/电池, 当前可行的两种方案:
  方案 A: App 也作为 MQTT 客户端连 OneNet, 订阅设备的上行 topic
  方案 B: App 用 OneNet 物模型 "属性获取" API (`/device/thing/property/get`),
          但这是反向的 (云下发给设备), 需要设备响应
  方案 C: 用 OneNet 的"查询设备影子" API (公开但走 Studio 项目, 非标准物模型)

当前 1.3 的 `status.vue` 走方案 B 调 HTTP, 实际可能拿到空 data.
**已告知用户**, 等下一步决定选 A/B/C 中的哪个, 再调整.

## 设备激活说明 (用户问 "设备怎么激活使用")

### 一、OneNet 平台没有"激活按钮"
经查 OneNet 官方文档 (https://open.iot.10086.cn/doc/mqtt/book/device-develop/manual.html),
**OneNet 设备无需手动激活**, 平台把"激活"和"上线"合并为一个动作:
> 设备首次成功完成 MQTT CONNECT 鉴权后, 自动变 "在线", 灰色→绿色

也就是说, **ESP32 上电 + 联网 + MQTT CONNECT 成功 = 激活完成**。

### 二、当前 1.3 的 ESP32 网络问题
1.3 工程的 `hardware/wifi/wifi_ap.c` 只实现了 `WIFI_MODE_AP`:
- ESP32 自己开 `BalanceRobot_XXXX` 热点, 给手机/电脑连上来网页调参
- **没有 STA 模式, 联不了家里 WiFi**
- 不联网 → 无法访问 `mqtts.heclouds.com:1883` → 设备永远 "离线" → 永远不激活

### 三、用户已选方案
用户选择 **STA 模式** (选项 sta_only):
- 第一次启动走 AP 配网 (开 `BalanceRobot_XXXX` 热点, 浏览器填家里 WiFi SSID/密码)
- 配好保存到 NVS, 重启后切到 STA 连家里 WiFi
- 网页调参也走 STA 模式 (访问 192.168.x.x, 需要先查路由器给 ESP32 分配的 IP)

### 四、待用户决策 (下一步)
是否现在就改 wifi 模块:
- **是** → 1.3 内新增 `hardware/wifi/wifi_sta/` 子目录
  (实现 NVS 存 WiFi + AP 配网 + STA 启动 + 状态切换)
  这是一次较大的网络层重构, 建议放到 1.4
- **否** → 保持 AP 模式, 1.3 的 OneNet MQTT 只能等 1.4 网络改造后再激活
