## 下午: 修"稳一会后高频抖动 + Kp 改了没用 + pitch 上电就不对" (0.30 原地修改, 未做版本迭代)

### 用户反馈 (原话)

> 现在稳一会后高频抖动, kp 降到 0 了都没用, 然后 pitch 每次上电重启后就不对了, 没有断电保存

### 定位到的 5 个问题 (按可信度排序)

1. **App 上改 Kp/Ki/Kd 完全不生效** —— 这是"kp 降到 0 都没用"的直接原因
   - `balance_load_params()` (读 param 表 → 配 PID) 只在 `balance_init()` 和
     `balance_reload_params()` 里调, 而 `balance_reload_params()` **全工程没人调用**
     (grep 只有它自己的定义和头文件声明)
   - 也就是说: App 的 `param_set` → `param_from_json()` 只改了 param 表里的内存值,
     **正在跑的 PID 系数还是开机时的老值** → 拖 Kp 滑块毫无反应
   - 雪上加霜: 唯一能配 PID 的 `pid_config()` 里带着 `pid_reset()` (清积分),
     所以也不能简单地改成"每周期调一次" (积分会被清成 0)
   - 修复: 拆出 `pid_set_gains()` (只改系数, 保留积分/微分历史),
     控制任务每个周期调用 `balance_load_params()` → 下一个周期就生效
2. **积分顶死** —— "先站住, 站一会儿后开始抖" 的典型机理
   - 输出饱和时积分还在同向累加, 攒到 `i_max` (现在 i_max = out_max/2/Ki,
     积分项最大 = 输出上限的一半 = 30%), 误差反向时要先花很久"退积分"
   - 修复: 加**条件积分抗饱和** (`pid_windup_blocked()`):
     输出已顶限幅且误差同向 → 本拍冻结积分; 误差反向 → 积分正常退出
3. **控制周期被网络任务抢占** —— 阻尼相位失配
   - 控制任务优先级 6, 与 OneNet 高速上报任务 (20Hz 发 pitch) **同级**;
     WiFi/MQTT 一忙就抢占控制任务 → dt 突然变大 → 阻尼相位对不上 → 高频抖
   - 而且上报任务是**联网之后**才开始跑的 → 正好对应"稳一会后"才出现
   - 修复: 控制任务优先级 6 → **7**, 上报任务 6/5/4 → **5/4/3**
4. **每次上电 pitch 都不一样** —— 陀螺零偏每次上电重新标定
   - `mpu9250_init()` 里每次开机都跑 `mpu9250_calibrate_gyro(100)`:
     标定那 1 秒里只要车被手抖一下 / 没放稳, 采到的就是**运动**而不是零偏
   - 零偏直接进两个地方: ① 陀螺积分 → 姿态角 (被 1/(1-alpha)≈49 倍放大一部分)
     ② 平衡环 D 项 → 一个**恒定**的力矩 (零偏 1°/s × Kd 1.5 = 1.5% 常数输出)
   - 修复: 零偏存进 NVS (`imu`/`gof`, int16 ×0.001 °/s), 上电直接沿用;
     没有才现场标定, 标完自动存盘; 标定加**运动抑制**
     (任一轴 > 2°/s 的样本直接剔除, 有效样本不足一半就判失败, 不写盘)
   - 顺带修掉一个隐藏 bug: 原来的标定用 `mpu9250_read_gyro()` (已经扣过旧零偏),
     **二次标定算出来的是残差**, 越校越歪 → 改成读原始寄存器
5. **互补滤波首帧从 0 开始收敛** —— 上电后有 0.5 秒 pitch 读数是错的
   - `current_angle` 初值 0, 要靠 accel 以 ~0.5s 的时间常数拉过去;
     如果这时候刚好起立, 控制器会拿着错姿态角输出
   - 修复: 首帧直接用加速度算出的角度当初值 (`s_filt_primed`)

### 配平零点 (pitch 零点) 的断电保存

- 手动配平 (App 控制页的「配平」按钮 → 服务 `calibrate`) 本来就存 NVS
  (`bal`/`pz`), **断电是保存的**; 屏上/网页上**没有**配平面板 (README 里
  "网页「配平标定」面板" 是老版本留下的说法, 已改掉)
- 新增: **起立时自动微调零点** —— 若当前 pitch 与上次标定相差 ≤1°,
  就重新采 0.5 秒零点并落盘 (顺带修掉加速度计零偏随温度的漂移);
  超过 1° 则**不动**零点, 串口日志提示按 App 的「配平」
  - 容差故意取 1°: 零点定的是平衡点, 差 1° 以上车就会带着倾角站、慢慢往一边跑,
    所以自动流程只允许"微调传感器漂移", 重新定义平衡点必须手动

## 傍晚: 修"点了恢复默认后, 车只朝一个方向转, 根本稳不住" (0.30 原地修改, 未做版本迭代)

### 用户反馈 (原话)

> 前面都在抖动着稳三四秒, 但是我点了恢复默认后怎么好久只向一个方向转, 根本稳不住了。

### 根因: App 的"恢复默认"下发的是**过期的默认值表**

排查过程:

1. 先怀疑是控制算法 (毕竟"抖"和"只朝一个方向"都像 PID 问题),
   读了 `balance.c` / `pid.c`, 确认速度环的用法本身没问题
2. 关键线索: 用户是**点了"恢复默认"之后**才出问题的 → 说明问题出在
   "恢复默认"这个动作上, 而不是控制算法
3. 对比 App 的默认值表和车端的默认值表, 发现**两边早就脱节了**:

| 参数 | App 旧默认 (v7 那套) | 车端默认 (v9/v10) |
|---|---|---|
| `bal_kp` | 40 | 12 |
| `bal_ki` | 12 | 0.5 |
| `bal_kd` | 2.0 | 1.5 |
| `spd_kp` | **20** | **0** |
| `spd_ki` | **30** | **0** |
| `spd_kd` | 0.0 | 0.0 |
| `motor_max` | 30 | 60 |
| `deadzone` | 8 | 4 |

4. 复盘 App 的代码路径, 确认了触发链:
   - 旧 `onReset()`: `this.dirtyValues = getDefaultValues(); this.dirty = true`
     → **只改 App 本地的副本**, 还得再点一次"保存"才下发
   - 用户点"恢复默认" → 再点"保存" → `setParams(dirtyValues)`
     → 把 App 那份 v7 旧默认值**整份下发**到车端 → `param_save()` 落盘
   - **坏值进了 NVS, 断电重启也不会自己恢复**
5. 算了一下"速度环被打开"到底有多致命 (这是"只朝一个方向转"的关键):

   - 轮速用 **100ms 窗口**统计 (`balance.c` 的 `SPD_WIN_MS`), 编码器 44 脉冲/转
     → **1 个脉冲 = 13.6 rpm** 的量化台阶
     (⚠ 这是按 gear=1 算的; 0.31 实测减速比 30:1 → 真实台阶是 0.45 rpm。
      本节分析的是 0.30 当时的状态, 数字保留作历史记录)
   - `spd_kp=20` → 一个脉冲的误差就产生 `20 × 13.6 = 273°` 的目标倾角需求
     (限幅 `spdout_max` 只有 40°) → **几乎每个控制周期都顶在限幅上**
     → 平衡环跟着饱和 → 电机前后猛顶
   - `spd_ki=30` → 积分上限 `i_max = (40×0.5)/30 = 0.667`, 积分项最大 **20°**,
     **方向由误差符号决定, 会锁死在一个方向**
     → 这正是"只朝一个方向转、根本稳不住"的形态
   - 另外 `bal_ki=12` (默认已改成 0.5) → 积分很快顶死, 先猛冲再回不来;
     `motor_max=30` (默认已改成 60) → 出力不够接住车身;
     `deadzone=8` (默认已改成 4) → 一顿一顿

### 修复: 把"默认值"这个概念收回到车端唯一一份

光把 App 的表改对只能解决这一次, 下次两边再脱节还会重演。所以做了三层:

| 层 | 改动 | 文件 |
|---|---|---|
| App | 默认值表同步到车端现状, 并加 `PARAM_VER` 常量 + 详细说明 | `app/common/paramDef.js` |
| App | "恢复默认"改成下发 `{"_reset":true}`, **由车端用自己 `param.c` 的默认值整表重置** | `app/utils/control.js` (`resetParams()`) / `app/pages/params/params.vue` (`onReset()`) |
| 车端 | `param_from_json()` 认 `_reset` 特殊键 (`true` / `1`); `param_get` 的 JSON 带上 `_v` 版本号 | `user/param/param.c` |
| 车端 | App 写参数时带 `_v`, 车端比对不一致就在串口打告警 | `user/onenet_client/onenet_client.c` (`param_set` 分支) |
| 车端 | `PARAM_DATA_VERSION` 9 → **10**: 让 NVS 里那批坏值彻底作废, 烧录后自动回到正确默认值 | `user/param/param.c` |
| App | 参数页顶部显示版本号; 车端版本与 App 不一致时显示提示条 | `app/pages/params/params.vue` |

> 关键设计: **App 不再持有"权威默认值"**, 它只有一份用于显示/初始化的镜像。
> 真正的默认值只有 `user/param/param.c` 一份, 恢复默认 = 让车端自己恢复。
> 这样两边默认值再怎么脱节, 也不可能把车的参数改坏。

## 深夜 (三): 修"稳两三分钟, 然后角度一大 / 一碰 / 一让走就剧烈抖动"

### 用户反馈 (原话)

> 现在基本能稳个两三分钟，然后角度一大，或者一碰，或者一让走就会剧烈抖动

形态很明确: **静止站立没事, 一有扰动就剧烈抖**。这不是"参数调得不好"那种抖,
是"回路几乎没有相位裕度"那种抖 —— 静止时误差≈0, 环路没被激励;
一旦有扰动, 反馈通道的滞后就把它放大成大幅振荡。

### 定位: 反馈通道上叠了两处滞后

平衡环是穿越频率 2~4Hz 的高增益回路, 反馈通道上每加一点滞后就是直接相位损失:

| 位置 | 旧值 | 折算滞后 | 后果 |
|---|---|---|---|
| 互补滤波 `alpha` (`mpu9250.c`) | 0.98 | 加速度纠偏时间常数 τ = dt/(1−α) = **0.5s** | P 反馈用的是**半秒前**的姿态角 |
| `gyro_lpf` (陀螺低通, `param.c`) | 0.2 | τ = dt/0.2 = **50ms** (截止 3.2Hz) | D 项 (唯一的阻尼源) 被延迟 50ms |

2~4Hz 穿越时, 0.5s 滞后 = 0.8 个周期 ≈ **290° 相位损失**;
D 项再叠 50ms, 在 3Hz 处再丢 **54°** → 阻尼被相位滞后吃光 → 扰动一来就发散。

顺带发现两个"看起来像主因、其实是配角"的问题:
- **加速度计测的是比力**: 车一加速, 加速度计读数里就多出车体加速度,
  `atan2(az,−ay)` 算出来的俯仰角会偏**几十度** (6m/s² → 31°),
  互补滤波再把姿态角往这个错值上拽 → 正反馈。
  (车静止时没有平动加速度 → 读数准 → 所以"站着没事、一动就出事")
- **死区补偿方式根本不起作用**: 旧的"抬到" (duty = max(|duty|, dz)) 在
  硬件死区 D > dz 时**一点死区都没补偿掉** (电机要转还是得自己超过 D);
  改成"加上" (duty = |duty| + dz) 后有效死区才是 max(0, D−dz)。

### 手段: 把离线仿真补成"跟固件一一对应"

原来的 `test/bal_sim.py` 只是个理想倒立摆 (无死区、无电机滞后、无抗饱和、
控制器直接拿真实角度), 所以它给出的结论跟真机对不上。这次把它补全:

- 固件 PID (含条件积分抗饱和) + 输出 int8 截断
- 电机链路: 死区补偿 (抬到/加上) → 硬件死区 → 一阶滞后 τ
- IMU 链路: 加速度计比力污染 (车体平动加速度) + 互补滤波 (α 可调)
- 植物参数不确定 (摆长 L / 电机增益 k / τ / 硬件死区) → **81 组组合**一起扫

> ⚠ 中间踩了一个大坑: 我一开始把加速度计污染的**符号写反了**
> (写成 ay = sinθ + a/g)。写成负反馈时, 仿真里"污染"反而在帮忙纠偏,
> 看起来一切正常。物理上正确的写法是 ay = sinθ − a/g:
> 车往倒的方向加速 → 加速度计的水平分量被抵消 → 算出的角度**偏小**
> → 控制器以为还没倒那么厉害 → 少出力 → 越晃越大 (正反馈)。
> 符号改对之后, 固件现状的仿真结果是"**摔了**", 才跟真机对得上。

### 仿真模型的坑 (写的时候绕了不少弯)

第一版行走模型把车当成"小车 + 摆"重新写了一套方程 (质量/惯量/推力增益),
结果跑出来"速度环必然跑飞"。查下来是**模型自相矛盾**:
定轴模型里 `a_w` 隐含的是 `ẍ/L` (L = 质心高), 而新模型把 `a_w` 当成了
真的轮角加速度, 质量和推力增益都是猜的 → 平衡环在那套参数下压根站不住,
后面的"速度环不稳定"结论全是假的。

**重写成: 行走模型 = 定轴模型 + 把丢掉的平动速度补回来**
(θ̈ = (g/L)sinθ − a_w 完全一样, ẍ = L·a_w, 轮速 = −ẋ/(2πr))。
这样"平衡环能站住"在两个模型里是同一套数学, 仿真结论才敢用。

## 深夜 (五): 修"起立就立马剧烈抖动" —— 根因是**陀螺零偏没被补偿**, 姿态角差 3°

### 用户反馈 (原话)

> 前面还能平衡的时候稳一会，现在起立就立马剧烈抖动。

### 现场取证

设备 `/dev/cu.usbmodem21133401` 在线, 抓了开机日志 + 用 OneNet 开放接口读遥测
(`/thingmodel/query-device-property`)。串口被 esptool 的失败尝试搞进了下载模式,
用 `esptool.py --after hard_reset chip_id` 救回来的 (见"踩到的坑")。

**开机日志 (关键三行)**:

```
I (2916) MPU9250: 开始校准陀螺仪,请保持设备静止...
E (3919) MPU9250: 陀螺仪校准失败: 采样期间检测到运动 (99/100 个样本被剔除), 请把设备放稳再校准
W (3919) MPU9250: 陀螺仪校准未成功 (设备可能在动), 零偏暂用 0
```

→ **陀螺零偏标定失败 → 零偏 = 0 → 姿态角带一个恒定误差**

**遥测 (车静止不动时连采 8 次, 值纹丝不动)**:

| 时刻 | gz (俯仰角速度) | pitch |
|---|---|---|
| 14:56 (修复前) | **0.90** °/s | −1.1° |
| 15:10 (修复后) | **−0.25** °/s | **−4.1°** |

→ 静止时角速度恒为 0.90 °/s = **陀螺零偏**; 补上零偏后 pitch 整体挪了 **−3.0°**

### 根因: 两个 bug 叠在一起

**Bug 1 —— 零偏标定的"运动检测"比错了量 (致命)**

`mpu9250_calibrate_gyro()` 旧代码: 任一轴 `|原始读数| > 2°/s` 就丢掉这个样本。

但**绝对值大 = 零偏大**, 而零偏正是要测的量! 本机 MPU6500 的 Y 轴零偏就有
**4.73 °/s** → 每个样本的 Y 都被判成"在动" → 100 个样本被剔除 99 个 →
**标定永远失败** → 零偏永远是 0。

**Bug 2 —— alpha 0.98→0.997 把残余零偏放大了 6.8 倍 (回归的引入点)**

互补滤波的稳态角误差 = 残余零偏 × dt/(1−alpha):

| alpha | 放大系数 dt/(1−alpha) | 残余零偏 0.9 °/s → 姿态角误差 |
|---|---|---|
| 0.98 (旧) | 0.5 | **0.45°** (能忍) |
| 0.997 (现在) | 3.33 | **3.0°** (致命) |

3° 的假倾角 → 平衡环以为车歪了 3° → 轮子猛冲 → **"起立就立马剧烈抖动"**。
时间线也对得上: alpha 是 2026-10-26 深夜(三) 改的, 之前"还能稳一会"。

**两个 bug 的因果链**:
标定失败(零偏=0) → 姿态角恒差 3° → alpha 调高后这个误差被放大 → 起立即猛冲。

### 修复

| 文件 | 改动 |
|---|---|
| `hardware/mpu9250/mpu9250.c` | 标定的运动判定改成**标准差 σ** (不是绝对值, 也不是极差); 阈值 2.0→2.5 °/s |
| `hardware/mpu9250/mpu9250.c` | 每次上电都重新标定 (成功就存 NVS), 失败才退回 NVS 里那份; 失败重试一次 + 大声报错 |
| `hardware/mpu9250/mpu9250.c` | 标定日志打印 均值/标准差/极差, 便于以后判断零偏合不合理 |

**为什么用标准差**: 极差 (max−min) 对单个离群样本太敏感 —— 本机静止时极差能到
3.5 °/s (复位瞬间的震动), 而 σ 只有 0.13~0.17 °/s。σ 对离群点稳健得多。
实测静止 σ ≈ 0.15 °/s, 阈值 2.5 °/s 有 16 倍余量; 真动手 (几十 °/s) 一抓一个准。

**为什么改成"每次上电都标定"**: 零偏会随温度漂 —— 本机实测冷机 0.92 °/s,
热机 0.67 °/s, 差 0.25 °/s = **0.83° 的姿态角误差**。存一份 NVS 零偏用一整天,
温度一变它就不准了。每次上电重标 = 零偏跟当前温度对得上。

### 踩到的坑 (记下来, 免得下次再踩)

1. **esptool 参数位置**: `--flash_mode` / `--flash_freq` / `--flash_size`
   是 **`write_flash` 子命令的选项**, 必须写在 `write_flash` **后面**;
   写在 `write_flash` 前面会被当成"操作名"直接报
   `argument operation: invalid choice: 'dio'`。
2. **二进制文件名别照抄 flash_args**: 构建目录里的 `app-flash_args` 写的是
   `balanced_dog.bin` / `bootloader/bootloader.bin` / `partition_table/partition-table.bin`,
   但实际产物在构建目录**根下**叫 `firmware.bin` / `bootloader.bin` / `partitions.bin`
   (ESP-IDF 的 `firmware.bin` 就是 app 镜像, `esptool image_info --chip esp32s3`
   能正常解析出 5 个 segment + 校验和)。
   直接照抄路径会报 `No such file or directory`。
3. **`esptool image_info` 不加 `--chip esp32s3` 会误判成 ESP8266** 然后报
   `Suspicious segment 0xee` —— 那不是固件坏了, 是芯片类型判断错了。
4. **flash_mode 必须跟 sdkconfig 一致**: `sdkconfig.esp32-s3-devkitc-1` 里
   `CONFIG_ESPTOOLPY_FLASHMODE_DIO=y`, 所以刷的时候用 `--flash_mode dio`,
   千万别用 platformio.ini 里那句 `board_build.flash_mode = qio`
   (那行对 ESP-IDF 框架不生效, 照它刷会跟 bootloader 期望的模式对不上)。

### 背景

### 关键设计决策

**1. "最稳窗口"标定 (任务 3)**

采样 200 个 (每 10ms 一个) 存进静态数组 `s_cal_samples[256][3]`, 然后用
**25 个样本 (≈0.25s) 的滑动窗口**在整段上滑, 每个窗口算三轴的均值和 σ,
取**三轴 σ 最大值最小**的那个窗口; 成功则用该窗口的**中位数**当零偏
(比均值抗离群点), 失败**不写 NVS** (保留旧零偏)。

为什么这样能解决手持标定: 手持晃动只会让"最佳窗口"更难找, 不再直接判失败;
只要能拿稳 0.25 秒就能标成功。日志打 (a) 整段均值/σ/极差 (b) 最佳窗口起点、
均值、σ (c) 采用的零偏 (d) 残余零偏对姿态角的放大。

**离线验证**: 用合成数据复刻了窗口算法 —— 前 150 个样本剧烈晃动 (σ=8) +
后 50 个静止 (σ=0.2), 算法准确挑出 `best_start=150`, σ=0.107, 中位数零偏
(0.874, 4.740, 0.591) ≈ 真值 (0.9, 4.7, 0.6); 全程晃动的场景正确判失败。

**2. 零偏慢漂跟随 (任务 4)**

`mpu9250_read_data()` 里维护 **100 个样本的滚动窗口** (环形缓冲 + 累加和,
不用存全部样本), 统计**扣过零偏后**三轴绝对值之和的平均值;
平均 < 0.5 °/s (判静止) 且距上次调整 > 30 秒 → `bias_k += 0.05*(raw_k - bias_k)`。

**只在 `s_state != BAL_STATE_BALANCING` 时打开** (balance.c 控制任务每周期调
`mpu9250_set_bias_tracking()`): 车站着顶的时候读数里全是真实角速度,
拿它当零偏会把真实运动也吸进零偏里 → D 项阻尼失准 → 越晃越歪。

**3. AK8963 磁力计 (任务 5)**

bypass 流程: `INT_PIN_CFG |= 0x42` + `USER_CTRL = 0` → 等 10ms → 读 0x0C 的
WIA (期望 0x48) → 没找到就只打告警 (**不报错退出, 不影响 IMU 其余功能**)
→ 找到就 CNTL1=0x00 (power down) → 0x0F (ROM) 读 ASA 厂标 → 0x12 (16bit 连续)
→ 再读 WIA 确认。量纲 `uT = raw × adj × 0.15`, 厂标 `adj = 1 + (asa-128)/256`。
读数**不参与任何姿态解算**, 只在 `read_data()` 里顺带读 + 每秒打一条日志。

### 踩到的坑 / 注意事项

1. **ESP_LOGI 不能在 I2C 锁里调** —— 一条 100 多字节的日志走 UART 要写 10ms,
   在锁里打印会把控制任务 (10ms 周期) 卡住 → 轮子输出抖。
   解法: 锁里只 `snprintf` 填缓冲, 解锁后再 `ESP_LOGI`。
2. **`mpu9250_read_data()` 的锁范围扩大了** —— 原来只锁 I2C 读那一段,
   现在整个函数在锁里 (因为慢漂跟随会改 `gyro_offset` 和一组统计计数器,
   而本函数被控制任务 10ms 和 UI 任务 50ms 同时调用)。锁的范围只有几十微秒。
3. **标定与慢漂跟随互斥** —— 标定最后要写 `gyro_offset`, 慢漂跟随也会改它。
   用 `s_calibrating` 标志互斥 (标志读写都在 I2C 锁里), 标定期间跟随让路。
4. **厂标系数不能用 `(int8_t)` 强转** —— `asa` 是无符号 8 位寄存器值,
   按 AK8963 手册公式 `H_adj = H × ((ASAx − 128) × 2⁻⁸ + 1)` 换算。
   用 int8_t 强转会让 asa > 127 变成负数, 系数算成 0.2x 这种离谱值。
   (参考工程 3.4 用的是无符号写法, 这里跟它一致。)
5. **`mpu9250_reset()` 必须清 `s_mag_available`** —— 复位后 MPU 寄存器回默认,
   bypass 没了, 磁力计访问不到, 留着 true 会一直去读一个访问不到的器件。
6. **`%02X` 必须配 `(unsigned)` 强转** —— 否则 `-Werror=format=` 直接编译失败。

### 收尾 1: 速度环增益的 step 改 0.01 (App 上调不动, 静默失效)

#### 现象

`user/param/param.c` 的 `g_param_items[]` 里, 三个速度环增益的 step 是:

| 参数 | 改动前 step | decimals | 改动后 step | decimals |
|---|---|---|---|---|
| `spd_kp` | 0.5 | 2 | **0.01** | 2 (不变) |
| `spd_ki` | 0.5 | 2 | **0.01** | 2 (不变) |
| `spd_kd` | 0.1 | 2 | **0.01** | 2 (不变) |

而 `param_set_float()` 的吸附逻辑是:

```c
static float snap_to_step(float val, float min, float step)
{
    if (step <= 0.0f) return val;
    return min + roundf((val - min) / step) * step;
}
```

于是:

| App 上想设的值 | 吸附后车端实际存的值 | 结果 |
|---|---|---|
| `spd_kp` = 0.06 | `min(0) + round(0.06/0.5)*0.5` = **0.0** | 被吸成 0 |
| `spd_kp` = 0.3 | `0 + round(0.3/0.5)*0.5` = **0.5** | 跳到 0.5 |
| `spd_ki` = 0.02 | `0 + round(0.02/0.5)*0.5` = **0.0** | 被吸成 0 |

也就是说 **App 上拖速度环增益, 车端要么给 0 要么给 0.5, 中间的值一个都设不进去**。

设成 0 还不算彻底坏: `balance.c` 里有兜底常量
`BAL_SPD_KP_DEFAULT=0.06` / `BAL_SPD_KI_DEFAULT=0.01`
(`balance_load_params()` 里 `spd_kp > 0.001f ? spd_kp : BAL_SPD_KP_DEFAULT`),
所以看起来"还能用" —— **但用户根本调不动**。这正是它难被发现的原因:
不报错、不崩溃、有兜底, 只是你拖滑块时车端在偷偷改你的数。

#### 改了什么

- 车端 `user/param/param.c`: `spd_kp` / `spd_ki` / `spd_kd` 的 step 统一改成
  **0.01f** (decimals 保持 2, 值域不变), 提示文字里补一句
  "步进 0.01, 步进太粗的话 App 拖出来的中间值会被吸附掉"。
- App `app/common/paramDef.js`: 三项的 step 同步改成 0.01 (dec 保持 2)。
- **`PARAM_DATA_VERSION` / `PARAM_VER` 都没有动 (仍然是 14)** ——
  step 只影响"怎么吸附", **blob 布局和默认值都没变**, 所以不需要作废 NVS。
  (但 App 和车端必须**同时**改 step, 只改一边就会出现"App 拖 0.06、车端按 0.5 吸附"。)
- `test/test_param_pc.c`: 新增用例 7, 断言三个 step 都是 0.01, 且
  `param_set_float(PARAM_PID_SPD_KP, 0.06)` 之后 `param_get_float()` 仍然是 0.06
  (走 `param_from_json()` 的 JSON 下发路径也断言一遍 —— App 实际走的是这条路)。

### 收尾 2: 速度死区 5.0 → 1.0 rpm, 量化台阶的注释全部重算

#### 现象

死区是按"编码器量化台阶"定的, 换算公式是:

```
rpm = 脉冲数 × 60 / (窗口秒数 × 44 × gear)
```

(44 = 编码器每转脉冲数, 装在**电机轴**上; gear = 减速比)

| 窗口 | gear=1 (旧) | **gear=30 (现在)** |
|---|---|---|
| 10 ms | 136 rpm | **4.55 rpm** |
| 100 ms | 13.6 rpm | **0.45 rpm** |
| 300 ms (固件实际用的) | 4.5 rpm | **0.15 rpm** |

`BAL_SPD_ERR_DEADBAND` 当时是 `5.0f` —— 那是按"300ms 窗口量化台阶 4.5 rpm"定的
(死区必须 ≥ 量化台阶, 免得车为了追量化噪声一直歪着)。换算比改成 30 之后,
真实量化台阶只剩 **0.15 rpm**, 5 rpm 的死区相当于把 **5% 的目标速度误差直接丢掉**
(目标 100 rpm 时死区 5 rpm) —— 太粗了。

#### 改了什么

- `user/control/balance.h`: `BAL_SPD_ERR_DEADBAND` **5.0f → 1.0f**
  (≈ 6.6 个量化台阶: 既能滤掉量化噪声, 又不会吃掉真实的速度误差),
  注释重写 (含换算公式和"改 gear 就要重算"的提醒)。
- `user/control/balance.c`: 三处写死数字的注释全部按 gear=30 重算 ——
  文件头的"轮速统计"段、`balance_update_speed()` 里"不用 encoder_get_rpm(...,10ms)"
  那段、以及速度环里"误差死区"那句; 换算公式那行也补了
  "轮子转一圈 = 44×30 = 1320 个脉冲"和"改 gear 必须重算"。
- `user/control/balance.c`: `balance_update_target()` 的注释里
  "目标不会瞬间跳到 48 rpm" → **80 rpm** (100% 档 = `move_rpm_max` 默认 100)。
- `user/control/balance.h`: `BAL_MOVE_RPM_MAX` 的注释与新量化数字无矛盾
  (100 rpm ≈ 最高转速 333 rpm 的 30%), 没改。
- **300ms 累加窗口保持不变** —— 减速比改 30 之后连 100ms 窗口的台阶都只有
  0.45 rpm 了, 300ms 窗口额外起低通作用, 测速延迟也更小。

### 踩到的坑 (这一轮)

1. **减速比 30 之后量化台阶从 4.5 rpm 变成 0.15 rpm, 速度死区 5 rpm 过粗** ——
   死区是按"量化台阶"定的, 换算比一变就必须重算, 否则要么量化噪声直接进目标倾角,
   要么把真实的速度误差一起吃掉 (这次是后者)。
   **教训**: 凡是以"某个物理量"为基准定出来的常数 (死区、限幅、斜坡率),
   都要在注释里写清楚**它依赖哪个参数**, 参数一改就得重算。
2. **速度环增益 step 0.5 导致 App 拖出来的中间值被吸附掉** ——
   `snap_to_step()` 是**静默**的: 值被改了, 不报错; 车端还有兜底常量, 看起来"还能用"。
   这类问题只能靠"车端和 App 两边 step 都改细 + 离线测试断言
   `param_set_float(0.06)` 之后还是 0.06"来防住。
3. **`snap_to_step()` 的吸附基准是 `min`, 不是 0** ——
   公式是 `min + round((val-min)/step)*step`。这三个参数 min 都是 0,
   所以看不出来; 但如果以后给某个参数设了非 0 的 min, 用"0 基准"去算期望值
   就会算错。
4. **仿真里的数字也是"会过期的"** —— `bal_sim.py` 里写死的 `enc_res=4.545`
   和 `spd_deadband=5.0` 是照着 gear=1 的固件抄的, 固件改了仿真不改,
   仿真结论就跟固件对不上, 反而会误导调参。这次改成**按 gear 算**而不是写死。
