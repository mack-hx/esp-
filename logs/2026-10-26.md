## 下午: 修"稳一会后高频抖动 + Kp 改了没用 + pitch 上电就不对" (0.30 原地修改, 未做版本迭代)

### 用户反馈 (原话)

> 现在稳一会后高频抖动, kp 降到 0 了都没用, 然后 pitch 每次上电重启后就不对了, 没有断电保存

### 定位到的 5 个问题 (按可信度排序)

1. **App 上改 Kp/Ki/Kd 完全不生效** —— 这是"kp 降到 0 都没用"的直接原因
   - `balance_load_params()` (读 param 表 → 配 PID) 只在 `balance_init()` 和
     `balance_reload_params()` 里调, 而 `balance_reload_params()` **全工程没人调用**
     (grep 只有它自己的定义和头文件声明)
   - 也就是说: App 的 `param_set` → `param_from_json()` 只改了 param 表里的内存值,
     **正在跑的 PID 系数还是开机时的老值** → 拖 Kp 滑块毫无反应
   - 雪上加霜: 唯一能配 PID 的 `pid_config()` 里带着 `pid_reset()` (清积分),
     所以也不能简单地改成"每周期调一次" (积分会被清成 0)
   - 修复: 拆出 `pid_set_gains()` (只改系数, 保留积分/微分历史),
     控制任务每个周期调用 `balance_load_params()` → 下一个周期就生效
2. **积分顶死** —— "先站住, 站一会儿后开始抖" 的典型机理
   - 输出饱和时积分还在同向累加, 攒到 `i_max` (现在 i_max = out_max/2/Ki,
     积分项最大 = 输出上限的一半 = 30%), 误差反向时要先花很久"退积分"
   - 修复: 加**条件积分抗饱和** (`pid_windup_blocked()`):
     输出已顶限幅且误差同向 → 本拍冻结积分; 误差反向 → 积分正常退出
3. **控制周期被网络任务抢占** —— 阻尼相位失配
   - 控制任务优先级 6, 与 OneNet 高速上报任务 (20Hz 发 pitch) **同级**;
     WiFi/MQTT 一忙就抢占控制任务 → dt 突然变大 → 阻尼相位对不上 → 高频抖
   - 而且上报任务是**联网之后**才开始跑的 → 正好对应"稳一会后"才出现
   - 修复: 控制任务优先级 6 → **7**, 上报任务 6/5/4 → **5/4/3**
4. **每次上电 pitch 都不一样** —— 陀螺零偏每次上电重新标定
   - `mpu9250_init()` 里每次开机都跑 `mpu9250_calibrate_gyro(100)`:
     标定那 1 秒里只要车被手抖一下 / 没放稳, 采到的就是**运动**而不是零偏
   - 零偏直接进两个地方: ① 陀螺积分 → 姿态角 (被 1/(1-alpha)≈49 倍放大一部分)
     ② 平衡环 D 项 → 一个**恒定**的力矩 (零偏 1°/s × Kd 1.5 = 1.5% 常数输出)
   - 修复: 零偏存进 NVS (`imu`/`gof`, int16 ×0.001 °/s), 上电直接沿用;
     没有才现场标定, 标完自动存盘; 标定加**运动抑制**
     (任一轴 > 2°/s 的样本直接剔除, 有效样本不足一半就判失败, 不写盘)
   - 顺带修掉一个隐藏 bug: 原来的标定用 `mpu9250_read_gyro()` (已经扣过旧零偏),
     **二次标定算出来的是残差**, 越校越歪 → 改成读原始寄存器
5. **互补滤波首帧从 0 开始收敛** —— 上电后有 0.5 秒 pitch 读数是错的
   - `current_angle` 初值 0, 要靠 accel 以 ~0.5s 的时间常数拉过去;
     如果这时候刚好起立, 控制器会拿着错姿态角输出
   - 修复: 首帧直接用加速度算出的角度当初值 (`s_filt_primed`)

### 配平零点 (pitch 零点) 的断电保存

- 手动配平 (App 控制页的「配平」按钮 → 服务 `calibrate`) 本来就存 NVS
  (`bal`/`pz`), **断电是保存的**; 屏上/网页上**没有**配平面板 (README 里
  "网页「配平标定」面板" 是老版本留下的说法, 已改掉)
- 新增: **起立时自动微调零点** —— 若当前 pitch 与上次标定相差 ≤1°,
  就重新采 0.5 秒零点并落盘 (顺带修掉加速度计零偏随温度的漂移);
  超过 1° 则**不动**零点, 串口日志提示按 App 的「配平」
  - 容差故意取 1°: 零点定的是平衡点, 差 1° 以上车就会带着倾角站、慢慢往一边跑,
    所以自动流程只允许"微调传感器漂移", 重新定义平衡点必须手动

## 傍晚: 修"点了恢复默认后, 车只朝一个方向转, 根本稳不住" (0.30 原地修改, 未做版本迭代)

### 用户反馈 (原话)

> 前面都在抖动着稳三四秒, 但是我点了恢复默认后怎么好久只向一个方向转, 根本稳不住了。

### 根因: App 的"恢复默认"下发的是**过期的默认值表**

排查过程:

1. 先怀疑是控制算法 (毕竟"抖"和"只朝一个方向"都像 PID 问题),
   读了 `balance.c` / `pid.c`, 确认速度环的用法本身没问题
2. 关键线索: 用户是**点了"恢复默认"之后**才出问题的 → 说明问题出在
   "恢复默认"这个动作上, 而不是控制算法
3. 对比 App 的默认值表和车端的默认值表, 发现**两边早就脱节了**:

| 参数 | App 旧默认 (v7 那套) | 车端默认 (v9/v10) |
|---|---|---|
| `bal_kp` | 40 | 12 |
| `bal_ki` | 12 | 0.5 |
| `bal_kd` | 2.0 | 1.5 |
| `spd_kp` | **20** | **0** |
| `spd_ki` | **30** | **0** |
| `spd_kd` | 0.0 | 0.0 |
| `motor_max` | 30 | 60 |
| `deadzone` | 8 | 4 |

4. 复盘 App 的代码路径, 确认了触发链:
   - 旧 `onReset()`: `this.dirtyValues = getDefaultValues(); this.dirty = true`
     → **只改 App 本地的副本**, 还得再点一次"保存"才下发
   - 用户点"恢复默认" → 再点"保存" → `setParams(dirtyValues)`
     → 把 App 那份 v7 旧默认值**整份下发**到车端 → `param_save()` 落盘
   - **坏值进了 NVS, 断电重启也不会自己恢复**
5. 算了一下"速度环被打开"到底有多致命 (这是"只朝一个方向转"的关键):

   - 轮速用 **100ms 窗口**统计 (`balance.c` 的 `SPD_WIN_MS`), 编码器 44 脉冲/转
     → **1 个脉冲 = 13.6 rpm** 的量化台阶
   - `spd_kp=20` → 一个脉冲的误差就产生 `20 × 13.6 = 273°` 的目标倾角需求
     (限幅 `spdout_max` 只有 40°) → **几乎每个控制周期都顶在限幅上**
     → 平衡环跟着饱和 → 电机前后猛顶
   - `spd_ki=30` → 积分上限 `i_max = (40×0.5)/30 = 0.667`, 积分项最大 **20°**,
     **方向由误差符号决定, 会锁死在一个方向**
     → 这正是"只朝一个方向转、根本稳不住"的形态
   - 另外 `bal_ki=12` (默认已改成 0.5) → 积分很快顶死, 先猛冲再回不来;
     `motor_max=30` (默认已改成 60) → 出力不够接住车身;
     `deadzone=8` (默认已改成 4) → 一顿一顿

### 修复: 把"默认值"这个概念收回到车端唯一一份

光把 App 的表改对只能解决这一次, 下次两边再脱节还会重演。所以做了三层:

| 层 | 改动 | 文件 |
|---|---|---|
| App | 默认值表同步到车端现状, 并加 `PARAM_VER` 常量 + 详细说明 | `app/common/paramDef.js` |
| App | "恢复默认"改成下发 `{"_reset":true}`, **由车端用自己 `param.c` 的默认值整表重置** | `app/utils/control.js` (`resetParams()`) / `app/pages/params/params.vue` (`onReset()`) |
| 车端 | `param_from_json()` 认 `_reset` 特殊键 (`true` / `1`); `param_get` 的 JSON 带上 `_v` 版本号 | `user/param/param.c` |
| 车端 | App 写参数时带 `_v`, 车端比对不一致就在串口打告警 | `user/onenet_client/onenet_client.c` (`param_set` 分支) |
| 车端 | `PARAM_DATA_VERSION` 9 → **10**: 让 NVS 里那批坏值彻底作废, 烧录后自动回到正确默认值 | `user/param/param.c` |
| App | 参数页顶部显示版本号; 车端版本与 App 不一致时显示提示条 | `app/pages/params/params.vue` |

> 关键设计: **App 不再持有"权威默认值"**, 它只有一份用于显示/初始化的镜像。
> 真正的默认值只有 `user/param/param.c` 一份, 恢复默认 = 让车端自己恢复。
> 这样两边默认值再怎么脱节, 也不可能把车的参数改坏。

### 踩到的坑

1. **`atoi` 不能直接吃 `":10"`** —— 版本对账时先写成 `atoi(vp + 4)`,
   `vp` 指向 `"_v"`, `+4` 正好落在冒号上, `atoi(":10")` 返回 **0**,
   会把"版本一致"误判成"版本 0 不一致"。改成先 `strchr(vp, ':')` 再 `atoi(colon+1)`
2. **`PARAM_ITEM_COUNT` 宏在 `param.c` 外面用不了** ——
   `g_param_items` 在头文件里只是 `extern` 的不完整数组类型, `sizeof` 编译不过。
   加了 `param_count()` 函数对外提供条目数
3. **离线测试要 `strtof` 得自己 include `<stdlib.h>`** —— ESP-IDF 下是别的头文件
   间接带进来的, PC 上直接编 `param.c` 就没有 → 隐式声明报错
4. **macOS 上 gcc 报 "tapi error: malformed file"** —— 是 CommandLineTools 的
   SDK 库文件坏了 (不是代码问题), 换 `-isysroot $(xcrun --show-sdk-path)` 即可。
   (过一会系统更新了 CommandLineTools 又能用了, 说明是环境临时问题)
