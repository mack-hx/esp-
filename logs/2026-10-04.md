### 修改 2: 物理左轮编码器方向反转

**问题**：实物左轮（= GPIO45/46 = 改后 ENCODER_1）正转时计数在减小。
**根因**：原 cfg 是 `pos_mode=INC, neg_mode=DIS, hctrl=REVERSE, lctrl=KEEP`，
电机正转时 ctrl 脚为高，REVERSE 把方向反过来；新编码器 cfg 也用同样的简化配置，
但实物左轮的"a_pos/a_neg"高低电平定义跟原 ENC2 假设相反。
**修复方法**：调用 `pcnt_set_mode()` 同时交换 `pos_mode↔neg_mode` 和 `hctrl↔lctrl`，
等价于把总计数方向反转一次。

`0.2/hardware/encoder/encoder.c`:
```c
/* 物理左轮 (ENCODER_1) 电机正转时计数方向反, 同时交换 pos_mode/neg_mode 和 hctrl/lctrl 反转 */
pcnt_set_mode(PCNT_UNIT_ENC1, PCNT_CHANNEL_0,
              PCNT_COUNT_DEC, PCNT_COUNT_INC,
              PCNT_MODE_REVERSE, PCNT_MODE_KEEP);
```

为什么同时交换两对：
- 只交换 pos_mode/neg_mode: 边沿方向反转，但 hctrl=REVERSE 仍然在 ctrl 高时反转
  (反转 + 反转 = 不反转) → 错误
- 同时交换 hctrl/lctrl: ctrl 高时变 KEEP，ctrl 低时变 REVERSE → 总效果 = 反转一次 ✓

### 修改 3.5: 舵机反向映射同步翻转

**用户反馈 (13:29)**：
> 你交换两个舵机前，一个正向一个反向是没问题的，现在交换后反向的变成正向了，正向的变成反向了。你需要再把两个舵机的方向也要换一遍

**根因**：
- GPIO13 那个舵机实物是**反向**安装的（调 80° 实际转 100°）
- GPIO14 那个舵机实物是**正向**安装的
- 改前编号：SERVO_1 = GPIO13（反向舵机），SERVO_2 = GPIO14（正向舵机）
- 改后编号：SERVO_1 = GPIO14（正向舵机），SERVO_2 = GPIO13（反向舵机）

旧的 `servo_logic_to_phys` 只对 SERVO_2 反向映射 (`180 - 逻辑`)：
- 改前：SERVO_2 是正向舵机 + 180-x → 物理转 180-x（反向）
- 改后：SERVO_2 是反向舵机 + 不映射 → 物理转 180-x（反向，反向舵机自己反）

而 SERVO_1：
- 改前：SERVO_1 是反向舵机 + 不映射 → 物理转 180-x（反向）
- 改后：SERVO_1 是正向舵机 + 不映射 → 物理转逻辑（正向）

**结果**：改后 SERVO_1 由"反向"变成"正向"，SERVO_2 由"反向"变成"反向"。实物表现：
- 改前：两路都转 180-x（视觉对称）
- 改后：S1 转逻辑（80°），S2 转 180-x（100°）→ **视觉不对称**

**修复**：把反向映射从跟着 ID 走改成跟着 GIID 走，但**反过来**（按 GPIO 的实物方向决定反向映射）：

`0.2/hardware/servo/servo.c` `servo_logic_to_phys`:
```c
if (id == SERVO_1) {
    /* SERVO_1 = GPIO14 (正向), 走反向得到 180-逻辑 */
    int phys = (int)SERVO_MAX_ANGLE - (int)logic_angle;
    if (phys < 0) phys = 0;
    if (phys > SERVO_MAX_ANGLE) phys = SERVO_MAX_ANGLE;
    return (uint8_t)phys;
}
/* SERVO_2 = GPIO13 (反向), 不映射, 反向舵机自己反向, 净结果 = 180-逻辑 */
return logic_angle;
```

**5 种模式**（K3 循环）：

|---|---|---|---|

- 若当前模式是 M1/M2/BOTH 且 s_running → 按当前方向符号驱动

```c
static void apply_motor_state(void)
{
    int8_t sign = (s_dir == MOTOR_DIR_REVERSE) ? -1 : 1;
    if (!s_running || s_mode == MODE_DIR || s_mode == MODE_SPEED) {
        motor_brake_all();
        return;
    }
    int8_t sa = 0, sb = 0;
    switch (s_mode) {
        case MODE_M1:   sa = 60 * sign; sb = 0;          break;
        case MODE_M2:   sa = 0;         sb = 60 * sign; break;
        case MODE_BOTH: sa = 60 * sign; sb = 60 * sign; break;
        default: break;
    }
    motor_set_speed_both(sa, sb);
}
```

1. **超出屏宽**：`R%4.0f P%4.0f Y%4.0f` = 17 字符 × 6 像素 = 102 像素，
   但起始 X=36 → 右边界 138 > 屏宽 128，Yaw 被切掉。
2. **`ui_draw_string` 会自动换行**（`lcd_ui.c:72`）：

```c
/* 超出右边距, 自动换行 */
if (cur_x + UI_FONT_W > UI_SCREEN_W) {
    cur_x = x;
    cur_y += UI_FONT_H;
}
```

所以 17 字符的 RPY 实际溢出后会**换到下一行**，
再叠加 `ui_fill_rect(36, 100, 90, ...)` 的清除区域也不匹配（清 90 像素但内容要 102 像素），
最终 RPY 溢出部分 + 温度行互相覆盖，两行都看不全。

**新约定：任何显示字符串都必须 ≤ 21 字符**（128/6 = 21.3），否则一定会换行。

### 数据包解析实现（用户描述的 strtok 方案）

```c
/* '[' 到 ']' 之间取包体 -> strtok 按 ',' 分割 -> strcmp 判类型 -> atof 取值 */
static bool parse_body(char *body, ble_packet_t *out)
{
    char *tag = strtok(body, ",");
    if (strcmp(tag, "plot-clear") == 0 || strcmp(tag, "p-c") == 0) { ... }
    if (strcmp(tag, "plot") == 0 || strcmp(tag, "p") == 0) { ... }   // 1~10 个数值
    if (strcmp(tag, "slider") == 0 || strcmp(tag, "s") == 0) { ... } // 名称 + 值
}
```

**分包处理**：BLE 是流式传输，一个包可能被拆成多次 WRITE 事件。
`drain_rx_buffer()` 做增量扫描：找到 `]` 才算一帧完整，半包留在缓存等下次。

### 踩坑记录（4 个真实报错，全部已解决）

**坑 1: `esp_bt.h: No such file or directory`**
整个 `bt` 组件被 `CONFIG_BT_ENABLED` 门控，没开就整个不编译。
根因：PlatformIO 实际读的是 `sdkconfig.esp32-s3-devkitc-1`（不是 `sdkconfig.defaults`），
`board_build.*` 选项被 PlatformIO 忽略（有启动警告），所以 `sdkconfig.defaults` 基本不起作用。
解决：直接改 `sdkconfig.esp32-s3-devkitc-1` 里的 `CONFIG_BT_ENABLED=y`。

**坑 2: `esp_bt_controller_init 失败: ESP_ERR_INVALID_ARG`**
两个原因叠加：
- 控制器配置结构体前两个字段 `magic` / `version` 是必填的，用 `{0}` 或复合字面量会被校验拒绝。
  解决：用官方宏 `BT_CONTROLLER_INIT_CONFIG_DEFAULT()` 拿一份 Kconfig 算好的配置。
- 我还顺手覆盖了 `controller_task_prio=5` / `stack_size=4096`，
  但 ESP32-S3 **强制要求**这两个值与 Kconfig 完全一致，报
  `Invalid controller task prioriy or stack size`。解决：不做任何覆盖。

**坑 3: 反复 `Guru Meditation (LoadProhibited)` 重启**（最耗时的一个）
`esp_bt_controller_mem_release(ESP_BT_MODE_BLE)` 传错了模式参数。
该函数会把对应模式的 ROM `.data/.bss` 区域**归还给系统堆**，传 BLE 就把
BLE 自己的 ROM 区也还了，控制器随后访问那块内存就 panic。
关键对照：官方示例 `gatts_demo.c` 传的是 **`ESP_BT_MODE_CLASSIC_BT`**。
解决：改成 `ESP_BT_MODE_CLASSIC_BT`。

> 排查过程中我一度误判为"内部堆不足"（加日志发现空闲 320KB，其实很充足），
> 用 `addr2line` 解回溯才定位到真正原因：`btdm_controller_init → malloc → block_locate_free`。
> 教训：崩溃在 malloc 里不代表内存不够，可能是内存被提前释放/踩坏。

**坑 4: 传统广播 API 链接失败**
`esp_ble_gap_start_advertising` / `esp_ble_gap_config_adv_data_raw` 报
`undefined reference`。根因：sdkconfig 开了 `CONFIG_BT_BLE_50_FEATURES_SUPPORTED`，
传统广播 API 被 `BLE_42_FEATURE_SUPPORT` 门控裁掉了。
解决：改用 BLE 5.0 扩展广播 API
（`esp_ble_gap_ext_adv_set_params` / `config_ext_adv_data_raw` / `ext_adv_start`），
`type` 填 `ESP_BLE_GAP_SET_EXT_ADV_PROP_LEGACY_IND`（等价传统 ADV_IND，兼容性最好）。

**附带发现**：`esp_ble_gatts_register_callback()` 只装回调，**不会触发** `ESP_GATTS_REG_EVT`，
必须再调 `esp_ble_gatts_app_register()`，否则回调里的建服务代码永远不执行（静默无广播）。
另外 ESP-IDF 5.1.2 **没有** `esp_ble_gatts_register_service` / `esp_ble_gatts_svcs_def_t`
（那是 5.2+ 才有的服务表 API），只能用 `create_service` + `add_char` 手动链。

## 修复 8MB Flash 分区表未生效（2026-10-04 下午）

用户反馈"都修复，底层都还没写完，后面还要大量 flash 写具体功能"，

### 问题 1：老分区表根本放不下 8MB

老 `partitions.csv` 写的是 `ota_0` 6MB + `ota_1` 6MB = **15MB**，
而板子只有 8MB Flash。就算它生效了也必然报错。

`gen_esp32part.py` 会强制校验）：

|---|---|---|---|
| nvs | 0x010000 | 24K | 键值存储（Bluedroid 存配对信息也用它） |
| otadata | 0x016000 | 8K | OTA 状态 |
| phy_init | 0x018000 | 4K | RF 校准 |
| ota_0 | 0x020000 | 3584K | 主固件 |
| ota_1 | 0x3A0000 | 3584K | 备份固件 |

## BLE UUID 改为小程序实际提供的值 + WiFi/蓝牙页重排（2026-10-04 下午）

### 背景

小程序 UUID 可以手动选择，用户把下拉列表截图发来。
列表里**只有 9 个 UUID，没有 FFE1/FFE2**，所以之前猜的透传组合一定连不上。
必须改成列表里实际存在的值。

### 列表里 9 个 UUID 的甄别

| 16 位 | 名称 | 能否当透传通道 |
|---|---|---|
| 0x1800 | GAP 服务 | 否（标准服务） |
| 0x1801 | GATT 服务 | 否（标准服务） |
| 0x2A00 | Device Name | 否（标准特征） |
| 0x2A01 | Appearance | 否（标准特征） |
| 0x2A05 | Alert Level | 否（标准特征） |
| 0x2A06 | Alert Level | 否（标准特征） |
| **0x2B29** | 自定义 | **唯一可能的服务 UUID** |
| **0x2B2A** | 自定义 | 候选特征 |
| **0x2B3A** | 自定义 | 候选特征 |

前 6 个全是 SIG 标准服务/特征，**没有任何一个能承载透传数据**。
所以只有 2B29 / 2B2A / 2B3A 这组自定义 UUID 可用，**没有备选方案**。

### ⚠️ 写/通知的对应关系是推断的，不是查到的

这点必须说清楚：网上**没有**江协小程序这组 UUID 的权威文档，而且资料互相矛盾——
有资料称 2B29 是透传服务（与小程序现象吻合），也有资料称
2B29/2B2A/2B3A 是 GATT 通用属性（设备名/设备ID/外观）。

按业界透传模块最常见的 **"服务 → 写 → 通知" 递增** 约定分配
（与 Nordic UART `6E400001/002/003`、CH579、RFCrazy 模块一致）：

| 角色 | UUID | 展开成 128 位 |
|---|---|---|
| 服务 | 0x2B29 | 00002B29-0000-1000-8000-00805F9B34FB |
| 写（手机→设备） | 0x2B2A | 00002B2A-0000-1000-8000-00805F9B34FB |
| 通知（设备→手机） | 0x2B3A | 00002B3A-0000-1000-8000-00805F9B34FB |

**如果连上后收发不通，只需把 `ble_tuner.h` 里两个宏的数值对调，重新编译烧录即可。**
为方便排查，UUID 会在串口启动日志和 UI 屏上同时显示。

### 变量改名（跟随语义变化，避免误解）

`s_rx_char_handle` / `s_tx_char_handle` → `s_write_char_handle` / `s_notify_char_handle`。
原因是原来 RX/TX 是以设备视角命名的，容易和小程序界面的"发送/接收"搞反，
现在直接叫"写特征""通知特征"，和 GATT 属性名对齐。

## BLE 能连上但无法通信：根因 = 漏调 esp_ble_gatts_start_service()

**时间**：2026-10-04 18:10

**用户反馈**：蓝牙可以连接，但是无法通信。

### 根因（已对照 ESP-IDF 5.1.2 源码确认，不是猜的）

GATT 服务创建分两步，工程只做了第一步：

```c
esp_ble_gatts_create_service(...)   /* 做了：预留 handle 区间 + 建属性表 */
esp_ble_gatts_start_service(...)    /* 没做：★这就是根因 */
```

关键在于 `esp_ble_gatts_create_service()`（→ `GATTS_CreateService`，`gatt_api.c:156`）
**不会**把服务加入协议栈的「已启动服务列表」 `gatt_cb.srv_list_info`。
该列表只在 `GATTS_StartService()`（`gatt_api.c:457`）里被填充：

```c
gatts_update_srv_list_elem(i_sreg, p_sreg->s_hdl, p_list->asgn_range.is_primary);
gatt_add_a_srv_to_list(&gatt_cb.srv_list_info, &gatt_cb.srv_list[i_sreg]);
```

而手机**服务发现**的三个 ATT 请求，全部只遍历这个列表（`stack/gatt/gatt_sr.c`）：

| 手机侧 API | ATT 请求 | IDF 处理函数 | 遍历的列表 |
|---|---|---|---|
| `getBLEDeviceServices` | Discover Services | `gatts_process_service_disc_req` | `gatt_cb.srv_list_info` |
| `getBLEDeviceCharacteristics` | Read By Type (0x2800/0x2803) | `gatts_process_read_by_type_req` | `gatt_cb.srv_list_info` |
| 属性发现 | Find Information | `gatts_process_find_info_req` | `gatt_cb.srv_list_info` |

服务没 start ⇒ 列表为空 ⇒ 三个请求全部返回 `GATT_NOT_FOUND` ⇒
小程序报 `10004 no service` / `10005 no characteristic`，读写自然全不通。

**为什么现象是"能连上"**：连接流程（`createBLEConnection` → ATT Exchange MTU）
不经过 `srv_list_info`，所以链路层握手完全正常。
这正好解释了"连得上却没任何 WRITE 事件、全程静默"。

> 官方示例 `examples/bluetooth/bluedroid/ble/gatt_server/main/gatts_demo.c:414`
> 正是在 `ESP_GATTS_CREATE_EVT` 里**先 start_service 再 add_char**，
> 之前照抄时漏了这一行。

### 顺带修的一个隐患：CCCD 句柄靠 `+1` 猜

原来判断「手机是不是在订阅通知」用的是 `写特征句柄 + 1`：

```c
if (param->write.handle == s_write_char_handle + 1 || ...) { /* 当成 CCCD */ }
```

但 CCCD 的真实句柄是由 `ESP_GATTS_ADD_CHAR_DESCR_EVT` 异步返回的，
不能假定恰好是 `+1`。现在新增 `s_cccd_handle` 保存真实句柄再比对。

### 顺带查证（已排除）：写权限不是问题

担心过"安卓默认用 Write Without Response，特征没给 WRITE_NR 会被拒"。
查 IDF 源码 `gatt_db.c:1181` 的 `gatts_write_attr_perm_check`：

```c
} else if (!(perm & GATT_WRITE_ALLOWED)) {     /* GATT_WRITE_ALLOWED 含 WRITE */
    status = GATT_WRITE_NOT_PERMIT;
```

`GATT_WRITE_ALLOWED` = `WRITE | WRITE_ENCRYPTED | WRITE_ENC_MITM | WRITE_SIGNED`，
不含 `WRITE_NR`（IDF 没有这个权限位），所以带响应/不带响应写都能过。
工程已同时打开 `CHAR_PROP_BIT_WRITE` 和 `CHAR_PROP_BIT_WRITE_NR`，配置正确，无需改。

### 修改文件

- `0.2/hardware/ble/ble_tuner.c`
  - `ESP_GATTS_CREATE_EVT` 里补 `esp_ble_gatts_start_service(s_svc_handle);`
  - 新增 `s_cccd_handle`，在 `ESP_GATTS_ADD_CHAR_DESCR_EVT` 记录，
    `ESP_GATTS_WRITE_EVT` 改用它判断 CCCD 写入
- `0.2/hardware/ble/ble_tuner.h` — 文件头补充第 4 条排查结论（含 IDF 源码依据）

### 编译验证

- `pio run` → SUCCESS (7.17s)，0 错误
- RAM: 10.3% (33,808 / 327,680)
- Flash: 22.7% (831,401 / 3,670,016)

### 待用户烧录验证

1. 小程序能扫到 `ESP32-BALANCE` 并连上
2. 串口出现 `WRITE 事件: handle=... len=N`（证明服务已能被发现并写入）
3. 出现 `-> CCCD 通知已开启`（证明订阅成功，设备→手机方向已通）

届时只需改 `ble_tuner.h` 三个宏重烧即可，不用改结构。

### 核心设计：参数表驱动，前端零硬编码

关键决定是把"参数"做成**一张扁平表**（`user/param/param.c` 的 `g_param_items[]`），
网页的滑块由 `/api/params` 返回的 JSON **动态生成**，前端 JS 里没有任何字段名。

所以以后加参数只要两步，前端和 NVS 都不用动：

1. `param.h` 的 `PARAM_ID` 加一个枚举
2. `param.c` 的 `g_param_items[]` 加一行描述

| 分组 | 参数 |
|---|---|
| 平衡环 | `bal_kp/ki/kd` |
| 速度环 | `spd_kp/ki/kd` |
| 转向环 | `steer_kp/ki/kd` |
| 限幅/滤波/硬件 | `motor_max` `spdout_max` `ang_limit` `ang_zero` `gyro_lpf` `deadband` `gear` `servo_c` `servo_l` `pwm_max` |

> 现在这些值是**占位默认值**（用户说"先做示例，具体参数等实际开始时再加"）。
> 以后写 PID 控制时直接 `param_get_float(PARAM_PID_BAL_KP)` 取值即可。

NVS 存盘用 blob（`nvs_set_blob` 一次写完整个 float 数组）+ 一个版本号。
版本号不匹配就丢弃旧数据用默认值，避免改了参数表之后旧数据错位。

### HTTP 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/` | 调参主页 |
| GET | `/api/params` | 取全部参数（含名称/范围/默认值/当前值） |
| GET | `/api/status` | 实时状态（姿态/编码器/WiFi/电机/堆/运行时长） |
| POST | `/api/params` | 批量设参数，body `{"bal_kp":12.5,...}` |
| POST | `/api/save` | 保存到 NVS |
| POST | `/api/reset` | 恢复默认（仅内存） |
| POST | `/api/motor` | 电机测试，body `{"on":1,"speed":40,"dir":1}`（1=A 2=B 3=双 0=停） |
| POST | `/api/stop` | 急停 |
| POST | `/api/servo` | 舵机回中 |
| POST | `/api/reboot` | 重启 |

**JSON 解析手写，没引 cJSON**：调参数据全是我们自己定的格式（ASCII 数字 + 引号），
手写扫描 60 行搞定，少一个组件依赖。`param_from_json()` 逐个 `"key"` 找到对应
`param_id_t` 再 `strtof` 取值，并按 `step` 对齐（避免拖出 12.37 这种值）。

### 网页的三个实用设计

1. **滑块拖动合并下发**：拖动时连续触发 `oninput`，每次都发 HTTP 会刷爆 ESP32。
   前端用 80ms 防抖 + `sending/resend` 单飞标志合并，**保证最后一个值一定送到**。
2. **电机看门狗**：网页被杀掉 / 手机断网时电机不能一直转。
   `motor_watchdog_task()` 每 200ms 检查，超过 4 秒没收到网页请求就自动停。
   > 踩过的坑：最初只在 `/api/motor` 喂狗，但用户**按住速度滑块拖动**时并不会重复发
   > `/api/motor` → 拖到一半电机被误停。改成"网页每 500ms 轮询 `/api/status`
   > 就是心跳，顺带在 `/api/status` 里喂狗"，拖滑块时轮询一直在，电机不会停。
3. **关页自动停**：`beforeunload` 里用 `sendBeacon('/api/stop')` 急停。

### 踩坑记录（4 个真实报错）

**坑 1：`esp_netif_create_default_ap_ap` / `IP_EVENT_AP_STAIPASSIGNED` 等符号不存在**
ESP-IDF 5.1.2 的 API 名和 5.2+ 不一样。对照 `esp_wifi_types.h` 实际枚举后修正：
- `esp_netif_create_default_ap_ap(NULL)` → `esp_netif_create_default_wifi_ap()`（**无参数**）
- 客户端连接事件在 `WIFI_EVENT_AP_STACONNECTED`（不在 `IP_EVENT`），
  且**没有** `WIFI_EVENT_AP_START_FAILURE` 这个事件
- 顺便把 IP 赋值改成 `ip4addr_aton(s, (ip4_addr_t *)&ipinfo.ip)`
  （`esp_ip4_addr_t` 和 `ip4_addr_t` 布局相同，但类型不同，直接传会报
  `-Wincompatible-pointer-types`）

**坑 2：`httpd_err_handler_func_t` 签名不匹配**
404 兜底 handler 是 `esp_err_t (*)(httpd_req_t*, httpd_err_code_t)`，
比普通 handler 多一个错误码参数。漏了会报
`expected 'httpd_err_handler_func_t' but argument is of type 'esp_err_t (*)(httpd_req_t *)'`。

**坑 3：加 `esp_timer` 依赖后仍报 `esp_timer.h: No such file`**
`idf_component_register(REQUIRES esp_timer)` 改了，但 PlatformIO 复用了旧的
`CMakeCache.txt`，组件的 `REQUIRES` 没重新解析。删掉
`.pio/build/<env>/CMakeCache.txt` 重编就过了。**改 REQUIRES 后遇到头文件找不到，先删缓存重试。**

**坑 4：屏幕显示的热点名和实际不符**
实际广播的 SSID 是 `BalanceRobot_7EBD`（`WIFI_AP_SSID` + MAC 后两字节），
但 UI 页直接打印了 `WIFI_AP_SSID` = `BalanceRobot` —— **用户按屏上名字根本搜不到热点**。
新增 `wifi_ap_get_ssid()` 返回真实 SSID，UI 和日志都改用它。

另外顺手算了一下 `/api/params` 的实际输出长度（19 项约 2991 字节），
原来 `static char buf[3072]` 只剩 81 字节余量，加几个参数就会截断导致
网页 JSON 解析失败、滑块全空。已加大到 4096 并在代码里写明"加参数超过 ~30 个要同步加大"。

### 一、0.2 整理（只做注释和冗余清理，不改功能）

扫了一遍全部 55 个源文件，确认**没有遗留调试代码**（无 `TODO` / `printf` 调试 / 临时 dump）。
这一轮实际改的只有 4 处：

#### 1. 修拼写错误 + 简化过时注释

`hardware/servo/servo.c`、`servo.h`：
- 「两**股**舵机」→「两路舵机」（错别字，2 处）
- `servo.c` 文件头原来写「舵机2 物理反向安装: 实际硬件角度 = 180 - 逻辑角度」，
  这句是 10-04 上午改 GPIO 映射**之前**的旧描述，和现在的

#### 2. 删除未使用的 API

- `servo_set_pulse()`（`.h` 声明 + `.c` 定义，全工程 0 处调用）→ 删
- `SERVO_MID_PULSE_US` 宏（0 处引用）→ 删

#### 3. 修一个真实的显示错位 bug（`ui_home.c`）

主页编码值行首次绘制和周期刷新用了**两套不同的 X 坐标**：

```c
// page_enter 里首次画
ui_draw_string(20, HOME_ENC_Y, buf, ...);   // 硬编码 20

// page_refresh 里刷新
ui_fill_rect(HOME_ENC_X /* =18 */, ...);   // 常量是 18
ui_draw_string(HOME_ENC_X, HOME_ENC_Y, buf, ...);
```

所以进主页后**第一次 150ms 刷新后，E1 数字会左移 2 像素**，和右路 E2 不对齐。
另外 `page_refresh` 里右路的 X 也是硬编码 `84`，没走常量。

修法：把两路拆成对称的 4 个常量（`HOME_L_LBL_X` / `HOME_L_VAL_X` /
`HOME_R_LBL_X` / `HOME_R_VAL_X`）+ 一个擦除宽度 `HOME_VAL_W`，
首次绘制和刷新共用同一组常量。顺带把 `HOME_VAL_W` 从 48 收到 42
（84+42=126，留 2px 右边距；原来 48 画到 132 已经超出 128 屏宽，
虽然多擦的部分在屏外不会显示，但属于无效操作）。

#### 4. 补 `encoder_get_rpm()` 的 `interval_ms` 语义

这个参数**声明和文档都写了，但实现里根本没用**——函数内部用 tick 快照差算 elapsed，
`interval_ms` 传什么都没区别。这是个隐患：调用间隔一变（比如从 150ms 改成 500ms），
函数会静默返回"瞬时速度"但没有任何提示。

补上校验：实际间隔与 `interval_ms` 偏差超过 ±50% 时返回 0，
并在 `.h` 里写明这个语义。`pdMS_TO_TICKS(interval_ms)` 为 0 时跳过校验（不误伤）。
