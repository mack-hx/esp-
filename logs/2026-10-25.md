## 二、查到的 SK6812 规格 (以官方/原厂规格书为准)

来源:
- 阶新科技 SK6812 (RGB) 规格书: `cdn-shop.adafruit.com/product-files/1138/SK6812+LED+datasheet+.pdf` (SPC/SK6812 Rev.01)
- 欧思科 SK6812 规格书: `cdn.semikey.com/upload/pdfs/10/fa/10faf1794d81012c0ad48d24300c6d49.pdf` (SK6812-EC20-001 A/0)
- SK6812-RGBW 规格书: `suntechlite.com/wp-content/uploads/2025/07/SK6812-RGBW-5V-Specification-Datasheet.pdf` (SKC6812RGBW-XX-X-00X B/0)

| 项目 | 规格要求 | 备注 |
|---|---|---|
| 数据结构 | 32bit, **GRBW** 顺序 (G7→G0 R7→R0 B7→B0 W7→W0), 高位先发 | RGBW 版确认; RGB 版是 GRB |
| 码元周期 | 1.2µs | 各版本一致 |
| "0"码 | T0H 0.2~0.4µs (取 0.3), T0L ≥0.8µs (取 0.9) | 各版本一致 |
| "1"码 | 阶新2020版: T1H/T1L = 0.6µs±0.15 (即 0.45~0.75)<br>欧思科/RGBW版: T1H 0.65~1.0µs, T1L ≥0.2µs | **两版不一致** |
| 复位码 | 低电平 **> 200µs** (RGBW/欧思科版), 另一版 > 80µs | 芯片靠它锁存数据 |
| 帧内低电平 | 必须 < 20µs (不能有断流) | 要求整帧连续发出 |
| 传输速率 | ≤ 800kbps | |
| 工作电压 VDD | RGBW 版 3.5~5.5V; RGB 版 3.7~5.5V | **3.3V 供电低于规格下限** |
| 输入翻转阈值 VIH | RGBW 版 2.7V @VDD=5.0V; 阶新2020版 3.4V @VDD=5.0V; 欧思科版 0.7×VDD | **5V 供电时 3.3V 的 IO 电平可能达不到阈值** |

参考驱动 (实测能点亮 SK6812-RGBW 的公开 ESP32 库 `gitpeut/SK6812-RGBW-ESP32`):
- 10MHz 时钟 (100ns/tick), "1"码 = 高 600ns + 低 600ns, "0"码 = 高 300ns + 低 900ns
- 数据按 GRBW 拼 32bit 发送 —— 与规格书一致

## 三、代码检查结论与修改

### 发现的问题 1: "1"码时序对不同版本的 SK6812 规格不通用
- 现状: `hardware/led/led_strip_encoder.c` 用 T1H=0.9µs / T1L=0.3µs (WS2812 时序)
- 问题: 三份规格书对 "1"码定义不一致 ——
  阶新 2020 版: T1H/T1L = 0.6µs±0.15 (0.45~0.75); 欧思科/RGBW 版: T1H 0.65~1.0µs, T1L ≥0.2µs。
  0.9/0.3 对 2020 版是**超规格**的 (高电平太长、低电平太短)
- 修改: 改成 **T1H=0.7µs / T1L=0.5µs** —— 唯一同时落在两种版本范围内的取值 (码元周期仍是 1.2µs);
  "0"码 0.3/0.9 不动 (各版本一致)

### 发现的问题 2: 复位码只有 50µs, 达不到规格的 >200µs
- 现状: 编码器默认 `reset_us = 50`, `param` 表里 `led_rst` 默认也是 50
- 问题: 规格要求 >200µs (RGBW 版), 芯片不锁存 → 灯不亮
- 注意: 0.2 版本 2026-10-24 已经把编码器里的复位码改成固定 300µs,
  **但 0.21 拷贝时又退回成 50µs**, 并且 `param` 默认值也是 50 → 两处默认值互相"盖住", 改一处不生效
- 修改:
  - `hardware/led/led_strip_encoder.c`: 默认 `reset_us` 50 → **300µs**
  - `hardware/led/led.c`: `s_reset_us` 初值 50 → **300µs**
  - `user/param/param.c`: `led_rst` 默认 50 → **300µs**, 取值范围 20~300 → **200~1000**
  - `hardware/led/led.c` 的 `led_set_reset_us()`: 强制下限 200µs (规格下限),
    防止 NVS 里存了旧值 (50/100µs) 时又把复位码压回不达标

### 检查过、确认没问题的部分
- 数据格式: 代码支持 24bit GRB / 32bit GRBW 两种, 开机自检各闪一遍 —— 与规格书的 32bit GRBW 一致
- 帧长: 一次发整条链 (8 颗 × 每颗字节数), `led_num` 可调 —— 逻辑正确
- DMA: `mem_block_symbols = 512` + `with_dma = true`, 一帧 256+1 个 symbol 一次装下, 帧内无断流 (满足"帧内低电平 < 20µs")
- RMT 空闲电平: IDF 的 `rmt_ll_tx_fix_idle_level(..., 0, true)` → 空闲为低, 复位低电平能形成
- MSB 先发: `msb_first = 1`, 与规格书"高位先发"一致

### 发现的问题 3: 默认数据格式是 24bit, 但实测灯珠是 32bit RGBW
- 用户确认: 新灯是 **SK6812-RGBW (32bit, GRBW 顺序)**, VCC 5V, DIN 高电平实测 3.3V
- 修改: `hardware/led/led.c` 里 `s_format` 初值 24bit → **32bit GRBW**;
  `user/param/param.c` 里 `led_fmt` 默认 0 → **1**
  (注意: NVS 里存的旧值优先级更高, 需要在 App 参数页把 led_fmt 设成 1、led_rst 设成 300)

## 四、临时诊断代码自身的问题 (还没删, 等问题定位完)

## 六、硬件层面的判断 (用户已确认: VCC=5V, DIN 高电平=3.3V, 灯珠=SK6812-RGBW 32bit)

### 1. 输入高电平裕量不足 —— 目前最可疑的一条
- 规格书对输入翻转阈值 VIH 有三种写法:
  - SK6812-RGBW (SKC6812RGBW): **VIH = 2.7V** @VDD=5.0V, VIL = 1.8V
  - 阶新 2020 版 SK6812: **VIH = 3.4V** @VDD=5.0V
  - 欧思科 SK6812: **VIH = 0.7×VDD = 3.5V** @VDD=5.0V
- ESP32-S3 的 IO 是 3.3V: 只在最宽松的那一版 (2.7V) 下才够, 裕量只有 0.6V;
  另两版阈值都在 3.3V **之上** → 芯片把 DIN 一直判成 "0" → 锁存全 0 → **灯不亮, 但 DIN 上确实有波形**,
  和现在的现象完全吻合
- 解决方案 (二选一):
  - **加电平转换 (推荐)**: 74AHCT125 / 74HCT245, VCC=5V, GND 与主控共地,
    ESP32 GPIO9 → 转换器输入, 转换器输出 → 模组 DIN (中间串 100~330Ω 电阻更好)
    ⚠ **不能用 74HC125**: HC 系列输入阈值 0.7×VCC=3.5V, 会把 3.3V 判成低电平 (和现在一样不亮);
    AHCT 系列输入阈值 2.0V, 3.3V 能被识别, 输出是 5V 满摆幅
  - **把模组改用 3.7V 供电**: VIH = 0.7×3.7 = 2.59V, 3.3V 逻辑能识别;
    VDD 3.7V 也在 RGBW 版规格 (3.5~5.5V) 内。代价: 白光通道 (正向 3.0~3.3V) 会偏暗
- 之前的 1.1 版本能用, 大概率是因为数据是经 74HC595 出来的 (5V 供电时是 5V 电平),
  现在直连 ESP32 的 3.3V 就掉到了阈值边缘

## 三、发现的硬约束 (ESP32-S3 的 RMT 内存)

- `SOC_RMT_MEM_WORDS_PER_CHANNEL = 48`, 每组 4 个 TX 通道 → 一组总共 **192 symbol**。
- 非 DMA 模式: `mem_block_num = mem_block_symbols / 48`, 申请超过一组总量直接失败。
  **实测: `mem_block_symbols=512` 且不开 DMA → `rmt_new_tx_channel` 返回
  `ESP_ERR_NOT_FOUND` → `ESP_ERROR_CHECK` 触发重启循环** (本次踩到了, 已修复)。
- 非 DMA 是 ping-pong 发送, 一帧必须装进**半个**内存块 (96 symbol) 才不会断流:
  → 24bit 格式一帧最多 3 颗, 32bit 格式最多 2 颗。
- DMA 模式只给通道 1 个内存块, 帧长受 DMA buffer 限制。

## 五、烧录过程中的故障与解决

1. **板子进了 bootloader 重启循环**: `ota_0` 分区校验失败

   + `0x20000 firmware.bin` → 校验通过, 板子恢复正常启动。
   **注意: `pio run -t upload` 只写 app (0x20000), 不写 bootloader 和分区表**,
   擦过整片 flash 后必须用 esptool 手动补这两段。
