## 下午 — 定位「输入内容过长」真因 + 跨对话交接机制

### 背景
上午定的第 14 条规则假设"大文件"是元凶，但用户反馈**仍然经常报错**，
且**新开对话会忘记上次对话的思考内容**。两条线索都要解决。

### 实测 (用 Cursor 会话记录 .jsonl 逐条统计, 排除构建产物)
统计每个会话的上下文占用 = 助手文字 + tool_use 入参 + tool_result 回读 + 用户输入：

| 会话 | 累计 token | 助手输出文字 | 工具 IO | 助手占比 | 最长单段 |
|---|---|---|---|---|---|
| 9f0cfa05 | 144,011 | 483,205 | 6,232 | **98.7%** | 59,538 |
| 3a6aedd0 | 126,474 | 419,732 | 10,145 | **97.6%** | 30,677 |
| 189a583b | 123,805 | 406,004 | 14,355 | **96.6%** | 57,394 |
| 78dc795d | 112,708 | 374,287 | 8,810 | **97.7%** | 41,677 |
| ced16e92 | 101,734 | 325,978 | 18,860 | 94.5% | 22,554 |
| b99da1c6 | 72,530 | 186,191 | 59,925 | 75.7% | 20,485 |

**结论：元凶是助手自己的输出文字（占 75%~99%），不是读进来的大文件（工具 IO 仅 1%~30%）。**
真实报错触发点累计上下文 80k~200k token，中位 ~101k。上午的规则诊断有误。

### 解决方案
1. **`scripts/ctx_check.py`（新增）** — 上下文自测脚本
   - 统计当前会话占用并判定红/黄/绿（<90k / 90k~140k / >140k token）
   - `--all` 看最近 10 个会话的历史规律；`--json` 机器可读
   - 会话目录自动探测（slug 规则 + 模糊匹配兜底），不写死路径
2. **`HANDOFF.md`（新增，根目录）** — 跨对话交接文件
   - 记录：当前在做什么、0.31 改了什么、验证状态、待办、关键约定
   - 解决"新开对话忘记上次思考"：新对话开工先读它，不用从头复述
3. **规则第 14 条重写** — 基于实测数据
   - 14.1 实测结论（先看这个，不要再猜）
   - 14.2 硬性要求：每轮输出 2~3 段以内、单段 ≤ 8 KB、大范围比对派子代理
   - 14.3 跨对话交接：收工前必须更新 `HANDOFF.md`
   - 14.4 自测：黄/红灯时主动告知用户，不等 Cursor 报错
4. **规则第 6 条补一句** — 把 `HANDOFF.md` 挂进日常日志流程

### 教训
- 遇到"上下文过长"先**测量**再改规则，不要凭直觉归因到"大文件"
- 用户说的"新开对话就忘事"和"输入过长"是**同一个病的两个症状**：
  思考全在对话里没落盘，所以既撑爆上下文，切换后又会丢失

## 上午 — 新增规则：大文件与上下文控制

### 背景
上一轮 (0.31 收尾) 会话输入过长，规则里没有"大文件怎么处理"的约定，
导致单次读入巨型源码 / 整篇日志吃满上下文。

### 修改内容
- 规则文件 `.cursor/rules/project-workflow.mdc` 新增第 14 条 **「大文件与上下文控制」**：
  - 阈值定义：源码 > 1000 行或 > 50 KB；日志/文档 > 800 行或 > 50 KB
  - 大文件禁止整篇 `Read`，改用 `Grep` 精确定位 + 分段 `Read`
  - 需通读时派子代理（`explore`/`generalPurpose`），只回传结论/行号/差异，不回传原文
  - 子代理 prompt 必须自包含
  - 开工读日志只读最近 1~2 天相关章节，或按关键词 `Grep`
  - 新写 `.c` 超 1000 行须按功能拆分
  - 单文件 > 100 KB 入库前先问用户
  - 上下文吃紧时主动提示新开对话，结论先落盘

## 下午 — 拆分控制环: 新建 `0.31/user/pid/` 组件

### 背景
用户反馈"平衡控制文件代码太长"。`0.31/user/control/balance.c` 有 1313 行，
里面混着三个控制环的 PID 运算 + 传感器采样 + 状态机 + 电机输出, 改一个环的参数
要在几百行里翻。

### 用户决定 (AskQuestion 确认)
1. **位置环怎么处理**: 工程里根本没有位置环 (没有里程计, 编码器只能给瞬时转速,
   积分成位移需要轮径参数, 参数表里也没有) → 选「只建文件 + 接口占位, 默认不接入
   控制流程, 当前车行为完全不变」。
2. **通用 PID 要不要一起搬**: 选「一并移到 `user/pid/`, `user/pid` 成为独立 IDF 组件」。

### 修改内容

**新增组件 `0.31/user/pid/`** (每个环一个 .c, 接口统一: init / load_params / reset / update):

| 文件 | 行数 | 环 | 输入 → 输出 |
|---|---|---|---|
| `pid.c` / `pid.h` | 155 / 158 | 通用 PID 算法 | 从 `user/control/` 搬过来, 新增 `pid_i_max()` |
| `balance_pid.c` / `.h` | 53 / 56 | 平衡环 (内环) | 姿态误差 + 角速度 → 电机输出 (%) |
| `speed_pid.c` / `.h` | 66 / 94 | 速度环 (外环) | 轮速误差 → 目标倾角 (°) |
| `steer_pid.c` / `.h` | 38 / 56 | 转向环 (差速环) | 左−右 轮速差 → 两轮输出差 (%) |
| `position_pid.c` / `.h` | 43 / 69 | 位置环 (**预留, 未接入**) | 位置误差 → 目标轮速修正 (rpm) |

**常量跟着环一起搬** (原来全挤在 `balance.h`):
- 速度环: `BAL_SPD_ERR_DEADBAND` → `SPD_PID_ERR_DEADBAND`,
  `BAL_WALK_PITCH_MAX` → `SPD_PID_WALK_PITCH_MAX`,
  `BAL_SPD_KP_DEFAULT/KI_DEFAULT` → `SPD_PID_KP_DEFAULT/KI_DEFAULT`
- 转向环: `BAL_YAW_KP/KI/OUT_MAX` → `STEER_PID_KP/KI/OUT_MAX`

**`balance.c` 瘦身**: 1313 → 1256 行。删掉三个静态 `bal_pid_t` 实例
(`s_pid_bal` / `s_pid_spd` / `s_pid_yaw`) 和 `balance_i_max()`, 改成转调各环:

`balance.c` 现在只管: 传感器采样 / 状态机 / 摔倒检测 / 电机输出 / 对外 API。
