# ESP32-S3R8N8 平衡轮腿机器人 - 版本 0.30

## 0.30 相对 0.22 改了什么

**0.30 是从 0.22 干净复制出来的新迭代基线**, 收编了 0.22 发布之后
(`v0.22` tag 之后) 在 0.22 目录里做的一批修复, 并把版本号整体推到 0.30。

> 0.22 的 GitHub release 是在那批修复之前发布的, 所以 **0.30 是第一个
> 包含"车能自己站住"这批修复的正式发布版本**。

### 一、平衡控制三处致命修复 (真机验证)

| 问题 | 症状 | 根因 | 修复 |
|---|---|---|---|
| 电机方向常量取反 | 车往前扑倒; 快扶正时轮子猛转 | `BAL_MOTOR_SIGN` = -1, 但实测"电机正转 = 轮子往车尾跑" | 改成 **+1** (`user/control/balance.h`) |
| 平衡环 D 项符号反了 | 起立时剧烈抖动, 站不住 | `kp*err + ki*i - kd*rate` → 阻尼项变成**负阻尼**, 越晃越大 | 改成 **+kd*rate** (`user/control/pid.c`) |
| 速度环吃 10ms 编码器量化值 | 电机前后猛顶 | 1 个脉冲 = 136 rpm, 2 rpm 误差就把目标倾角打到限幅 | 轮速改 **100ms 窗口**统计; 速度环默认关 (`spd_kp`/`spd_ki` = 0) |

另外把积分限幅改成按**输出量**算 (`i_max = (out_max/2)/Ki`), 原来直接写 `out_max/2`,
乘上 Ki=12 后积分项能到输出的 180%。

### 二、其它固件修复

- `motor_max` 默认 30 → **60** (方向修正后实测接得住)
- `PARAM_DATA_VERSION` 7 → **9**: 让 NVS 里存的旧参数 (含错的 D 符号默认值) 作废
- 编码器增量改成 `(int16_t)(cur-last)`: PCNT 计数到 ±32767 会回绕, 按 int 相减会算出 65535 的假增量
- MPU9250 初始化失败**重试 10 次** (间隔 500ms): 实测上电第一次读 WHO_AM_I 会失败
- **配平表不再每次上电被擦除** (`balance_init()` 只 `trim_load()`), 修掉"网页标定一断电就归零"
- **AP 配网热点开不起来**: `start_ap_mode()` 设 IP 前先 `esp_netif_dhcps_stop()`,
  失败不再中断 (原来一失败就 `return`, `esp_wifi_start()` 永远没执行 → 热点一帧都不广播);
  认证方式从开放网络改成 WPA2 (密码 12345678), 新增 `wifi_sta_get_ap_ssid()`
- 屏上网络页 AP 模式显示**真实热点名** (原来显示 "<AP Mode>", 用户按屏上的名字搜不到)
- 修正 MPU 轴向注释: 上 = Z 轴, 车头 = -Y 轴, 俯仰绕 X; 前倾时 pitch 与 gx **都是负数**

### 三、App 端修复 (状态页)

1. **修 `requestAnimationFrame is not defined`**: 折线图原来照 H5 端写死, App 端
   (app-plus 逻辑层) 没有 `document` 也没有 `requestAnimationFrame` → 整页 `onShow` 抛异常。
   改成跨端画布适配器 (H5 用原生 ctx, App/小程序用 `uni.createCanvasContext`),
   动画循环改 `setInterval`
2. **修"车动了要七八秒曲线才变"**: 属性历史查询的窗口原来用手机本地时钟算,
   手机时钟一不准, 窗口整体落在过去 → 只能查到旧点。改成以**平台服务器时间**为基准
   (从 HTTP 响应头 `Date` 取), 实测最新点落后真实时间从 8.2s 降到 ~1s
3. 曲线量程 ±30° → **±60°**; 心跳读数改显示"最近 3 秒最大到达间隔" (不再在 0 与 200ms 之间跳);
   "时钟偏差"改成响应式 data 字段 (计算属性里调非响应式函数 → 永远不刷新)

### 四、配套新增

- `test/bal_sim.py`: 倒立摆离线仿真脚本, 可 `--scan` 扫参数, 用来在不动硬件的情况下
  验证 D 项符号、电机极性这类结构性错误
- `test/test_pid_pc.c`: 新增闭环阻尼用例 (正确符号必须衰减, 取反必须发散)

### 五、0.30 相对 0.22 实际改动的地方

只改版本号相关的文件, 功能代码与 0.22 (含修复) 逐字节一致:

- `version.txt` → `0.30.0`
- `app/package.json` → `version: 0.30.0`
- `app/manifest.json` → `versionName: 0.30.0`, `versionCode` 131 → 140
- `README.md` → 版本号与目录结构说明
- 注释里的历史版本号引用同步 (`ui_home.c` / `param.c`)

### 六、2026-10-26 追加修复 (反馈: "稳一会后高频抖动, kp 降到 0 都没用" + "pitch 每次上电重启后就不对")

| 问题 | 根因 | 修复 |
|---|---|---|
| App 上改 Kp/Ki/Kd **完全不生效** | `balance_load_params()` 只在启动时调一次, 且用的是 `pid_config()` (带清积分) | 拆出 `pid_set_gains()` (只改系数保留积分), 控制任务**每周期**重新读参数表 → 拖滑块下一个周期就生效 |
| 积分顶死后开始抖 | 输出饱和时积分还在同向累加, 攒到 `i_max` (输出上限的 180%) | 加**条件积分抗饱和**: 输出已顶限幅且误差同向 → 冻结积分 |
| 控制周期被网络任务抢占 → 相位失配 | 控制任务优先级 6, 与 OneNet 高速上报任务同级 | 控制任务提到 **7**, 上报任务降到 5/4/3 |
| 每次上电 pitch 都不一样 | 陀螺零偏每次上电重新标定, 标定时手一抖零偏就变; 互补滤波首帧从 0 收敛要 0.5s | 陀螺零偏**存 NVS** (`imu`/`gof`), 上电直接沿用; 标定加**运动抑制** (采样期间在动就剔除); 互补滤波首帧直接用加速度角当初值 |
| 配平零点没做断电保存的处理 | 手动配平本来就存 NVS (`bal`/`pz`), 但零点会随传感器零偏漂移 | 起立时若 pitch 与上次标定相差 ≤1°, **自动微调零点并落盘**; 超过 1° 则不动零点并提示按 App 的「配平」 |

配套: `test/test_pid_pc.c` 新增 2 个用例 (抗积分饱和 / `pid_set_gains` 保留积分), 共 **21/21 通过**。

> ⚠ 陀螺零偏现在存在 NVS 里, 换 IMU 或觉得零偏不对时, 用屏上 **MPU9250 页按 K2** 重新标定
> (标完自动存盘)。首次烧录新固件时 NVS 里没有零偏, 开机标定一次即可 (要求设备静止)。

## 0.21 相对 0.2 改了什么

**只改一件事: App 状态页的俯仰角数据传输速度**。

0.2 里 pitch 混在 200ms 一帧的慢通道里上报, App 只能每 200ms 轮询一次"最新值",
曲线点稀、跟手感差。0.21 把 pitch 拆出来走一条独立的高速通道。

### 一、设备端 (`user/onenet_client/onenet_client.c`)

- **新增 `publish_fast_task`**: 单独一个任务, 周期 `FAST_PERIOD_MS = 50ms` (即 20Hz),
  每次只发一帧、帧里只有 `pitch` 一个属性 (帧短, 平台入库快)。
- **pitch 从慢通道移出**: 200ms 那帧现在只发 `roll` / `yaw`。
  两条通道各发各的, 慢通道不占 pitch 的带宽, 高速通道也不被慢通道拖慢。
- **时间戳改成毫秒精度**: `now_epoch_ms()` 从 `time(NULL)` (秒) 改成 `gettimeofday()`。
  20Hz 上报时同一秒里有 20 个采样点, 只用秒级时间戳 App 端根本分不出先后。

### 二、App 端

- `app/common/onenet.js`: 新增 `queryDevicePropertyHistory(identifier, start, end)`,
  走平台开放接口 `GET /thingmodel/query-device-property-history` 读属性历史采样点。
- `app/pages/status/status.vue`:
  - 新增 `_pollPitch()`: 每 `PITCH_POLL_MS = 120ms` 拉一次历史 (平台一次最多返回 10 个点),
    按时间戳排序去重后合并进 `pitchSeries`;
  - 折线图改成**按时间轴**摆点 (以最新点为右端, 往左铺 `PITCH_WINDOW_MS = 3000ms`),
    漏采样时曲线的疏密能反映真实采样密度;
  - 图表下方新增"采样点"和"数据延迟"两行文字;
  - 高速通道没有数据时, 退回 0.2 的 200ms 轮询兜底。

### 三、没改的部分

LED / 电机 / 平衡环 / 参数表 / UI 全部保持 0.2 原样 (0.2 的 LED 代码是好的, 不要动)。

## 驱动方式: 双轮同向 (不是差速)

平衡靠两轮**一起**朝倒的方向跑, 用轮子的牵引力把重心甩到轮轴上方 ——
标准 inverted-pendulum-on-wheels 平衡车做法。

差速只能让车**原地转**, 产生不了托住重心所需的平移加速度, 扶不住倒下的车身。

| 常量 | 值 | 说明 |
|---|---|---|
| `BAL_MOTOR_SIGN` | `+1` | **2026-10-25 真机实测复核**: 前倾 (pitch<0) 时电机输出必须为负, 轮子才会往车头方向跑去接住车。之前取 `-1` 正好反了 → 车往前扑倒 |
| `GYRO_PITCH_SIGN` | `+1` | 实测: 前倾时 `pitch` 与 `gx` **都是负数**, 两者同号 (互补滤波自洽) |
| `PITCH_ZERO_REF` | `90.0°` | 2026-10-15 新四连杆结构: 水平位 az≈1, ay≈0 → atan2(1,0)=90° |

> ⚠ **本工程的姿态角符号**: 车头前倾 (车头往下) = **负数**。
> 实测装机: 车的上方向 = MPU 的 **Z 轴**, 车头方向 = MPU 的 **-Y 轴**,
> 俯仰 = 绕 MPU 的 **X 轴**旋转。详见 `hardware/mpu9250/mpu9250.c` 的注释。

这三个数**只有拆电机 / 换 MPU 装配方向**才会变, 一年也碰不到一次。
留成网页滑块反而是隐患: 被误碰 / 不小心存盘, 下次烧录就翻车。

## 控制结构

```
速度环 (外环, 慢)  ──> 目标倾角 target_pitch (°)
     │
     ▼
平衡环 (内环, 快)  ──> 电机输出 (%)  ──>  两轮同向

输入: MPU 姿态角/角速度 + 编码器轮速
输出: 电机 A/B PWM (两轮同向) + 两路舵机
```

**控制周期 10ms 单环串级**, 用 `vTaskDelayUntil` 保证周期稳定。

## 姿态读数的修正链

```
pitch_修正 = pitch_原始 − trim_pitch(舵机角, 舵机中心角)
```

`trim_pitch` 是配平表 (`user/trim`)。在信号侧减而不是在目标倾角上加, 这样
摔倒判定 (`|pitch| > ang_limit`) 也跟着被修正, 否则腿弯多了会误判摔倒。

## 状态机

```
IDLE ──(启动)──> STANDBY ──(连续稳定 arm_time)──> BALANCING
                                                    │
                                               (倾角超限)
                                                    ▼
                                                 FALLEN
                                                    │
                                              (人把车扶正)
                                                    ▼
                                                 STANDBY
```

- **IDLE**: 未启动, 电机刹车
- **STANDBY**: 已启动但还没进平衡 (等姿态连续稳定 = 启动门控)
- **BALANCING**: 控制中
- **FALLEN**: 判定摔倒, 电机已停、积分已清, **等扶正后自动回 STANDBY**

**启动门控**: 必须连续满足 `|pitch| < arm_pitch` 且 `|角速度| < arm_rate`
达 `arm_time` 毫秒才放行。原因是"没超限"和"稳得住"完全是两回事 ——
被扶着还在晃就放行, 电机一接手晃得更厉害, 直接摔。

**摔倒判定**: `|pitch| > ang_limit` (默认 25°)。宁可误停也不能不停。

## 硬件映射

编号统一为「物理左 = 1, 物理右 = 2」。

| 实物位置 | 编码器 | 电机 | 舵机 |
|---|---|---|---|
| 左 | `ENCODER_1` = GPIO45/46 | `MOTOR_A` = PWMA (GPIO15) | `SERVO_1` = GPIO14 |
| 右 | `ENCODER_2` = GPIO41/42 | `MOTOR_B` = PWMB (GPIO16) | `SERVO_2` = GPIO13 |

     超过 1° 则不动零点, 串口日志会提示按 App 的「配平」。

   2026-10-25 方向已真机确认, 默认值已提到 60)
3. 扶正车 → 启动 → 看到启动门控计时满 `arm_time` 后电机才开始输出
4. 观察车往**倒的方向**冲 = 方向正确 (已烘焙在 `balance.h` 里, 2026-10-25 实测通过)
5. **只调平衡环, 速度环先关着** (`spd_kp`/`spd_ki` 默认 0)。
   站着的时候目标轮速恒为 0, 开速度环只会把编码器量化噪声放大成抖动。
6. 调平衡环的顺序 (一次只动一个参数):
   - `bal_kp`: 车软趴趴站不住 → 往上加; 高频嗡嗡抖 → 往下减
   - `bal_kd`: 晃得停不下来 → 往上加; 尖叫声 → 往下减
   - `bal_ki`: 最后才加, 只用来消"站住了但慢慢歪"的残余偏差;
     一加就猛冲就说明配平没标好, 回配平去
7. **全程扶着车, 随时准备断电**
