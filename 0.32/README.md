# ESP32-S3R8N8 平衡轮腿机器人 - 版本 0.32

## 0.32 相对 0.31 改了什么

**0.31 的遗留问题**: 0.31 里 `bal_kd` 的默认值已经改成 0.4 (真机实测修好了
"一起立就剧烈抖动"), 但 **App 侧 `paramDef.js` 还停在 1.5**, 而 App 下发参数时
用的是 App 里的值 —— 也就是说**源码默认值改了, 真机行为没改**。
0.32 把这条链补齐, 并把控制回路跟踪从 `balance.c` 拆成独立组件。

| # | 改动 | 起因 | 影响 |
|---|---|---|---|
| 一 | `bal_kd` 默认值 **1.5 → 0.4** (车端 + App 两侧同步) | 0.31 只改了车端, App 还在推 1.5 | App 不会再把车打回打摆状态 |
| 二 | 参数表版本 16 → **17** (作废旧 NVS blob) | 只改默认值不升版本 → NVS 里的旧 kd=1.5 照样生效 | 所有参数回到出厂默认, **必须重新配平** |
| 三 | 控制回路跟踪拆成独立组件 `user/trace/` | 在控制任务里 `printf` 会给内环加几十毫秒延迟 | 采集不再干扰内环, 数据也不再被打印污染 |
| 四 | TRACE 行格式统一 (固件 / 采集 / 分析三方对齐) | 三个脚本各自写死一份列名, 早就不一致 | 分析脚本不用再手工改列号 |
| 五 | `fft_trace.py` 修了两个真 bug (列错位一列 / 段切太碎) | 之前"找到 0 段抖动" —— 恰好在真抖时什么都不输出 | 频谱分析现在能用了 |
| 六 | 控制台波特率 115200 → **230400** | 100Hz × 125 字节 = 12.5KB/s > 115200 的 11.5KB/s | 不再丢行, 采样率不再骗人 |

> ⚠ **0.32 烧录后必须重新配平**: 参数表版本 16 (0.31) → **17** (0.32),
> NVS 里**旧的参数表和旧的配平表 / 配平零点全部作废**, 会自动回到 0.32 的新默认值
> (`bal_kp=12` / `bal_ki=0.5` / **`bal_kd=0.4`** / 位置环默认关),
> 配平要用 App 的「配平」重新标一次。
>
> ⚠ **别再加大 `bal_kd`**。真机实测的机理 (详见 `logs/2026-10-27.md`):
> kd=1.5 时平衡内环存在一个**饱和极限环** —— 输出常驻 ±60% 打摆, 陀螺读到
> 机身 8~12Hz 的摆动 → D 项放大 → 电机满幅 → 机身被带着继续摆, 自激。
> 内环总延迟 ~17ms, 极限环频率由延迟决定 (gyro_lpf 0.3→8.4Hz, 0.8→12.4Hz),
> 所以**调参只能挪频率, 断不掉**。kd=0.4 实测: pitch 标准差 0.01°,
> 输出标准差 0.12%, 饱和帧 0% → 死稳。
> 想找回阻尼余量, 正确做法是给 D 路加 8~20Hz 的陷波 (保持低频相位)。

### 0.32 的代码结构变化: `user/trace/`

0.31 的跟踪代码内嵌在 `balance.c` 里 (环形缓冲 + `ESP_LOGI` 实时打印 + 回灌),
有两个问题:

1. **在控制任务里打印会污染测量**。一次 `ESP_LOGI` 写一百多字节要几毫秒,
   等于给平衡内环加了一段几十毫秒的延迟 —— 内环本来就在相位裕度边缘,
   这一下足以把车顶出振荡, 而且测出来的数据本身就是被打印污染的。
2. **采样期和打印期混在一起**, 想抓"起立那一刻"的波形必须守着串口。

0.32 拆成两个角色:

| 角色 | 谁做 | 干什么 | 耗时 |
|---|---|---|---|
| 采集 | 控制任务调 `trace_push()` | 只往内存环形缓冲写一条 | 几百纳秒, **不碰串口** |
| 输出 | `trace` 组件的独立任务 (钉 core 0) | 实时打印 + 收到请求后回灌历史 | 阻塞也不影响控制环 |

环形缓冲 600 条 × 10ms = **6 秒**历史。状态从"平衡中"变成别的 (摔倒 /
关平衡 / 退出) 时自动回灌, 不用卡时间点守着采集。

行格式 (固件 / 采集脚本 / 分析脚本 三方统一, 改一处要同步改三处):

```
TRACE t=1.234 pitch=-0.50 gyro=-12.3 out=8.0 tgt=0.20 spd=2.0 \
      yaw=0.0 pos=1.2 pos_out=0.0 kd=0.40 dt=10.0 st=2
```

CSV 表头: `t_ms,pitch,gyro,out,tgt,spd,yaw,pos,pos_out,kd,dt,st`

### 八、2026-10-26 追加修复 (反馈: "能稳两三分钟, 然后角度一大 / 一碰 / 一让走就剧烈抖动")

**根因: 姿态角反馈通道的滞后太大, 扰动一来就过冲。**

平衡环是个穿越频率 2~4Hz 的高增益回路, 任何加在反馈通道上的**滞后**都会
直接变成相位损失。旧固件里有两处滞后叠在一起:

| 位置 | 旧值 | 换算成滞后 | 后果 |
|---|---|---|---|
| 互补滤波系数 `alpha` (mpu9250.c) | 0.98 | 加速度纠偏的时间常数 τ = dt/(1−α) = **0.5s** | P 反馈用的是**半秒前**的姿态角 |
| `gyro_lpf` (陀螺低通) | 0.2 | τ = dt/0.2 = **50ms** (截止 3.2Hz) | D 项 (唯一的阻尼源) 被延迟 50ms |

平衡环穿越 2~4Hz 时, 0.5s 滞后 = 0.8 个周期 ≈ **290° 相位损失**;
D 项上再叠 50ms 延迟 = 在 3Hz 处再丢 **54°**。
→ 回路只剩一点点相位裕度, **静止时误差≈0 看着没事, 一有扰动就被激起大幅振荡**。

这正好解释了症状的形态: 站着不动没事 / 碰一下就抖 / 角度一大就抖 / 一走就抖。

**离线仿真验证** (`test/bal_sim.py`, 新增: 电机死区 + 电机一阶滞后 + 加速度计污染 +
积分抗饱和, 植物参数 81 组组合, 扰动 = 初始歪 8°):

| 配置 | 81 组里没摔 | 末段振幅中位数 |
|---|---|---|
| 旧配置 (α=0.98, gyro_lpf=0.2, 死区"抬到") | **11** | 30.8° |
| 新配置 (α=0.997, gyro_lpf=0.8, 死区"加上") | **80** | 2.0° |

**修复清单**:

| 文件 | 改动 | 理由 |
|---|---|---|
| `hardware/mpu9250/mpu9250.c` | 互补滤波 `alpha` 0.98 → **0.997** (τ 0.5s → 0.03s) | 陀螺零偏已存 NVS 标定好, 可以大幅提高陀螺权重; 姿态角反馈不再滞后半秒 |
| `user/param/param.c` | `gyro_lpf` 默认 0.2 → **0.8** (τ 50ms → 12ms) | D 项是唯一的阻尼源, **不能加延迟**; MPU 自带 41Hz 数字低通已经够用 |
| `hardware/motor_driver/motor_driver.c` | 死区补偿从"**抬到**"改成"**加上**" | 旧做法**根本没补偿死区**: 输出抬到 dz 之后, 电机要转还是得自己超过硬件死区 D, 跟 dz 无关。改成"加上"后有效死区 = max(0, D−dz), 且小输出也能得到连续力矩 (不再有"突跳") |
| `user/control/balance.c` | 控制任务绑到 **core 1** | IDF 的 WiFi 任务 (优先级 23) 在 core 0, lwIP tcpip 任务 (优先级 18) 两个 core 都跑 → 会抢占优先级 7 的控制任务, 10ms 周期被抖成 20~30ms |
| `sdkconfig` / `sdkconfig.defaults` | `CONFIG_LWIP_TCPIP_TASK_AFFINITY_CPU0=y` | 把网络协议栈赶出 core 1, core 1 只留给控制任务 |
| `hardware/k230_uart/k230_uart.c`, `hardware/voice_module/voice_module.c` | UART 事件任务优先级 10 → **6** | 原来比控制任务 (7) 还高, K230/语音一有数据就抢控制环的 CPU |
| `user/control/balance.c` | 新增 `BAL_TRACE_ENABLE` 编译开关 (默认关) | 打开后每 100ms 打印 pitch/gyro/out/dt, 真机上一眼看出是"读数在抖"还是"控制器在抖" |

> ⚠ **`deadzone` 这个参数现在必须填电机真正的最小启动占空比** (硬件死区 D):
> 填小了补偿不够 (小输出时电机不转, 车会突然猛冲), 填大了每个非零输出都自带
> 一个多余固定力矩 (平衡点附近空转抖动)。测法: 慢慢加 PWM, 看轮子刚要动的那个值。

### 九、2026-10-26 追加修复 (反馈: "一让走就剧烈抖" → 方向键改走速度环)

**根因: App 的方向键走的是"遥控直驱"通道 —— 平衡环整个被暂停。**

老流程: 方向键 → 直接给电机 PWM → **平衡环和摔倒检测都不跑**。
车是站着的时候这么一推, 等于把平衡环关掉了; 松手时车已经歪了,
平衡环一接手必然剧烈纠偏 → 看起来就是"一让走就剧烈抖"。

**新流程: 方向键 → 目标轮速 → 目标倾角 → 平衡环 (全程在线)。**

```
App 方向键 ──speed 属性──> 目标轮速 (斜坡逼近)
                              │
                              ├─ 速度环 (Kp 0.06 / Ki 0.01) → 目标倾角 (≤ 4°)
                              │        ↓
                              └─ 平衡环 (Kp 12 / Ki 0.5 / Kd 1.5) → 电机输出
                                       ↓
                                  两轮同向 (+ 转向时的差速)
```

| 位置 | 改动 | 理由 |
|---|---|---|
| `user/control/balance.c` | 方向键不再直驱, 改成设**目标轮速**; 平衡环/状态机**始终运行** | 平衡环不撒手, 车就不会"歪了才纠偏" |
| `user/control/balance.c` | 测速改成 **300ms 累加窗口** (3 个 100ms 窗口加起来再换算) | 100ms 窗口的量化台阶是 13.6 rpm (按 gear=1 算), 速度环拿到这种读数会直接顶限幅 (减速比改成 30 之后台阶变成 0.45 rpm, 见"十一"节) |
| `user/control/balance.c` | 新增**差速环** (转向): 左−右 轮速差 → 两轮输出差 | 转向也走速度环, 平衡环照样在线 |
| `user/control/balance.h` | 目标倾角上限 12° → **4°**; 斜坡 20/40 → **15/30** rpm/s; 速度死区 3 → **5** rpm | 倾角上限 = 允许摇多大; 死区必须 ≥ 编码器量化台阶 (当时按 gear=1 算是 4.5 rpm; 减速比改成 30 之后量化台阶变成 0.15 rpm, 死区已再改回 1.0, 见"十一"节) |
| `user/control/balance.h` | 速度环默认增益 0.15/0.05 → **0.06/0.01**; 差速输出上限 35% → **20%** | 仿真结论 (见下); 差速吃太多会削掉平衡环的出力 |
| `user/param/param.c` | `spd_kp` 默认 0.06 / `spd_ki` 默认 0.01; 参数表版本 12 → **13** | 版本 +1 让 NVS 里的旧值作废, 烧录后自动回到新默认值 |
| `app/common/paramDef.js` | 默认值表同步 + `PARAM_VER` 13 | App 侧必须跟车端一致, 否则 App 一保存就把车改回旧值 |
| `app/utils/control.js` | 方向键的注释改成"走速度环" | 文档与实现一致 |
| `test/bal_sim.py` | 新增**行走模型** (车真的会平动) + `--walk` / `--walk-scan` | 原来的定轴模型验证不了"走" |

**仿真结论** (`test/bal_sim.py --walk`, 27 组植物参数: 死区 8/12/16%,
电机增益 ×0.7/1.0/1.4, 滞后 30/50/80ms, 目标 24 rpm):

| 速度环 | 车身倾角波动 (中位 / 最大) | 速度误差 (中位) | 摔 |
|---|---|---|---|
| 旧默认 (0.15 / 0.05, 倾角上限 12°) | **10.7° / 28.9°** | 16.9 rpm | 0/27 |
| **新默认 (0.06 / 0.01, 倾角上限 4°)** | **3.5° / 6.8°** | 7.8 rpm | 0/27 |

走着被推 25°/s 也不摔 (倾角波动中位 3.5°)。
**倾角上限就是"允许摇多大"** —— 上限 12° 时车会大幅摇摆, 看着就是"剧烈抖";
上限 4° 时只有 ±1.7° 左右的轻微晃动, 走起来是稳的。

> ⚠ 仿真只是方向性参考 (植物参数是猜的), 最终要在真机上复核。
> 仿真里"目标 12 rpm 走不动"是因为电机的硬件死区比那点轮速需要的力矩还大 ——
> 这也说明 `deadzone` 填准很重要。

> ⚠ 改了参数表版本 → 烧录后 NVS 里的旧值作废, **配平表和配平零点要重新标一次**
> (App 的「配平」按钮, 或网页的标定面板)。


### 十、2026-10-26 追加修复 (反馈: "起立就立马剧烈抖动" → 陀螺零偏标定永远失败)

**根因: 标定代码把"零偏大"误判成"在动", 标定 100% 失败 → 零偏永远是 0。**

`mpu9250_calibrate_gyro()` 旧逻辑: 任一轴 `|原始读数| > 2°/s` 就丢掉这个样本。
但**绝对值大 = 零偏大**, 而零偏正是要测的量! 本机 MPU6500 的 Y 轴零偏就有
**4.73 °/s** → 每个样本都被判成"在动" → 100 个样本被剔除 99 个 → 标定永远失败。

零偏补偿不了 → 姿态角带一个**恒定误差**, 互补滤波把它放大:

| alpha | 放大系数 dt/(1−alpha) | 残余零偏 0.9 °/s → 姿态角误差 |
|---|---|---|
| 0.98 (0.30) | 0.5 | **0.45°** (能忍) |
| 0.997 (0.31 第一节改的) | 3.33 | **3.0°** (致命) |

3° 的假倾角 → 平衡环以为车歪了 3° → 轮子猛冲 → **"起立就立马剧烈抖动"**。

**修复**:

| 文件 | 改动 |
|---|---|
| `hardware/mpu9250/mpu9250.c` | 标定的运动判定改成**标准差 σ** (不是绝对值, 也不是极差); 阈值 2.0 → 2.5 °/s |
| `hardware/mpu9250/mpu9250.c` | 每次上电都重新标定 (成功就存 NVS), 失败才退回 NVS 里那份; 失败重试一次 + 大声报错 |
| `hardware/mpu9250/mpu9250.c` | 标定日志打印 均值/标准差/极差, 便于以后判断零偏合不合理 |

**为什么用标准差**: 极差 (max−min) 对单个离群样本太敏感 —— 本机静止时极差能到
3.5 °/s (复位瞬间的震动), 而 σ 只有 0.13~0.17 °/s。σ 对离群点稳健得多。
实测静止 σ ≈ 0.15 °/s, 阈值 2.5 °/s 有 16 倍余量; 真动手 (几十 °/s) 一抓一个准。

**为什么改成"每次上电都标定"**: 零偏会随温度漂 —— 本机实测冷机 0.92 °/s,
热机 0.67 °/s, 差 0.25 °/s = **0.83° 的姿态角误差**。存一份 NVS 零偏用一整天,
温度一变它就不准了。每次上电重标 = 零偏跟当前温度对得上。

### 十一、2026-10-26 追加: 减速比 30 / 手持标定 / 零漂跟随 / 磁力计观察 / 配平标定入口

数字"。

| 四 | 陀螺零偏标定改成"**挑最稳的 0.25 秒窗口**" (手持也能标定成功) | `hardware/mpu9250/mpu9250.c` |
| 五 | 新增零偏**慢漂跟随** (只在不处于平衡状态时允许) | `hardware/mpu9250/mpu9250.c` / `user/control/balance.c` |
| 六 | **磁力计** (AK8963 bypass 探测 + 每秒日志) + **配平标定入口** (4 个云端服务 + App 页面) | `hardware/mpu9250/mpu9250.c` / `user/onenet_client/onenet_client.c` / `app/pages/trim/trim.vue` |

#### 一、减速比 30 + 新的轮速上限

- **为什么改**: 编码器装在**电机轴**上, 减速箱 30:1, 轮子最高转速 333 rpm (用户实测)。
  之前 `gear=1.0` 意味着"轮子转一圈 = 编码器 44 个脉冲", 但实际是 1320 个脉冲 ——
  算出来的轮速大了 30 倍, 速度环一开就顶满目标倾角, 车自己跑偏。
- **改了什么**: `gear` 默认 1.0 → **30** (范围 0.1~50, 步进 0.1);
  新增参数 `move_rpm_max` (默认 **100** rpm, 范围 0~333) 作为"App 方向键 100% 档位
  对应的目标轮速"; `BAL_MOVE_RPM_MAX` 这个兜底宏 60 → **100**;
  真正生效的上限改成查参数表 (`balance_move_rpm_max()`), App 参数页能实时调。
- **为什么 100 而不是 333**: 轮子最高 333 rpm 是**空载**极限; 目标轮速越大,
  速度环要求的车身倾角越大, 而倾角被 `BAL_WALK_PITCH_MAX` (4°) 卡着 ——
  目标太大时车只会一直倾着追速度, 表现为左右猛摇。100 rpm 约为最高转速的 30%,
  留足余量, 速度环在 100 rpm 以内跟得住。
- **注意事项**: 填错 `gear` 会让轮速算错 (30 倍 → 速度环饱和 / 跑偏)。
  验证方法: 手动把左轮**整整转 1 圈**, 看遥测 `enc_l` 变化: 变 44 → 编码器在轮轴上
  (`gear` 填 1); 变 ~1320 → 编码器在电机轴上 (`gear` 填 30)。

#### 二、速度环增益的步进改成 0.01 (App 上调不动, 静默失效)

- **为什么改**: 车端 `param_set_float()` 会用 `snap_to_step()` 把下发值吸附到
  step 的整数倍。原来 `spd_kp` 的 step 是 0.5, 于是:
  - 想设 **0.06** → `min(0) + round(0.06/0.5)*0.5` = **0.0**
  - 想设 **0.3** → **0.5**

  也就是说 App 上拖速度环增益, 车端要么给 0 要么给 0.5, **中间的值一个都设不进去**。
  设成 0 还不算彻底坏 —— `balance.c` 里有兜底常量 `BAL_SPD_KP_DEFAULT=0.06`,
  所以看起来"还能用", 但用户根本调不动, 调参变成盲调。
- **改了什么**: 车端 `spd_kp` / `spd_ki` / `spd_kd` 的 step 统一改成 **0.01**
  (decimals 保持 2, 值域不变); App 侧 `paramDef.js` 同步改成 0.01。
  提示文字里都补了一句"步进 0.01, 步进太粗的话 App 拖出来的中间值会被吸附掉"。
- **注意事项**: step 只是"怎么吸附", **不改变参数表的 blob 布局和默认值**,
  所以 `PARAM_DATA_VERSION` (车端) 和 `PARAM_VER` (App) 都**不用动**, 仍然是 14。
  但 App 和车端必须**同时**改 —— 只改一边会出现"App 拖 0.06, 车端按 0.5 吸附"。

#### 三、速度死区 5.0 → 1.0 rpm, 量化台阶的注释全部重算

- **为什么改**: 死区必须 ≥ 编码器量化台阶, 免得车为了追量化噪声一直歪着。
  换算公式: `rpm = 脉冲数 × 60 / (窗口秒数 × 44 × gear)`。
  gear 从 1 改成 30 之后, 300ms 窗口下 1 个脉冲从 **4.5 rpm** 变成 **0.15 rpm**,
  而死区还停在按 4.5 rpm 定的 5.0 rpm —— 相当于把 5% 的目标速度误差直接丢掉
  (目标 100 rpm 时死区 5 rpm), 太粗了。
- **改了什么**: `BAL_SPD_ERR_DEADBAND` 5.0 → **1.0** (≈ 6.6 个量化台阶:
  既滤掉量化噪声, 又不吃掉真实的速度误差); `balance.c` / `balance.h` 里所有写死的
  "1 个脉冲 = 136 rpm" / "13.6 rpm" / "4.5 rpm" 全部按 gear=30 重算
  (10ms 窗口 4.55 rpm / 100ms 窗口 0.45 rpm / 300ms 窗口 0.15 rpm),
  并注明**这些数字依赖 `gear` 参数, 改了 gear 就要重算**。
- **注意事项**: 300ms 累加窗口**保持不变** —— 减速比改 30 之后连 100ms 窗口的
  台阶都只有 0.45 rpm 了, 300ms 窗口额外起低通作用, 测速延迟也更小。

#### 四、陀螺零偏标定: 拿稳 0.25 秒就能成功

- **为什么改**: 旧标定要求"整段采样 σ ≤ 2.5 °/s", 手持一定超 → 标定永远失败 →
  零偏用 0 → 姿态角恒差约 3° → 起立就剧烈抖。
- **改了什么**: 采 200 个样本存进静态数组, 用 **25 个样本 (≈0.25s) 的滑动窗口**
  在整段上滑, 每个窗口算三轴均值和 σ, 取**三轴 σ 最大值最小**的那个窗口;
  成功则用该窗口的**中位数**当零偏 (比均值抗离群点), 失败**不写 NVS**
  (保留旧零偏)。日志会打"最稳窗口: 起点 #N"。
- **注意事项**: 手持晃动只会让"最佳窗口"更难找, 不再直接判失败 ——
  只要能拿稳 0.25 秒就能标成功。**标定失败时不写 NVS**, 所以失败一次不会把
  之前标好的零偏弄坏。

#### 五、零偏慢漂跟随

- **为什么改**: 零偏随温度漂 (冷机 0.90 → 热机 0.65 °/s), 互补滤波把残余零偏
  放大 1/(1−alpha) ≈ 333 倍 → 姿态角差 0.83° → 车带着倾角站、慢慢往一边跑。
- **改了什么**: `mpu9250_read_data()` 里维护 100 个样本的滚动窗口, 统计**扣过零偏后**
  三轴绝对值之和的平均值; 平均 < 0.5 °/s (判静止) 且距上次调整 > 30 秒 →
  `bias_k += 0.05*(raw_k - bias_k)`。
- **注意事项**: 跟随**只在不处于平衡状态时允许** (`mpu9250_set_bias_tracking()`,
  由 `balance.c` 的控制任务每周期调用) —— 车站着顶的时候读数里全是真实角速度,
  拿它当零偏会把真实运动吸进零偏里, D 项阻尼失准 → 越晃越歪。
  标定与跟随互斥 (标定期间跟随让路)。

#### 六、磁力计 (只观察, 不做航向融合)

- **为什么改**: 板子确实是 9 轴, 磁力计读得出来, 但芯片是"盗版"的, 需要先确认
  能不能读到。
- **改了什么**: 按参考工程 3.4 移植 AK8963 bypass 探测
  (`INT_PIN_CFG |= 0x42` + `USER_CTRL = 0` → 读 0x0C 的 WIA, 期望 **0x48**),
  找到后读 0x0F 的厂标 ASA 做灵敏度换算 (`uT = raw × adj × 0.15`),
  再开 0x12 的 16bit 连续模式, 每秒打一条日志 (`MAG raw(...) uT(...)`)。
- **注意事项**: **读数不参与任何姿态解算**, 只做观察。**用户明确要求先不做航向融合**
  —— 互补滤波里加磁力计会带来它自己的滞后问题, 没有实测数据前不冒险。
  没找到 AK8963 时只打告警, **不报错退出, 不影响加速度/陀螺**。

#### 七、配平表标定入口 (车端 4 个云端服务 + App 新页面)

配平表 (`user/trim/trim.c`) 早就实现了, 但**没有任何地方能往表里录点** ——
表永远是空的, 补偿恒为 0, 换腿高就得重新配平。

- **车端**: 新增 `balance_record_trim_point()` (取舵机角 + **原始** pitch 存表)
  和 `balance_get_trim_json()`; 云端服务 `trim_record` / `trim_save` / `trim_clear` /
  `trim_get` (输出统一是 `values`, string)。
- **App**: 新页面 `app/pages/trim/trim.vue`「配平标定」; `app/pages.json` 注册该页
  (普通页面, **不**进 tabBar); 状态页加一个「去标定」入口。
- **标定流程 (顺序不能乱)**:
  1. 先在 **servo_c 那一档 (默认 80°)** 用遥控页的「配平」采**配平零点**
  2. 再进配平标定页, 拨腿 (30°~100°), 每个姿态扶稳后点「记点」, 录 **6~8 个点**
  3. 最后点「保存到 NVS」
- **注意事项**:
  - 表里存的是**原始 pitch** (`pitch_raw`), 不是修正后的 pitch ——
    修正链里还会再扣一次 `trim_pitch()`, 存修正后的会重复扣一次。
  - 标定时页面显示的也是**原始 pitch** —— 修正后的 pitch 在表没录满时跟
    "平衡姿态"对不上号, 拿它判断姿态会误导人。
  - **OneNet 后台要手动加这 4 个服务** (`trim_record` / `trim_save` / `trim_clear` /
    `trim_get`), 输出参数都配一个 `values` (string)。不加的话 App 点按钮报
    `10412 identifier not exist`。
  - 记完点后看串口日志里的"配平表俯仰角跨度" —— 正常应该有几度的跨度
    (换腿高差约 10°); 跨度接近 0 说明每次都扶成了同一个姿态。

#### 八、收尾时踩到的两个坑

1. **减速比 30 之后量化台阶从 4.5 rpm 变成 0.15 rpm, 速度死区 5 rpm 过粗** ——
   死区是按"量化台阶"定的, 换算比一变就必须重算, 否则要么噪声进目标倾角,
   要么把真实的速度误差一起吃掉。
2. **速度环增益 step 0.5 导致 App 拖出来的中间值被吸附掉** ——
   `param_set_float()` 的 `snap_to_step()` 是**静默**的: 值被改了, 不报错,
   车端还有兜底常量, 看起来"还能用"。这类问题只能靠"车端 step 和 App step
   都改成细粒度 + 离线测试断言 `param_set_float(0.06)` 之后还是 0.06"来防住。

## 0.30 相对 0.22 改了什么

**0.30 是从 0.22 干净复制出来的新迭代基线**, 收编了 0.22 发布之后
(`v0.22` tag 之后) 在 0.22 目录里做的一批修复, 并把版本号整体推到 0.30。

> 0.22 的 GitHub release 是在那批修复之前发布的, 所以 **0.30 是第一个
> 包含"车能自己站住"这批修复的正式发布版本**。

> ⚠ **本节里的编码器量化台阶数字 (13.6 / 136 rpm) 是按 `gear=1` 写的** ——
> 那是 0.30 当时的状态。0.31 实测减速比是 **30:1**, 300ms 窗口的真实台阶是
> **0.15 rpm**, 速度死区也已从 5 rpm 改成 **1.0 rpm** (见上面"十一"节)。

### 一、平衡控制三处致命修复 (真机验证)

| 问题 | 症状 | 根因 | 修复 |
|---|---|---|---|
| 电机方向常量取反 | 车往前扑倒; 快扶正时轮子猛转 | `BAL_MOTOR_SIGN` = -1, 但实测"电机正转 = 轮子往车尾跑" | 改成 **+1** (`user/control/balance.h`) |
| 平衡环 D 项符号反了 | 起立时剧烈抖动, 站不住 | `kp*err + ki*i - kd*rate` → 阻尼项变成**负阻尼**, 越晃越大 | 改成 **+kd*rate** (`user/pid/pid.c`) |
| 速度环吃 10ms 编码器量化值 | 电机前后猛顶 | 1 个脉冲 = 136 rpm, 2 rpm 误差就把目标倾角打到限幅 | 轮速改 **100ms 窗口**统计; 速度环默认关 (`spd_kp`/`spd_ki` = 0) |

另外把积分限幅改成按**输出量**算 (`i_max = (out_max/2)/Ki`), 原来直接写 `out_max/2`,
乘上 Ki=12 后积分项能到输出的 180%。

### 二、其它固件修复

- `motor_max` 默认 30 → **60** (方向修正后实测接得住)

- 编码器增量改成 `(int16_t)(cur-last)`: PCNT 计数到 ±32767 会回绕, 按 int 相减会算出 65535 的假增量
- MPU9250 初始化失败**重试 10 次** (间隔 500ms): 实测上电第一次读 WHO_AM_I 会失败
- **配平表不再每次上电被擦除** (`balance_init()` 只 `trim_load()`), 修掉"网页标定一断电就归零"
- **AP 配网热点开不起来**: `start_ap_mode()` 设 IP 前先 `esp_netif_dhcps_stop()`,
  失败不再中断 (原来一失败就 `return`, `esp_wifi_start()` 永远没执行 → 热点一帧都不广播);

### 七、2026-10-26 追加修复 (反馈: "点了恢复默认后, 车只朝一个方向转, 根本稳不住")

**根因不在控制算法, 在 App 的"恢复默认"**。

App 的"恢复默认"以前是把 **App 内置的默认值表整份下发**到车端, 而那份表早就跟
车端脱节了 —— 还停在 v7 的旧值:

| 参数 | App 旧默认 (v7) | 车端默认 (v9) | 后果 |
|---|---|---|---|
| `spd_kp` | **20** | 0 | 速度环被意外打开 |
| `spd_ki` | **30** | 0 | 同上, 且积分锁死方向 |
| `bal_ki` | **12** | 0.5 | 积分顶死, 先猛冲再回不来 |
| `motor_max` | **30** | 60 | 出力不够接不住车身 |
| `deadzone` | **8** | 4 | 死区太大, 一顿一顿 |

量化一下"速度环被打开"有多致命:

- 轮速用 **100ms 窗口**统计, 编码器 44 脉冲/转 → **1 个脉冲 = 13.6 rpm** 的量化台阶
- `spd_kp=20` → 一个脉冲的误差就产生 `20 × 13.6 = 273°` 的目标倾角需求
  (限幅只有 40°) → **基本每个控制周期都在限幅上**, 平衡环跟着饱和 → 电机前后猛顶
- `spd_ki=30` → 积分项最大 20°, **方向由误差符号决定, 会锁死在一个方向**

## 驱动方式: 双轮同向 (不是差速)

平衡靠两轮**一起**朝倒的方向跑, 用轮子的牵引力把重心甩到轮轴上方 ——
标准 inverted-pendulum-on-wheels 平衡车做法。

差速只能让车**原地转**, 产生不了托住重心所需的平移加速度, 扶不住倒下的车身。

| 常量 | 值 | 说明 |
|---|---|---|
| `BAL_MOTOR_SIGN` | `+1` | **2026-10-25 真机实测复核**: 前倾 (pitch<0) 时电机输出必须为负, 轮子才会往车头方向跑去接住车。之前取 `-1` 正好反了 → 车往前扑倒 |
| `GYRO_PITCH_SIGN` | `+1` | 实测: 前倾时 `pitch` 与 `gx` **都是负数**, 两者同号 (互补滤波自洽) |
| `PITCH_ZERO_REF` | `90.0°` | 2026-10-15 新四连杆结构: 水平位 az≈1, ay≈0 → atan2(1,0)=90° |

> ⚠ **本工程的姿态角符号**: 车头前倾 (车头往下) = **负数**。
> 实测装机: 车的上方向 = MPU 的 **Z 轴**, 车头方向 = MPU 的 **-Y 轴**,
> 俯仰 = 绕 MPU 的 **X 轴**旋转。详见 `hardware/mpu9250/mpu9250.c` 的注释。

这三个数**只有拆电机 / 换 MPU 装配方向**才会变, 一年也碰不到一次。
留成网页滑块反而是隐患: 被误碰 / 不小心存盘, 下次烧录就翻车。

## 控制结构

```
速度环 (外环, 慢)  ──> 目标倾角 target_pitch (°)
     │                    ↑ App 方向键 = 目标轮速 (斜坡逼近)
     ▼
平衡环 (内环, 快)  ──> 电机输出 (%)  ──>  两轮同向 (+ 转向时的差速)

输入: MPU 姿态角/角速度 + 编码器轮速
输出: 电机 A/B PWM (两轮同向) + 两路舵机
```

**控制周期 10ms 单环串级**, 用 `vTaskDelayUntil` 保证周期稳定。
站立时目标轮速恒为 0 (原地保持); App 方向键按下才给目标轮速, 且
**平衡环全程在线** (不再有"直驱"通道把平衡环关掉)。

### 代码组织 (2026-10-27 拆分)

各控制环的 PID 运算拆到了独立组件 `user/pid/`, 每个环一个文件:

| 文件 | 环 | 输入 → 输出 |
|---|---|---|
| `user/pid/pid.c` | 通用 PID 算法 | 位置式 PID + 角速度反馈型 D 项 |
| `user/pid/balance_pid.c` | 平衡环 (内环) | 姿态误差 + 角速度 → 电机输出 (%) |
| `user/pid/speed_pid.c` | 速度环 (外环) | 轮速误差 → 目标倾角 (°) |
| `user/pid/steer_pid.c` | 转向环 (差速环) | 左−右 轮速差 → 两轮输出差 (%) |
| `user/pid/position_pid.c` | 位置环 (**预留, 未接入**) | 位置误差 → 目标轮速修正 (rpm) |

`user/control/balance.c` 只剩传感器采样 / 状态机 / 摔倒检测 / 电机输出 / 对外 API。

位置环目前**没有接进控制流程**: 工程里没有里程计 (编码器只能给瞬时转速,
积分成位移需要轮径参数), 拿不到位置反馈。文件先建好、接口定死,
等里程计做好了直接接。

## 姿态读数的修正链

```
pitch_修正 = pitch_原始 − trim_pitch(舵机角, 舵机中心角)
```

`trim_pitch` 是配平表 (`user/trim`)。在信号侧减而不是在目标倾角上加, 这样
摔倒判定 (`|pitch| > ang_limit`) 也跟着被修正, 否则腿弯多了会误判摔倒。

## 状态机

```
IDLE ──(启动)──> STANDBY ──(连续稳定 arm_time)──> BALANCING
                                                    │
                                               (倾角超限)
                                                    ▼
                                                 FALLEN
                                                    │
                                              (人把车扶正)
                                                    ▼
                                                 STANDBY
```

- **IDLE**: 未启动, 电机刹车
- **STANDBY**: 已启动但还没进平衡 (等姿态连续稳定 = 启动门控)
- **BALANCING**: 控制中
- **FALLEN**: 判定摔倒, 电机已停、积分已清, **等扶正后自动回 STANDBY**

**启动门控**: 必须连续满足 `|pitch| < arm_pitch` 且 `|角速度| < arm_rate`
达 `arm_time` 毫秒才放行。原因是"没超限"和"稳得住"完全是两回事 ——
被扶着还在晃就放行, 电机一接手晃得更厉害, 直接摔。

**摔倒判定**: `|pitch| > ang_limit` (默认 25°)。宁可误停也不能不停。

## 硬件映射

编号统一为「物理左 = 1, 物理右 = 2」。

| 实物位置 | 编码器 | 电机 | 舵机 |
|---|---|---|---|
| 左 | `ENCODER_1` = GPIO45/46 | `MOTOR_A` = PWMA (GPIO15) | `SERVO_1` = GPIO14 |
| 右 | `ENCODER_2` = GPIO41/42 | `MOTOR_B` = PWMB (GPIO16) | `SERVO_2` = GPIO13 |

## 调参方式

0.14 起调参**改走 OneNet App**, 不再有网页调参服务器
(`http://192.168.4.1` 那个页面在 0.14 就删了, 0.2 里只剩 AP 配网页)。

- App "参数"页: 拉取 (显示车上的真实值) → 改滑块 → 保存 → 落盘 NVS
- 参数表 **20 项**, 定义见 `user/param/param.c` (`PARAM_DATA_VERSION 17`),
  App 侧镜像在 `app/common/paramDef.js` —— **改了一边必须同步另一边**
  (包括 `step`: step 不一致时 App 拖出来的值会被车端吸到别的档上)
  ⚠ **0.32 特别提醒**: `bal_kd` 的默认值两边曾经脱节 (车端 0.4 / App 1.5),
  App 下发时用的是 App 里的值 → 车照旧打摆。改默认值**两边都要改**。
- App 的"恢复默认"由**车端执行** (下发 `{"_reset":true}`), 不用 App 本地的默认值表,
  免得两边默认值脱节把车参数改坏 (2026-10-26 出过这个事故, 见上文第七节)
- 屏上也能看状态 (菜单 → 平衡控制页), 但不能改参数

## 下一步要做的事

0. ⚠ **先把 `gear` (减速比) 填对**: 电机转速/轮转速, 带减速箱就填实际比值。
   不填对的话编码器速度全错, 任何跟速度有关的判断都不可信。
1. **先做配平标定** (不标定腿一动车就歪, 永远站不起来)
   - 配平按钮在 **App 的控制页** (服务 `calibrate`): 把车扶到平衡点再按,
     采 0.5 秒的 pitch 取平均当零点, **结果存进 NVS, 断电不丢**。
   - 屏上**没有**配平面板 (只有 MPU 调试页的陀螺仪标定 K2), 别按网页找。
   - 2026-10-26 起: 起立时若 pitch 与上次标定相差 ≤1°, 设备会**自动微调零点**;
     超过 1° 则不动零点, 串口日志会提示按 App 的「配平」。
2. **试车前把 `motor_max` 压到 25 以内** (方向还没确认过时宁小勿大;
   2026-10-25 方向已真机确认, 默认值已提到 60)
3. 扶正车 → 启动 → 看到启动门控计时满 `arm_time` 后电机才开始输出
4. 观察车往**倒的方向**冲 = 方向正确 (已烘焙在 `balance.h` 里, 2026-10-25 实测通过)
5. **只调平衡环, 速度环先关着** (`spd_kp`/`spd_ki` 默认 0)。
   站着的时候目标轮速恒为 0, 开速度环只会把编码器量化噪声放大成抖动。
6. 调平衡环的顺序 (一次只动一个参数):
   - `bal_kp`: 车软趴趴站不住 → 往上加; 高频嗡嗡抖 → 往下减
   - `bal_kd`: **默认 0.4, 不要再加**。>1 会激起 8~12Hz 满幅打摆自激 (实测);
     出现高频嗡嗡声就减小。想加阻尼余量要走"给 D 路加陷波", 不是加大 kd
   - `bal_ki`: 最后才加, 只用来消"站住了但慢慢歪"的残余偏差;
     一加就猛冲就说明配平没标好, 回配平去
7. **全程扶着车, 随时准备断电**

> 0.30 修了三个致命问题, 刷完新固件请先看 `../logs/2026-10-25.md`:
> ① 电机方向反了 (`BAL_MOTOR_SIGN` 取反), 车往前扑倒;
> ② 平衡环 D 项符号反了 (负阻尼, 必然站不住);
> ③ 速度环用 10ms 编码器读数 (1 个脉冲 = 136 rpm, 把目标倾角打到限幅 → 电机前后猛顶)。
